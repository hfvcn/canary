## 三、明确可采纳的发现（共 8 条）

以下条目均经代码核实，有真实代码依据，跨多份文档共识。

### A1｜Phase 1 监控器必须先 Observe-only，不能直接阻断

**共识来源**：gedt-6（置信度 1.0）、gedt-6-m（1.0）、gp-6-n、gpp-6-n、gedt-6-n、groh-6-n — **6 份独立文档一致**

**代码印证**：当前 `workflow_monitor.py` 是纯函数 + warn-only，Orchestrator 调用后只记日志，不阻断。v4 系统依赖 `_fallback_to_group_actors`（ARCH-2）和 `_resuggest_ready_tasks`（ARCH-3）才能完成 E2E。如果 Phase 1 立即部署阻断模式，这两条路径会立即触发不变量违规，系统无法跑通任何工作流，Phase 2 的修复无法被验证。

**推荐做法**：
- Phase 1：5 个不变量全部以 `observe`（只记录）模式部署，输出 violation ledger 建立当前违规基线
- 同时定义三档 rollout 语义和对应的恢复路径（observe → warn → block，每档有显式恢复命令如 `cccc workflow resume`）
- Phase 2 修复完成后，只把 `INV-1/INV-2` 切到 `block`；Phase 4 修复完成后，其余切 `block`

---

### A2｜ARCH-6（assignment_id/actor_run_id 透传）必须前移至 Phase 2

**共识来源**：gp-6（severity: critical, 0.96）、gpp-6（critical, 0.93）、gpp-6-n、gp-6-n

**代码印证**：`ralph_service.py:237` docstring 声称"会检查 assignment_id + actor_run_id match"，但实现代码没有这个检查。IPC handler 到 task_ops 的链路只传递 `idempotency_key` 和 `agent_id`。字段存在于合约但在管道中被静默丢弃。

**推荐做法**：
- Phase 2 引入 `BatchAssignmentFailed` 前，先把 ARCH-6 补齐：`workflow_id`、`task_id`、`assignment_attempt_id`、`state_version` 必须在整个 handler 链透传
- Engine/Orchestrator 做 compare-and-swap：不匹配当前 attempt 的回复一律拒绝
- 在这套 ID 体系建立之前，不启用 Option Z

---

### A3｜Phase 4 持久化状态回滚必须升级为硬门槛

**共识来源**：groh-6（severity: critical, 0.85）、gp-6（high, 0.93）、gpp-6（high, 0.89）、gedt-6（high, 0.95）— **4 份文档一致**

**代码印证**：`replay_from_ledger()` 直接 `json.loads()` + `_apply_event()`，无 schema version、无 migration dispatcher。如果 Phase 4 改变 event 格式，旧代码 replay 会静默忽略新字段或崩溃，无法恢复 in-flight workflow。

**推荐做法**：
- 定义事件 schema version（v1 → v2）和 migration dispatcher
- 部署前对活跃 workflow 的 ledger 做物理快照
- 提供可重复执行的迁移脚本（支持 dry-run）
- 演练"有在途 workflow 的回滚 drill"，作为 Phase 4 上线前门槛
- 至少一个版本窗口的双读兼容

---

### A4｜Phase 2 完成条件不应宣称"Foreman owns assignment"全面恢复

**共识来源**：gp-6-m（high, 0.96）、gedt-6（structural, 0.85）

**代码印证**：`_resuggest_ready_tasks()` 在 `orchestrator:1042` 调用，DAG 后续批次完全走 `auto_start_agents=True` 路径，ARCH-3 明确放到 Phase 4 才修。Phase 2 宣称 INV-2 变绿（"没有任何任务分配发生在 Foreman 显式 submit 之外"）是不成立的。

**推荐做法**（二选一）：
- Phase 2 完成条件缩窄为"初始 submit assignment"，明确 DAG 后续批次仍是自动的
- 或将 ARCH-3 前移到 Phase 2，使 Foreman 权威在所有 assignment 入口同时收口

---

### A5｜监控器必须改为 Engine pre-transition hook，不能作为 Orchestrator 事后调用

**共识来源**：gedt-6（medium, 0.85）、gedt-6-m（high, 0.90）、gp-6（high, 0.89）

**代码印证**：`workflow_monitor.py` 是纯函数，在 Orchestrator 的 `on_task_completed()` 和 `monitor_incoming_event()` 等处被调用，仅 `logger.warning()`。这是事后审计，不是预防式 guard。如果状态已经被写入 Engine，monitor 抛异常也无法回滚。

**推荐做法**：
- 5 个核心不变量断言直接嵌入 `WorkflowEngine` 状态转换入口，作为同步 pre-transition hook
- Engine 在接受非法转换之前就拒绝，返回 `TransitionRejected`，不产生任何副作用
- 现有的 `workflow_monitor.py` 函数保留作告警/审计层（事后），不做控制面

---

### A6｜assignment 最小持久化必须前移到 Phase 2 的 Engine

**来源**：gp-6-m（high, 0.91）、gpp-6（high, 0.91）、groh-6（high, 0.80）

**代码印证**：`TaskState` 只有 `agent_id: str = ""`，没有 `assignment_id`、`actor_run_id`、`assigned_by`、`assigned_at` 等字段。daemon 重启时走 ledger replay，如果 assignment provenance 不在事件流里，重启后无法还原谁被授权执行哪个 task。

**推荐做法**：
- Phase 2 时，在 Engine 的 `approve_batch()` 事件中写入最小 assignment record（`assigned_by`、`assigned_at`、`assignment_attempt_id`）
- 读路径同时切到 Engine，`_active_workflows` 降为过渡期副本
- Phase 4 再做完整收敛（删除影子状态、补齐字段）

---

### A7｜Option Z 的 BLOCKED 状态必须定义 DAG 级联规则

**来源**：gedt-6（high, 0.90）、gedt-6-m（medium, 0.90）— 注：仅 gedt 系列，非广泛共识，但代码印证后认定为真实问题

**代码印证**：`_resuggest_ready_tasks()` 在任务完成后立即触发，但没有对应的"任务 BLOCKED 后取消下游"逻辑。如果 Task A BLOCKED，sibling Task B 的 `process_batch_suggestion(auto_start_agents=True)` 仍会继续执行，整体 workflow 永久挂起。

**推荐做法**：
- 任务进入 `BLOCKED` 时，Orchestrator 向所有并行 sibling 任务发取消信号
- 定义 workflow 级 TTL
- 定义 BLOCKED 的"可解封"路径（显式命令）

---

### A8｜Findings 不能只靠提示词注入

**共识来源**：gp-6-n、gpp-6-n、groh-6-n、gedt-6-n — **4 份文档一致**

**分析**：审查文档一致认为纯提示词注入容易产生"引用格式"而非"真正受约束"。这与 Finding #12（AI 在长 session 中失去全局上下文）直接相关。

**推荐做法**：
- 计划 YAML 新增 `finding_refs` 结构化字段，要求声明 `mitigation` 和 `enforced_by`（指向具体规则/monitor/状态机）
- Ralph 校验 finding 是否引用、是否给出 mitigation、mitigation 是否绑定可执行约束
- 错误触发时在响应中附上相关 Finding 原文（响应式注入），替代前置注入

## 四、待进一步核实的发现（共 9 条）

以下发现代码中能找到部分依据，但来自单一审查方，或方案细节需结合实际情况确认。

### B1｜`W_NO_FAILURE_PATH` 规则应升级为关键路径上的 hard gate（gp-6-m，修正：规则目前不存在）

**审查原文**：审查认为这条规则是"warning 级别，应升级为 error"。

**代码事实**：`ralph/validator.py` 中完全没有这条规则，它既不是 warning 也不是 error，而是尚未实现。文档的根因分析（"失败暴露通道缺失"）是准确的，但修复起点是"实现此规则"而非"升级级别"。

**建议**：先实现 `E_NO_FAILURE_PATH`（或 `W_NO_FAILURE_PATH`），对"涉及 assignment / external actor / async decision 的任务"强制要求声明失败处理方式；确定是 warning 还是 error 可在实现时讨论。

---

### B2｜监控 rollout 需要显式三档状态机和恢复语义（gp-6-m + groh-6-n）

A1 只吸收了"先 observe"，但没有覆盖：
- observe / warn / block 三档的具体切换条件是什么
- 阻断后 workflow 进入什么状态（`SAFE_PAUSE`？），如何 resume
- 谁有权解封被监控阻断的 workflow

**建议**：在 Phase 1 设计文档中明确定义三档和对应的 unblock 命令，作为实现前提。

---

### B3｜数据模型先行：缺少 `decision_source`/`rejection_context` 字段（groh-6-n）

**代码印证**：`TaskState` 只有 `agent_id: str = ""`，没有任何"这个 assignment 来自谁的决策"的语义字段。

**审查观点**：这不只是"持久化时机晚"，而是数据模型从 03-26 起就未定义决策权语义，导致历史上三次都重新引入了 fallback 逻辑——因为系统永远没有地方记录"这次为什么这样分配"。

**建议**：在 Phase 2 数据模型中加入 `decision_source`（Foreman 决策事件 ID）和 `rejection_context`（拒绝原因、约束集、retry count）。但具体字段名称和在现有 event 结构中的位置需要结合 `workflow_state_types.py` 设计。

---

### B4｜`reverse-check` 应在 Phase 2.5 而非 Phase 5 引入（gp-6-n）

**审查观点**：Phase 5 才引入 `reverse-check` 意味着 Phase 1-4 整个修复过程只有在线监控，没有离线审计闭环。

**建议**：在 Phase 2 核心修复完成后，立即引入最小版 reverse-check（只检查三条：`NO_SILENT_APPROVAL / FOREMAN_OWNS_ASSIGNMENT / NO_AUTO_DISPATCH`）。Phase 5 再扩展为完整版。

---

### B5｜"Foreman 作为唯一授权源"vs"唯一决策者"（gpp-6-n 独有）

将"NO_AUTO_DISPATCH"改为"NO_UNAUTHORIZED_DISPATCH"，允许 Daemon 在 Foreman 显式下发的授权策略（policy）范围内自动调度，而不是要求每次都同步回问 Foreman。

**待核实**：这是对方案核心约束的概念重构，影响范围大。"授权策略"的边界如何定义、如何防止策略本身被滥用，需要进一步讨论。

---

### B6｜Liveness Invariants 补充（gpp-6-n 独有）

提议补两条 liveness 不变量：
- `EVENTUAL_VISIBILITY`：每个 task 必须在 SLA 内进入 done/failed/blocked，带明确 owner
- `BOUNDED_ESCALATION`：无 actor、Foreman 不响应、verify 超时等情况必须在边界时间内升级

**待核实**：现有 5 条不变量全是 safety 类，缺少 liveness 维度是真实缺口。但 SLA 参数和升级路径的具体设计需要进一步确定。

---

### B7｜动态任务拆分（Option Z "拆分任务"）使 Ralph 静态验证失效（gedt-6 + gedt-6-m 两份）

如果 Foreman 在运行时拆分任务，新节点会绕过 Ralph 的编译期检查，且 Phase 5 的 reverse-check 会将其标记为大量违规。

**待核实**：需确认 v5 方案中"拆分任务"是否是 Option Z 的保留选项。如果是，需要在接受 DAG 变更前同步调用 Ralph verify API 对动态子图做校验。

---

### B8｜统一 assignment decision contract（gp-6-m 独有）

当前方案中，初始 submit 用 `assignments: dict`，失败时用 `BatchAssignmentFailed`，后续解锁用 `TasksReadyForAssignment`——三套消息格式/语义，容易再次漂移（某条路径补了安全轨道，另一条没补）。

**建议**：统一成一套 `AssignmentRequested → AssignmentDecided/Declined` 协议，相同的幂等规则、相同的 timeout/blocked 处理。

---

### B9｜Reflector 子 Agent 强制门控 Findings（groh-6-n 独有）

在 Foreman 提交计划前强制调用轻量 Reflector（专用小模型，上下文仅 Findings + 当前计划），要求输出"合规证明 JSON"（必须引用具体 Finding ID 并说明规避措施），不通过不许提交。把 Findings 从"提醒"升级为"门控"。

---

### B10｜INV-6: NO_IMPLICIT_DECISION（groh-6-n 独有）

提议新增第 6 条负向不变量：Orchestrator 不得包含任何未经 ForemanDecision 的 if-then 自动状态转换（Approved/Assigned）。

**代码印证**：`_fallback_to_group_actors()` 和 `_resuggest_ready_tasks()` 都是这类隐式决策的典型实例，代码完全印证该不变量的必要性。

**注意点**：需精确定义"隐式决策"的边界，避免与正常路由逻辑混淆导致误报。

---

### B11｜Decision Ledger 独立架构（gpp-6-n 独有）

将决策历史从 Engine 状态中分离出来：
- **Decision Ledger**：append-only，存 `decision_id / causation_id / correlation_id / assignment_version`，负责完整历史溯源
- **Engine**：当前状态的唯一投影，不负责保存完整历史
- **Orchestrator**：只驱动 transition，不保存任何业务影子状态

这比"Engine 既是状态权威又是 assignment 权威"的混合描述更清晰，避免职责混淆。引入新的存储层，当前阶段是否合适需评估。

---

### B12｜AssignmentRecord 完整数据结构（gp-6-n 独有）

比 A6 提议的最小持久化更进一步，引入完整的 `AssignmentRecord` 对象：

```
task_id
actor_id
decision_id
decided_by          # foreman / user
decision_reason
constraint_snapshot
assigned_at
```

CLI/IPC 传 `AssignmentRecord[]`，Engine 持久化 `AssignmentRecord`，Monitor 检查 `decision_id` 是否属于 Foreman 决策事件链。这样 INV-2 才是可验证对象而非口号。

---

### B13｜Option Z 重试参数改为 Foreman 下发的 Policy（gedt-6-n + gpp-6-n + gp-6-n 三份）

当前"最多 2 次 + N 分钟"是硬编码在 Daemon 里的业务策略，三份文档都指出这仍然是 Daemon 在做业务决策。

**建议**：由 Foreman 在 `workflow submit` 时以 Policy 形式下发（如 `{"max_retries": 2, "timeout_mins": 10}`），Daemon 只做数值减扣和触发器。Daemon 保留一个不含业务维度的"物理极值兜底"（如全局 30 分钟 SLA timeout），超时直接转 BLOCKED 并告警，不设重试逻辑。

gp-6-n 进一步提议按任务类型分层（interactive / normal / expensive），每类对应不同默认预算。

---

### B14｜Orchestrator 纯状态机重构的硬触发条件（gp-6-n 独有）

当前方案将 Orchestrator 纯状态机重构列为"长期方向"，没有触发条件，现实中容易无限延期。

**建议**：改为满足任一条件即立项启动：
1. Phase 4 后仍有任一 invariant 违规来源于 Orchestrator 内部 if-then 分支
2. 一个新功能需要同时改 Orchestrator、Monitor、Engine 三处才能维持决策边界
3. assignment / retry / readiness 三类事件仍有任一类无法只靠 Engine 权威还原

---

### B15｜负向不变量测试用 xfail/phase expectation matrix 管理（gpp-6-n 独有）

Phase 0 让 5 个不变量测试"全部红色"作为验收条件，会让团队对红灯失去感觉。

**建议**：
- 把这些测试放进单独套件（如 `tests/invariants/`）
- 用 `xfail(strict=True)` 管理每个 Phase 的预期状态
- 明确写出每个 Phase 哪些测试应 `xfail`（预期中的失败）、哪些应 `pass`
- 例如：Phase 2 时 `INV-1/INV-2` 从 xfail 变 green，Phase 4 时全部 green

这样信号更清晰，不污染主 CI。
