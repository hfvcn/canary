## 待解决

> 来源：v4 E2E 实战 + Codex 对抗审查 + 过程审查 + Foreman 反馈

### FIX-11 daemon start 恢复所有 group 的 actor（P1）✅ 待人工验证
> **实施状态**：Batch B（commit 99d3346）。bootstrap_actor_ops.py 新增 active group 过滤，空值安全回退。8 tests 通过。
- **严重度**：Medium — 浪费资源，每个旧 group 的 actor 都启动 claude 进程
- **现象**：`cccc daemon start` 后出现 10+ 个 claude 进程，只有 1 个是当前需要的，其余来自历史 group
- **根因**：daemon 启动时遍历所有 group，恢复所有 `desired_state=running` 的 actor，不区分 group 是否 active
- **改进方案**：daemon 启动时只恢复 active group（`cccc use` 选中的 group）的 actor。非 active group 的 actor 保持 stopped 直到该 group 被显式 `cccc group start`
- **验收标准**：daemon start 后只有 active group 的 actor 启动，`ps | grep claude` 只显示预期数量的进程
- **触发实例**：v4 实测启动后发现 10 个 claude 进程，来自 5 个 group（4 个旧 group 贡献 12 个多余 actor）

### FIX-13 plan.yaml state 自动回写（P1）
- **严重度**：Medium — 导致 ralph suggest CLI 显示 stale state
- **现象**：engine 完成所有任务后，`ralph suggest plan.yaml` 仍显示 T1+T2 为 ready，因为 plan.yaml 的 `state.completed_task_ids` 未更新
- **根因**：engine 更新内存状态和 ledger，但不回写 plan.yaml 文件
- **改进方案**：engine 完成任务/验证后回写 plan.yaml 的 `state.completed_task_ids`；或提供 `ralph sync-state plan.yaml --group GROUP_ID` 命令从 ledger 同步
- **验收标准**：任务完成后 `ralph suggest plan.yaml` 正确反映 engine 状态
- **触发实例**：v4 Foreman 反馈 "had to manually update state.completed_task_ids for ralph CLI to show correct status"
- **影响维度**：体验 +0.5

### FIX-15 ralph validate 无 ledger 事件（P2）
- **严重度**：Low — 无法从日志证明 Foreman 执行过 validate
- **现象**：v4 过程审查中 "Foreman 是否在提交前执行 ralph validate" 判定为"无证据"，因为 validate 只在 CLI 本地运行，不产生 ledger 事件
- **根因**：`ralph validate` 是纯 CLI 命令，不经过 daemon，不写 ledger
- **改进方案**：validate 通过后写一条 ledger 事件（如 `workflow.plan_validated`），记录验证结果（0 error, N warning）
- **验收标准**：执行 `ralph validate` 后 ledger 中出现 `workflow.plan_validated` 事件
- **触发实例**：v4 过程审查 item #1 "判定：无证据 — ledger 无 validate 事件"
- **影响维度**：过程 +0.5

### ARCH-1 workflow submit 无 assignment 字段（P0）✅ 待人工验证
> **实施状态**：Batch C（commit b9debf8）。ReadyBatchSuggestion.assignments 字段、CLI --assignments、Web route、所有 IPC handler 入口透传。5 E2E tests 通过。
- **严重度**：Critical — Foreman 无法通过 submit 指定 task→actor 映射
- **现象**：`ReadyBatchSuggestion`、`BatchDecision`、CLI `workflow submit` 均无 assignment 字段；`TaskRef` 用 `extra="ignore"`，即使在 JSON 里塞 assignment 信息也会被丢弃
- **根因**：contract 层设计时未考虑 Foreman 显式分配的需求（按当时的自动分配设计）
- **代码位置**：`contracts/v1/ralph_ipc.py:74`（TaskRef extra="ignore"），`cli/workflow_cmds.py:99`，`ports/web/routes/workflow.py:58`
- **改进方案**：在 submit 协议中加入 assignment 信息，最小可行是 `assignments: dict[task_id, actor_id]`；完整方案是引入 `AssignmentRecord`（含 `decision_id`、`decided_by`、`decision_reason`、`assigned_at`），同步到 CLI → IPC → Engine
- **注意**：ARCH-6 必须与 ARCH-1 同步前移 — 有了 assignment 字段但没有 `assignment_attempt_id` 透传，新的异步协议仍无法防止陈旧响应重放
- **验收标准**：Foreman 可在 `cccc workflow submit` 时指定每个任务的执行 actor，orchestrator 直接执行不再自行分配

### ARCH-2 _fallback_to_group_actors() 静默覆盖（P0）✅ 待人工验证
> **实施状态**：Batch C（commit b9debf8）。_fallback_to_group_actors 已删除。rejected batch 不再触发 on_batch_started 等副作用，Foreman 收到结构化通知。
- **严重度**：Critical — 无合适 agent 时静默把 rejected 改写成 approved，绕过了"应向 Foreman 报告"的原则
- **现象**：agent pool 无匹配时，orchestrator 将 batch decision 从 rejected 改为 approved，round-robin 分配给现有 peer actor（包括 Foreman 自身）
- **根因**：WF-NEW-4 修复时加入 fallback 解决了当时的匹配失败问题，但违反了"分配失败应暴露"的设计原则
- **代码位置**：`daemon/foreman/workflow_orchestrator.py:397-435`
- **改进方案**：删除 `_fallback_to_group_actors()`；无合适 actor 时通过 orchestrator→inbox 路径向 Foreman 发结构化消息，包含 task_id 和阻塞原因，等待 Foreman 决策
- **验收标准**：agent pool 无匹配时，Foreman inbox 收到包含任务信息的请求指示消息，batch 不自动 approved

### ARCH-3 _resuggest_ready_tasks() 绕过 Foreman（P1）✅ 待人工验证
> **实施状态**：Batch C（commit b9debf8）。_resuggest_ready_tasks 改为向 Foreman 发送 tasks_ready 通知，不再直接调用 process_batch_suggestion。register_and_suggest 也透传 assignments。
- **严重度**：High — 首批 submit 即使改成 Foreman 显式 assignment，后续 DAG 释放的任务仍走自动分配
- **现象**：任务完成后 `_resuggest_ready_tasks()` 直接调用 `process_batch_suggestion(auto_start_agents=True)`，绕过 Foreman 对后续批次的决策权
- **根因**：DAG 门控（FIX-6）实现时直接复用了自动分配路径
- **代码位置**：`daemon/foreman/workflow_orchestrator.py:1103-1151`
- **改进方案**：`_resuggest_ready_tasks()` 发现新就绪任务后，向 Foreman 发"新任务已就绪，请决策"消息，而不是自动处理
- **验收标准**：DAG 下游任务就绪时，Foreman 收到通知并自行提交下一批次的 assignment

### ARCH-9 Phase 1 监控器部署策略错误（P0，执行方案前提）✅ 待人工验证
> **实施状态**：Batch A（commit 99d3346）。MonitorMode 三档枚举（observe/warn/block），默认全 observe。violations 写入 ledger（workflow.monitor_violation 事件），workflow 不中断。47 tests 通过。
- **严重度**：Critical — v5 方案要求 Phase 1 "违规时阻断"，但 v4 系统依赖 `_fallback_to_group_actors()`（ARCH-2）和 `_resuggest_ready_tasks()`（ARCH-3）才能跑通 E2E。如果直接部署阻断模式，所有工作流立即触发不变量违规，开发环境彻底瘫痪，Phase 2 修复无法被验证

### ARCH-11 BLOCKED 状态缺 DAG 级联规则（P1）
- **严重度**：High — Option Z 中任务进入 `BLOCKED` 终态后，DAG 中并行的 sibling 任务仍继续执行并修改代码库，但整体 workflow 永久挂起，造成资源泄漏和不可幂等的 repository 状态
- **来源**：对抗审查 gedt-6（high 0.90）、gedt-6-m（medium 0.90）
- **代码现状**：`_resuggest_ready_tasks()` 在任务完成后立即触发，但没有对应的"任务 BLOCKED 后取消下游"逻辑；任务状态机没有 workflow 级 TTL
- **改进方案**：
  - 任务进入 `BLOCKED` 时，Orchestrator 向所有并行 sibling 任务发取消信号
  - 定义 workflow 级 TTL：超时后强制终止整个 DAG
  - 定义 BLOCKED 的"可解封"路径：由 Foreman 或用户通过显式命令恢复（如 `cccc workflow resume`）
- **验收标准**：任务 BLOCKED 后，sibling 任务在短时间内收到取消信号；workflow 不永久挂起

- **严重度**：High — 当前 `workflow_monitor.py` 是纯函数，在 Orchestrator 的 `on_task_completed()` 等处被调用后只 `logger.warning()`，是事后审计而非预防式 guard。如果将来切到阻断模式，状态已被 Engine 写入，监控器抛异常也无法回滚，形成撕裂状态
- **来源**：对抗审查 gedt-6（medium 0.85）、gedt-6-m（high 0.90）、gp-6（high 0.89）

## 蓝图对齐（ARCH-14~16，蓝图 v0.3 新增）

> 来源：2026-04-04 工作流蓝图 v0.3 对齐讨论
> 定位：架构偏移修复（Phase 0~4）完成后，在 Phase 5 落地蓝图新增能力
> 依赖：ARCH-1~13 修复完成是前提，蓝图能力建立在偏移已修正的基础上

### ARCH-14 Ralph Agent 层实现（P5，蓝图新增）
- **严重度**：Medium — 蓝图核心新增能力，但不影响现有功能运行
- **现象**：Ralph 当前只有静态结构校验，已知局限（RV-15/18/19/20、RO-10n）中的语义问题无法检测
- **蓝图要求**：
  - Gemini CLI Flash 模型，每个 workflow 一个实例
  - 可脱离 workflow 独立启动（`--no-agent` 退回纯静态模式）
  - 只审查 Ralph 标记的"超出结构校验范围"项（基于静态的"超出范围检查项清单"）
  - 不读代码，基于 Ralph 输出 + plan 文本做语义判断
  - 结果标注"仅供参考"，无决策权
  - 运行时验证：执行 `verification_mode: agent` 的模拟测试用例
  - 验证重试上限 2 次，超过升级 Foreman
- **改进方案**：
  - 实现"超出范围检查项清单"静态配置文件（内容来源于问题清单-v5-ralph 二、已知局限）
  - Ralph validate 输出新增 `beyond_scope` 标记
  - 实现 Ralph Agent（复用现有持久化 agent 机制）
  - CLI 增加 `--no-agent` 参数
- **验收标准**：Ralph Agent 可启动、审查超出范围项、返回标注"仅供参考"的建议；`--no-agent` 时退回纯静态模式

### ARCH-15 两阶段拆分对齐（P5，蓝图新增）
- **严重度**：Medium — 保留 Ralph 已有的调度能力，确保与蓝图模块化拆分衔接
- **现象**：蓝图 v0.3 引入两阶段拆分：Ralph 任务拆分（第一阶段）→ Foreman 模块化拆分（第二阶段）。现有 `core.suggest()` / `_unlock_score()` / `_write_sets_conflict()` 需确保在新流程中正常工作
- **蓝图要求**：
  - Ralph suggest() 输出 Task 批次 → Foreman 对每个 Task 做 Module 级拆分
  - Task 间并行安全由 Ralph 负责（依赖分析 + 写冲突检测）
  - Module 间并行安全由 Foreman 负责（统一接口规范 + 模拟 I/O）
  - 批次完成后 Ralph suggest 计算下一批
- **改进方案**：
  - 确认 Ralph suggest → Foreman 模块化拆分 → 执行 → verify → Ralph suggest 下一批的闭环
  - 如需调整 suggest 输出格式以携带更多信息供 Foreman 拆分使用，扩展 `BatchResult`
- **验收标准**：两阶段拆分 E2E 跑通；Ralph 调度算法在新流程中保持有效

### ARCH-16 INV-7 + verification_mode 分流（P5，蓝图新增）
- **严重度**：Medium — 验证与执行分离，是蓝图核心设计
- **蓝图要求**：
  - plan.yaml 支持 `verification_mode: ralph|agent` 字段
  - `ralph` 模式：结果可预期，Ralph 静态判断（exit code 等）
  - `agent` 模式：结果不可预期，Ralph Agent 执行 Foreman 预设的模拟测试用例（贴近真实使用的输入/输出，非静态 pytest）
  - Worker 全程不知道测试输入和预期输出
  - INV-7 `NO_COMPLETE_WITHOUT_FRESH_SELF_TEST`：Worker complete 必须附带当次 attempt 的自测结果
- **改进方案**：
  - TaskSpec 模型新增 `verification_mode` 可选字段（默认 `ralph`，向后兼容）
  - Ralph validator 校验 verification_mode 值有效性
  - verify gate 实现分流逻辑
  - INV-7 先作为可选字段 + warning，后改为必填 + 驳回
- **验收标准**：verification_mode 可声明；ralph 模式走现有路径；agent 模式走 Ralph Agent 路径；INV-7 变绿
