## 待解决

> 来源：v4 E2E 实战 + Codex 对抗审查 + 过程审查 + Foreman 反馈

### FIX-11 daemon start 恢复所有 group 的 actor（P1）
- **严重度**：Medium — 浪费资源，每个旧 group 的 actor 都启动 claude 进程
- **现象**：`cccc daemon start` 后出现 10+ 个 claude 进程，只有 1 个是当前需要的，其余来自历史 group
- **根因**：daemon 启动时遍历所有 group，恢复所有 `desired_state=running` 的 actor，不区分 group 是否 active
- **改进方案**：daemon 启动时只恢复 active group（`cccc use` 选中的 group）的 actor。非 active group 的 actor 保持 stopped 直到该 group 被显式 `cccc group start`
- **验收标准**：daemon start 后只有 active group 的 actor 启动，`ps | grep claude` 只显示预期数量的进程
- **触发实例**：v4 实测启动后发现 10 个 claude 进程，来自 5 个 group（4 个旧 group 贡献 12 个多余 actor）

### FIX-13 plan.yaml state 自动回写（P1）
- **严重度**：Medium — 导致 ralph suggest CLI 显示 stale state
- **现象**：engine 完成所有任务后，`ralph suggest plan.yaml` 仍显示 T1+T2 为 ready，因为 plan.yaml 的 `state.completed_task_ids` 未更新
- **根因**：engine 更新内存状态和 ledger，但不回写 plan.yaml 文件
- **改进方案**：engine 完成任务/验证后回写 plan.yaml 的 `state.completed_task_ids`；或提供 `ralph sync-state plan.yaml --group GROUP_ID` 命令从 ledger 同步
- **验收标准**：任务完成后 `ralph suggest plan.yaml` 正确反映 engine 状态
- **触发实例**：v4 Foreman 反馈 "had to manually update state.completed_task_ids for ralph CLI to show correct status"
- **影响维度**：体验 +0.5

### FIX-15 ralph validate 无 ledger 事件（P2）
- **严重度**：Low — 无法从日志证明 Foreman 执行过 validate
- **现象**：v4 过程审查中 "Foreman 是否在提交前执行 ralph validate" 判定为"无证据"，因为 validate 只在 CLI 本地运行，不产生 ledger 事件
- **根因**：`ralph validate` 是纯 CLI 命令，不经过 daemon，不写 ledger
- **改进方案**：validate 通过后写一条 ledger 事件（如 `workflow.plan_validated`），记录验证结果（0 error, N warning）
- **验收标准**：执行 `ralph validate` 后 ledger 中出现 `workflow.plan_validated` 事件
- **触发实例**：v4 过程审查 item #1 "判定：无证据 — ledger 无 validate 事件"
- **影响维度**：过程 +0.5

## 架构偏移修正（ARCH 系列）

> 来源：2026-04-03 Codex 代码调查 + 文档对比分析
> 背景：详见 [设计偏移发现记录.md](./设计偏移发现记录.md) 和 [ralph-foreman-workflow.md](./ralph-foreman-workflow.md) 第 1 节

### ARCH-1 workflow submit 无 assignment 字段（P0）
- **严重度**：Critical — Foreman 无法通过 submit 指定 task→actor 映射
- **现象**：`ReadyBatchSuggestion`、`BatchDecision`、CLI `workflow submit` 均无 assignment 字段，Foreman 提交 batch 时无法表达"这个任务交给哪个 actor"
- **根因**：contract 层设计时未考虑 Foreman 显式分配的需求（按当时的自动分配设计）
- **代码位置**：`contracts/v1/ralph_ipc.py:103-188`，`cli/workflow_cmds.py:147-148`
- **改进方案**：在 `TaskRef` 或 `ReadyBatchSuggestion` 中加入 `assignments: dict[task_id, actor_id]` 字段；或设计新的 submit 协议让 Foreman 随 batch 一起传入分配决策
- **验收标准**：Foreman 可在 `cccc workflow submit` 时指定每个任务的执行 actor，orchestrator 直接执行不再自行分配

### ARCH-2 _fallback_to_group_actors() 静默覆盖（P0）
- **严重度**：Critical — 无合适 agent 时静默把 rejected 改写成 approved，绕过了"应向 Foreman 报告"的原则
- **现象**：agent pool 无匹配时，orchestrator 将 batch decision 从 rejected 改为 approved，round-robin 分配给现有 peer actor（包括 Foreman 自身）
- **根因**：WF-NEW-4 修复时加入 fallback 解决了当时的匹配失败问题，但违反了"分配失败应暴露"的设计原则
- **代码位置**：`daemon/foreman/workflow_orchestrator.py:397-435`
- **改进方案**：删除 `_fallback_to_group_actors()`；无合适 actor 时通过 orchestrator→inbox 路径向 Foreman 发结构化消息，包含 task_id 和阻塞原因，等待 Foreman 决策
- **验收标准**：agent pool 无匹配时，Foreman inbox 收到包含任务信息的请求指示消息，batch 不自动 approved

### ARCH-3 _resuggest_ready_tasks() 绕过 Foreman（P1）
- **严重度**：High — 首批 submit 即使改成 Foreman 显式 assignment，后续 DAG 释放的任务仍走自动分配
- **现象**：任务完成后 `_resuggest_ready_tasks()` 直接调用 `process_batch_suggestion(auto_start_agents=True)`，绕过 Foreman 对后续批次的决策权
- **根因**：DAG 门控（FIX-6）实现时直接复用了自动分配路径
- **代码位置**：`daemon/foreman/workflow_orchestrator.py:1103-1151`
- **改进方案**：`_resuggest_ready_tasks()` 发现新就绪任务后，向 Foreman 发"新任务已就绪，请决策"消息，而不是自动处理
- **验收标准**：DAG 下游任务就绪时，Foreman 收到通知并自行提交下一批次的 assignment

### ARCH-4 WorkflowEngine 缺 assignment 存储（P1）
- **严重度**：High — engine 不是 assignment 权威，影子状态 _active_workflows 实际承担了这个角色
- **现象**：`TaskState` 只有 `agent_id`，assignment 的丰富元数据（model、runtime、reason、is_new_agent）存在 orchestrator 的 `_active_workflows` 中；`get_workflow_state()` 读影子状态而非 engine
- **根因**：engine 设计时未规划存储 assignment，orchestrator 自然填补了这个空白
- **代码位置**：`kernel/workflow_state_types.py:39-50`，`daemon/foreman/workflow_orchestrator.py:180-205`
- **改进方案**：扩展 `TaskState` 包含 assignment 元数据；engine 成为 assignment + 状态的唯一权威；删除 `_active_workflows` 影子状态
- **验收标准**：`get_workflow_state()` 只读 engine；orchestrator 无独立状态存储

### ARCH-5 cccc actor add CLI 缺 --worker-prompt（P2）
- **严重度**：Medium — Foreman 无法通过 CLI 创建带专属提示词的持久化 actor
- **现象**：daemon 层 `actor_add_ops.py` 支持 `worker_prompt`，kernel `actors.py` 能存储，system_prompt 会注入，但 CLI `actor_cmds.py` 发送 daemon 请求时未传此字段
- **代码位置**：`cli/actor_cmds.py:92-108`
- **改进方案**：在 CLI `cmd_actor_add` 的 daemon 请求中加入 `worker_prompt` 字段；在 argparse 中暴露 `--worker-prompt` 参数
- **验收标准**：`cccc actor add --runtime claude --worker-prompt "你是后端专家..." backend-worker` 创建的 actor，其 system prompt 包含指定内容

### ARCH-6 assignment_id/actor_run_id 管道中丢失（P2）
- **严重度**：Medium — assignment 身份无法在任务事件链中追溯
- **现象**：`TaskEvent` contract 有 `assignment_id/actor_run_id`，CLI 也携带，但经过 `ralph_ipc_handler.py:871` → `workflow_task_ops.py:109` 后被丢弃；`ralph_service.py` 注释说要校验 assignment validity，实现为空
- **代码位置**：`daemon/ralph_ipc_handler.py:871`，`daemon/ops/workflow_task_ops.py:109`，`daemon/foreman/ralph_service.py:232-243`
- **改进方案**：在 handler 链中传递 assignment_id；在 `apply_task_event()` 中实现 assignment 校验逻辑
- **验收标准**：ledger 中 task_reported_completed 事件包含 assignment_id；非分配 actor 完成任务时产生 verification_warning

### ARCH-7 DEFERRED 状态只在影子状态（P2）
- **严重度**：Low — engine 状态机和 orchestrator 状态表示不一致
- **现象**：`TASK_STATUS_DEFERRED` 是 orchestrator 的字符串常量（`workflow_orchestrator.py:64`），写入 `_active_workflows` 影子状态；`WorkflowTaskStatus` 枚举无此状态
- **代码位置**：`daemon/foreman/workflow_orchestrator.py:556-567`，`kernel/workflow_state_types.py:27-36`
- **改进方案**：将 DEFERRED 加入 `WorkflowTaskStatus` 枚举；`_record_deferred_tasks()` 通过 engine 事件记录

### ARCH-8 retry_after_verification() 不清空 agent_id（P2）
- **严重度**：Low — 重试任务在 engine 中仍显示旧 assignee
- **现象**：`retry_after_verification()` 将 task 状态改回 READY，但 `TaskState.agent_id` 保留旧值
- **代码位置**：`kernel/workflow_state_engine.py:153-161`
- **改进方案**：`retry_after_verification()` 同时清空 `agent_id`，待重新分配后由新 assignment 填充
