# Findings — CCCC 工作流实践教训

> 来源：2026-03-26 ~ 2026-03-29 四天的完整实践
> 过程：问题定位 → 方案讨论(4轮) → 外部审查(3份) → 代码修复(27 Task + Phase 0-6) → 两轮端到端测试
> 参与：Claude (Opus 4.6) + Codex (GPT-5.4) + Gemini + 用户

---

## 一、编译通过不等于功能可用

27 个 Task 全部通过 `py_compile` 和 `tsc --noEmit`。两轮实际测试发现 Ralph 全部功能是死代码——daemon 不初始化、无 MCP 暴露、无事件触发。

**根因**：验证标准是"文件能编译"而非"功能能运行"。

**教训**：验证的最低标准应该是"从入口到出口，这条路径能走通"。

---

## 二、按文件拆任务会产生精致的死代码

27 个 Task 按 write_set 无交集拆分，每个文件内部正确但彼此孤立。没有 Task 负责"在 daemon 启动时创建 RalphService 实例"，也没有 Task 负责"在 MCP 注册 Ralph 工具"。

**根因**：端到端功能需要多文件协作，但按文件拆分的每个 Task 只看自己的范围。集成层不属于任何 Task 的 write_set。

**教训**：并行化的正确单元是"可独立验证的功能切片"——有明确输入输出的黑盒。接入正确输入后得到符合预期的输出才是关键，怎么实现是其次的。按文件拆分会放大 AI 之间的独立性，导致代码彼此孤立。

---

## 三、讨论精细度和验证粗糙度不匹配

4 轮讨论 + 3 份审查产出 21KB 方案文档，聚焦数据模型命名和接口格式。没有人问过"daemon 启动后会发生什么"、"Foreman 的第一个工具调用是什么"。

**教训**：方案讨论应从"描述一次完整的用户场景从头到尾怎么走"开始，而不是从"这个数据结构应该有哪些字段"开始。

---

## 四、让 AI 扮演缺失的组件会掩盖问题

让 Codex 扮演 Ralph 做了很好的任务拆分，但真正的 Ralph 需要 MCP 注册、daemon 初始化、事件触发。模拟和实现有本质区别。

**教训**：如果一个组件不存在，先让它的最小版本真正运行，而不是让另一个 AI 假装它存在。一个能跑的空壳比一个不能跑的完整实现有价值得多。

---

## 五、用户一开始就说了正确答案

用户在讨论初期就提出了三个判断，每个都在后续被验证为正确：

1. **"由 Codex 扮演 Ralph 发现不了 Ralph 本身的问题"** — 最终所有 Ralph 功能确实是死代码
2. **"要把 MCP 转成一般工具，通过提示词和 Ralph 引导"** — 我们在 MCP 框架内打转讨论优化，用户的意图是去掉 MCP
3. **"工作流太笨重，不利于 AI 直接端到端测试"** — 修完 27 个 Task 后才发现这一点

**教训**：当用户基于实际使用经验提出架构级判断时，应作为约束条件纳入方案出发点，而不是当作"一个优化建议"去讨论折中。

---

## 六、验证基础设施应先于功能开发

当前顺序是"先写功能 → 发现没法验证 → 补验证"。应该反过来。Phase 0-6 修复后增加的冒烟测试 (`test_smoke_workflow.py`) 验证了事件流路径正确——这证明了端到端测试的价值。但这个测试来得太晚。

**教训**：先有端到端验证命令（哪怕只覆盖最简单场景），再以"这个命令能通过"为所有开发的验收标准。

---

## 七、代码审查能发现逻辑错误，发现不了集成缺失

Wave 3 联合审查发现了 7 个代码级问题（handler 调用路径错误、权限过宽、状态不同步等）并修复。但没发现 daemon 不初始化 RalphService、MCP 工具层缺失、prompt 注入链路断裂。

**教训**："这段代码对不对"和"这段代码有没有被用到"是两个不同的问题，后者需要运行时验证。

---

## 八、第二轮测试的进步与不足

### 进步（修复确实生效的部分）
- Actor 三层状态正确运作，stop 后不再自动恢复
- Foreman 主动划定文件范围边界（"Do NOT touch packages/client/"）
- Foreman 主动发现集成 bug（ID 类型、API 格式）并在开发中途修正
- 依赖顺序正确：frontend 等 backend scaffold 完成后才开始
- backend-worker 通过实际 curl 做了集成测试

### 不足（修复未生效的部分）
- Ralph 验证闭环未触发——Worker 完成后直接 done，没经过 verifying
- Foreman 未使用新 workflow CLI——仍用 MCP cccc_task
- Worker 间无共享合约机制——类型不一致仍靠 Foreman 人工 spot-check
- Worker 无进度推送——Foreman 靠 sleep/poll

### 规律
修复有效的集中在**数据模型和状态管理**（能被静态检查验证的）。未生效的集中在**运行时集成**（需要端到端场景才能发现的）。

---

## 九、先跑通一条路径，再扩展功能

我们的做法：先做完所有数据模型 → 再并行实现所有功能 → 最后发现接不起来。

正确做法：
1. 先让最简单的路径从头到尾跑通（哪怕硬编码）
2. 在可运行基础上逐步替换为真实实现
3. 每一步都保持端到端可运行

**一个能跑的最小闭环 > 十个不相连的完整模块。**

---

## 总结

| 做法 | 预期效果 | 实际效果 |
|------|---------|---------|
| 4 轮方案讨论 | 方案完善 | 数据模型精细，运行时行为未讨论 |
| 3 份独立审查 | 发现所有问题 | 发现逻辑错误，漏掉集成缺失 |
| 27 Task 按文件并行 | 高效完成 | 每个文件正确但没人负责接线 |
| py_compile + tsc | 验证正确性 | 只验证语法，不等于功能可用 |
| Codex 扮演 Ralph | 弥补缺失 | 掩盖了 Ralph 不存在的问题 |
| 讨论 MCP 优化 | 渐进改善 | 用户的判断是去掉 MCP，不是优化 |

**核心教训：不可运行的代码，无论计划多精细、审查多严格、并行度多高，都只是假进展。真正的进展是系统能做到昨天做不到的事。**

## 十、Prompt 修改有效但不稳定，系统级约束才可靠（Day 5 E2E 验证）

> 来源：2026-03-30 第三轮真实 E2E 测试（test3 项目）

### 测试设计
在 Ralph 独立化 + 9 任务修复计划执行完成后（41 项 pytest 全通过），用真实 daemon + Foreman (Claude) + Worker (Codex) 跑 test3 项目。

### 发现

**Prompt 改动在新 session 生效，在有历史上下文时回退：**
- 第一次（无历史）：Foreman 正确使用 `cccc workflow submit`，ledger 出现 `workflow.task_registered` + `workflow.batch_registered`
- 第二次（有历史）：Foreman 回退到旧模式——`context.sync task.create` + `cccc_message_send` 直接分配 Worker
- Worker 始终使用 `cccc_message_send` + `context.sync task.move done` 报告完成，从未调用 `cccc task complete`

**新发现的断裂点：**
- `auto_process` 默认为 `False`，导致 batch 被注册但永远不进入分配流程（已修复为 `True`）
- 即使 Foreman 走了 workflow submit，orchestrator batch → agent assignment → worker prompt 链条仍有缝隙

### 结论

**外部审查 (gp-4, gpp-4) 的核心判断被验证为正确：**

> "仅靠 prompt 把 AI 引到正确路径是不够的。必须让错误路径在系统层面失效或无法改变状态。"

具体表现为：
1. Prompt 修改是**必要的**（让 AI 知道新路径存在），但**不充分**（无法阻止 AI 使用旧路径）
2. AI 在上下文压力下（历史消息、长对话）会回退到训练数据中更常见的模式
3. 41 个 pytest 全通过 ≠ 真实场景中 AI 会走新路径

### 下一步方向

这验证了架构层面修复的必要性（原标记为"后续方向"，现需提前）：

1. **Completion guardrail** — `cccc_message_send` 发送类完成消息时，系统应拒绝状态推进或自动转换
2. **Canonical backend entry** — 无论 CLI/MCP/消息，任务完成都必须走同一个 `complete_task()` 入口
3. **MCP 降级** — `cccc_task` 的状态变更能力应被限制为只读/委托
