# 发送给外部审查 AI 的提示词

> 用法：把下面 `=====` 之间的内容**整段**复制到外部 AI（无代码库访问权限者，如 ChatGPT/Gemini/DeepSeek/Kimi 等）的对话框。随附 `ralph-加强方案-2026-04-17.md` 作为附件或粘贴到对话里。

=====

你是资深软件架构师和静态分析专家，擅长代码评审和系统设计。我需要你扮演**独立第三方评审者**的角色，评审一份由两个 AI（Claude + Codex）经过 6 轮协同讨论产出的工程加强方案。

## 背景

方案的系统是 CCCC 项目内的 **Ralph**：一个 Python 实现的 **plan 静态验证器 + 调度器**，用来校验 workflow plan.yaml 文件（DAG 任务图 + 验证策略 + 契约声明）。Ralph 生成 ValidationReport，被 Foreman（workflow 编排器）消费后，拼接成 prompt 发给 Worker（Claude/Codex/Gemini 等 LLM）执行任务。

文档 `ralph-加强方案-2026-04-17.md` 包含：
- Ralph 架构与模块布局
- 关键数据模型（Plan / TaskSpec / ValidationReport）
- 关键数据流锚点（file:line 级）— Foreman 怎么用 Ralph 产物，哪些产物被丢掉
- **23 个改进项** 分 7 个 PR（第一阶段 13 项 + 第二阶段 11 项 + 1 个新命令 `ralph audit`）
- **显式拒绝的方向**（含 code-level 理由）
- **风险分析**与我们自己提的**审查问题 14 条**

## 你的任务

请按 **三个维度** 严肃评审，不要做无差别点赞：

### 维度 1 · 方案本身的漏洞与盲区

1. 逐项评审 23 个改进项。对每一项给出：
   - ✅ **ENDORSE**（无异议）
   - ⚠️ **ENDORSE WITH CAVEAT**（同意方向，但设计细节有缺陷）——必须列出具体缺陷
   - ❌ **REJECT**（反对）——必须给出替代方案或明确的业务理由
2. 特别关注 **#1 / #2 / #5 / #7 / #10** 这 5 项（方案中标为最关键）：它们的设计是否真的解决了描述的问题？是否引入新的失败模式？
3. 对第一阶段里 Codex 砍掉的 8 项（H-2/H-3/H-4/H-5/H-7/H-9/H-10/CMP-8），你是否认同全部砍掉？有没有你认为应该救回来的？
4. 对 Codex 拒绝的 4 个方向（ralph init / incremental validate / auto-severity / rule retirement），你是否认同？如果认同，请**强化**他的理由；如果反对，请给出使他的 code-level 论证失效的反例。

### 维度 2 · 他们没想到的新方向

请提出 **5-10 条或以上** 真正新增的改进建议（**不能和方案 23 项重叠**，**也不能和方案"显式拒绝"的方向重叠**，**更不能只是已有规则的变种**）。评分标准：

- 🏆 **Tier 1（"huh, good catch"）**：Claude + Codex 6 轮讨论都漏掉、但一旦说出来对方会立刻认同的盲区
- 🥈 **Tier 2**：有价值但可能只是优先级低
- 🥉 **Tier 3**：方向对但落地困难，值得纪录

每条给出：
- **名字**（issue code 或 feature 名）
- **kind**（新规则 / CLI 能力 / data flow 改动 / observability / 其他）
- **动机**（描述它阻止的具体失败模式 — 不要"code quality"这种空话）
- **落地约束**（你看到的实现难点）
- **Tier**

**禁区**：不要提以下泛泛建议（这些已在讨论中被排除或已覆盖）：
- "加个 LLM 语义评审" — 已在 todo 清单 RA-1 安排
- "加 unit test 覆盖率检查" — 已有 _check_test_coverage_gaps
- "加 CI 集成" — 超出 Ralph 边界
- "加 AST 检查" — Ralph 已有 ast 和 semantic_validator
- "文档化 / 加注释" — 不是工程项
- "加 linter" — Ralph 本身就是 linter

### 维度 3 · 系统级判断

请回答这几个问题：

**A. 边界问题**：Ralph 应该停留在"纯静态 plan 校验器"还是演变为"plan + 历史 + agent"的混合体？方案里的 `ralph audit` 读 ledger、#2 给 worker 注入 issue digest — 这两个改动在朝哪个方向走？是否正确？

**B. LLM 时代的 linter 形态**：传统 linter 给**人**看。Ralph 的下游消费者主要是 **LLM worker**。方案里 #2/#3/#4 都在改 Ralph 输出如何被 LLM 消费。但仍使用传统"error/warning/hint"三级+自由文本 message 的格式。你会建议 Ralph 引入"专为 LLM 设计"的输出格式吗？具体什么样？

**C. 23 项的执行顺序**：PR 分组 α/β1/β2/γ/δ 是否合理？是否有某一项应该延后（或提前）到不同 PR？

**D. 反事实思考**：如果只能做 **5 项**（而不是 23），你会选哪 5？给出排名和简短理由。

**E. 方案之外的系统性风险**：基于你对类似系统的经验，Ralph 在半年后最可能遇到的麻烦是什么？是规则噪音、性能、用户抱怨、还是别的？

## 输出格式要求

结构：
1. **执行摘要**（200 字）：总体评价 + 最关键的 3 个发现
2. **维度 1 · 方案评审**：逐项 ✅/⚠️/❌ + caveat
3. **维度 2 · 新建议**：Tier 1-3 清单，每条一段
4. **维度 3 · 系统级判断**：A-E 逐项作答
5. **反事实选 5**：给出你会做/不做哪 5 项
6. **结论**：一句话 — 这份方案**可以直接执行**/**需要修改**/**需要重新讨论**

语言：中文或英文皆可，但**术语（issue code / 文件路径）保持原文**。

## 关于协作基调

- **不要礼貌性认同**。Claude 和 Codex 讨论了 6 轮互相反驳才收敛，我要的是**第三视角的再反驳**。
- **如果你认为方案本质上是对的，就直接说"本质正确"然后专注维度 2 和 3** — 不要凑数挑刺。
- **不要提"建议用 LLM / 建议加 AI agent"这类模糊方向** — 除非你能指出**具体**的 integration 点。
- **code-level 具体性是最高标准**。你看不到代码，所以要基于文档里给的 file:line 锚点 + 数据流描述来论证。凡是无法锚定到具体机制的建议都降级为 Tier 3。

开始评审。
