## 七、后续改进及对应实例

### RO-70 verification 命令被 runtime 变形（P1，v26 发现）

**优先级**：P1  
**影响维度**：过程  
**预期分数变化**：过程 3→4

**触发实例**：
> v26 T1 plan.yaml 中 import-check 命令为 `cd backend && python -c 'from main import app'`，worker 实际创建的是 package-style import（`from backend.api import ...`）。verification runner 执行 plan 中的命令失败，导致 false negative。

**根因**：plan.yaml 的 verification 命令假设了特定的 import 风格，但 worker 可能用不同的代码组织方式。plan 阶段无法预知 worker 实现细节。

**改进方案**：能力指南建议使用更 resilient 的验证命令（如 `python -c "import importlib; importlib.import_module('...')"` 或仅检查 `pytest` 通过）

**验收标准**：下一轮 verification 命令不因 import 风格差异而失败

### RO-71 completer_mismatch 应更严格处理（P2，v26 发现）

**优先级**：P2  
**影响维度**：过程  
**预期分数变化**：过程 +0.5

**触发实例**：
> v26 T1 由 planner 执行 `task complete`（而非 assigned worker-be），产生 `completer_mismatch` 警告但仍允许通过。

**根因**：force-complete 路径允许任何 actor 完成 task，缺少更严格的审计链

**改进方案**：completer_mismatch 时 verification 应升级为 mandatory（不允许 skip）

**验收标准**：completer_mismatch + verification_skipped 不同时出现

### RO-72 retry 后 worker 类型错配（P2，v26 发现）

**优先级**：P2  
**影响维度**：过程  

**触发实例**：
> v26 T2 (frontend) Gemini stall 后 retry 分配给 worker-be (Codex/backend worker)。功能上 Codex 完成了任务，但 assignment_map 中 worker 类型与 task 类型不匹配。

**根因**：retry 时 assignment_map 使用原始映射或 fallback 到可用 worker，不检查 worker 类型与 task 类型兼容性

**改进方案**：retry 时优先选择类型匹配的 worker；如无匹配，发出 warning

**验收标准**：retry 后 task_started 事件中 worker 类型与 task 类型匹配或有明确 warning
