## 一、结果指标（2/5）

1. **[frontend/src/api/client.ts:49,61] HTTP 方法不匹配 — 前端 PATCH vs 后端 PUT**
   - `updateTask` 发送 `PATCH /api/tasks/{id}`，后端 `tasks.py:56` 只有 `@router.put`

## 七、后续改进及对应实例

### [RO-65] challenge mode Gemini 不可达 graceful degradation

**优先级**：P1
**影响维度**：过程 + 体验
**预期分数变化**：过程 4.5→5, 体验 4→4.5

**触发实例**：
> v24 T2 worker checks (app-import + routes-registered) 全部 passed，但 challenge mode 因 Gemini ECONNRESET 报 failed。Foreman 需要 `cccc task complete T2 --force` 手工干预。
> Foreman 反馈："The auto-upgrade should degrade gracefully — if the challenge agent is unavailable, the task should pass with a warning, not fail entirely."

**根因**：`ralph_service.py` challenge 失败时仅在 payload 含 `degraded:true` 时降级，Gemini CLI 网络错误直接返回 `failed`

**改进方案**：Gemini CLI 网络错误（ECONNRESET/timeout/auth failure）时设置 `degraded=True`，走 `W_CHALLENGE_DEGRADED` warning 路径

**验收标准**：Gemini 不可达时 challenge 降级为 worker-only + warning，不 fail task

### 监察机制增强：跨栈语义一致性拦截

**优先级**：P0（结果指标从 2/5 突破到 4/5 的关键）
**影响维度**：结果
**预期分数变化**：结果 2→4

**触发实例**：
> v24 Codex 审查发现前端 PATCH vs 后端 PUT（v20 W-2 同类问题重现）。当前三道防线（verification checks、challenge agent、integration verification）均未拦截。

**监察机制缺口**：
- verification checks：各栈独立，后端 pytest 用正确 PUT，前端 tsc 不检查 HTTP method
- challenge agent：仅对 critical_flow entrypoint 触发，前端 UI 组件不在其中
- integration verification：T6 只跑 "pytest + npm build"，不含跨栈 HTTP 调用

**改进方案**：
1. challenge agent 触发范围——当 plan 同时含 `*/api/*.ts` + `*/routers/*.py` 时，对 integration task 强制 challenge，prompt 注入"对比 API client fetch method 与 router decorator"
2. capability guide 增加 integration verification 示例——跨栈 HTTP 调用检查命令模板
3. Ralph validate 新规则 `W_CROSS_STACK_NO_INTEGRATION_CHECK`——前后端同在 plan 但 integration task 无跨栈检查时 warning

**验收标准**：下一轮 E2E 中 PATCH vs PUT 类 bug 被上述任一机制拦截
