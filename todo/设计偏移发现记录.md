## 一、发现过程

### 触发点：FIX-14 讨论

v4 实战评估报告中记录了 FIX-14："Batch 1 worker 自动创建"——因为 batch 1 的 worker 需要 Foreman 手工 `cccc actor add`，而 batch 2-3 由引擎自动创建了泛型 worker，评估认为这是缺陷。

用户指出：**Foreman 根据任务需要自主判断并创建合适 worker 本来就是正确行为**，不应该由引擎自动创建泛型 worker。反而引擎自动创建 batch 2-3 的 `claude-general-worker` 才是偏离设计的。

### Codex 第一轮调查（代码层）

通过 Codex 对代码进行调查，发现 5 个设计偏移：

1. **High**：agent pool 的 `create_or_reuse_agent()` 在无匹配时自动创建新 worker，记作 `created_by="foreman"`，混淆了引擎自动行为和 Foreman 显式决策
2. **High**：`_fallback_to_group_actors()` 静默把 rejected batch 改写成 approved，round-robin 塞给现有 peer actor
3. **High**：orchestrator 维护 `_active_workflows` 影子状态，`get_workflow_state()` 读影子而非 engine
4. **Medium**：`verifying` 状态在 engine 是完整状态，但 orchestrator 快照不统计，直接写成 `completed`
5. **Medium**：worker 可跳过 `assigned→running` 转换，orchestrator 静默补 `report_worker_started()`

### Codex 第二轮审查（设计意图层）

对重新表述的设计意图进行对抗式审查，发现 6 个额外技术缺口（详见第四节）。

### Codex 第三轮分析（文档溯源层）

阅读三份核心文档（findings.md、问题清单-full.md、ralph-foreman-workflow.md）还原跑偏时间线：

**关键发现：`ralph-foreman-workflow.md` 本身就是偏移后的文档。**

该文档最后更新于 2026-03-30，彼时 WF-NEW-4 的 fallback 已加入，E-2 模型注册表驱动分配已在计划中。文档描述的是已实现的东西，不是最初的意图。

### Codex 第四轮分析（会话溯源层）

进一步读取 `~/.claude/projects/-Users-vfch-Documents-project-canary-cccc-main-git/*.jsonl` 中 2026-03-29、2026-03-30、2026-04-01 附近的 Claude 会话记录，发现跑偏不是单点失误，而是三次连续决策造成：

1. **2026-03-30（session `cd0f...` / `d2d...`）**：问题被重新定义为"默认路径根本不会到达后端"，明确得出"**最高 ROI 的改动是改 prompt，不是改后端**"。这一步把修复目标收缩为"先让正确路径走通"，没有继续追问"谁拥有 worker 决策权"。
2. **2026-03-31（session `d2d...`）**：WF-NEW-4 被识别为当前 E2E 的上游阻塞点。会话先得出"agent pool 只看 `.cccc/agents/` YAML，不看 group actors；peer 角色得分为 0，阈值过严"，随后直接下发修复：添加 `_fallback_to_group_actors()`，并把 peer 角色纳入评分。成功标准也随之变成"`agent pool rejected → fallback to group actors → batch approved`"。
3. **2026-04-01（session `a114...`）**：能力扩展计划把 E-2 明确写成"**模型能力驱动评分**"，直接增强 `agent_pool.py` 的 `_score_agent_for_task()`。模型注册表从 Foreman 的信息参考进一步变成了调度器内建的自动决策依据。

**关键补充发现**：repo 内 `.claude/` 只有 worktree 和 `.workflow` 产物；真正的会话证据在用户目录下 `~/.claude/projects/...`。因此这次证据链可以同时覆盖：设计文档、代码状态、以及当时做决策的对话上下文。

### 2.2 每次偏移的根因

**WF-NEW-4（最关键的偏移点）**

agent pool 匹配失败时，修复决策是"加 fallback"而不是"向 Foreman 报告匹配失败"。这个修复解决了当时的症状，但把"分配失败应暴露问题"的原则悄悄改成了"系统自动兜底继续跑"。当时这条原则还没有被正式写下来，所以没有人意识到这次修复违反了它。

**ralph-foreman-workflow.md 成为偏移记录**

文档在修复完成后写成，自然描述了已实现的状态。"process_batch_suggestion() → 评估 agent pool → 分配"被写进目标架构，相当于把偏移后的设计背书为"应该的样子"。后续所有人看文档，看到的就是偏移后的架构。

**E-2 加深耦合**

"模型注册表驱动分配"这个能力本意是让 Foreman 知道各模型能力，但在 agent_pool.py 的实现中变成了"基于评分自动分配"。模型信息库和自动决策引擎被混在一个类里，职责边界进一步模糊。

### 2.3 根因归类

| 根因类型 | 具体表现 |
|---------|---------|
| **设计未明确** | "Foreman 负责 worker 决策"从未写进文档；"无合适 agent 应向 Foreman 报告"从未成为系统原则 |
| **明确了但被绕过** | `workflow submit → orchestrator → assign` 路径、`task complete → verify gate` 路径 |
| **修复压力下的局部最优** | WF-NEW-4 加 fallback 解决了当时问题，但没有做架构影响评估 |
| **文档滞后导致偏移固化** | 文档写于修复之后，记录了偏移后的状态并将其背书为设计意图 |

### 2.4 更深一层的根因

上面的归类解释了"为什么会偏"，但还不足以解释"为什么偏得这么自然"。结合会话记录，根因还包括以下几层：

| 深层根因 | 具体表现 |
|---------|---------|
| **负向不变量缺失** | 系统里有很多"应该怎么做"的正向流程，但几乎没有"绝不能自动做什么"的硬约束。没有把"无匹配时不能自动批准"、"orchestrator 不能替 Foreman 生成 assignment"写成测试或接口不变量。 |
| **失败暴露通道缺失** | 当 agent pool 无匹配时，系统缺少顺手的"向 Foreman 发结构化失败消息并等待决定"路径；相比之下，直接 round-robin fallback 到 group actors 更容易实现。结果就是架构对正确行为的支持更弱，对兜底行为的支持更强。 |
| **成功判据偏向‘先跑通’** | 当时被视为成功的信号是 E2E 通过、batch 被 approved、task 不再停在 READY，而不是"决策权仍在 Foreman"、"失败被显式暴露"。在这种判据下，fallback 很容易被误判为修复。 |
| **命名和职责归属有误导性** | `create_or_reuse_agent()`、`created_by="foreman"` 这类设计会把系统代执行和 Foreman 显式决策混淆，降低偏移的可见性。 |
| **实现反向塑造文档** | 03-30 文档重写不是回到原意校准实现，而是总结当前可运行实现。结果文档不再是约束实现的依据，而变成了为实现背书的记录。 |
| **AI 天然偏向最短闭环** | 在意图未形式化、失败路径未设计成一等公民的前提下，AI 会自然朝着"最少报错、最快通过 E2E、最短闭环"的方向收敛。WF-NEW-4 和 E-2 都体现了这种局部最优倾向。 |

## 三、关键认知

**这次更新 ralph-foreman-workflow.md 不是"修正实现偏离了文档"，而是第一次把原始意图正式写进文档。**

原始意图从来没有被正式写下来，导致第一版实现就按最方便的方式做了（orchestrator 自动分配），后来的文档也跟着记录了这个已实现的状态。

更准确地说，真正的根因不是单纯"AI 想错了"，而是：

1. 原始意图只有背景描述，没有接口级、状态机级、错误路径级的硬约束；
2. 修复阶段的成功标准偏向"跑通当前 E2E"；
3. 系统缺少把失败显式抛回 Foreman 的现成通道；
4. 文档在修复后回填，进一步把局部最优方案固化成架构。

因此，跑偏是"设计边界未被形式化 + AI 在修复压力下选择局部最优 + 文档事后背书"三者叠加的结果。

这是 findings.md 教训五的再现：
> "用户一开始就说了正确答案，但被当作背景而不是约束。"

## 五、对 FIX-14 的重新定性

FIX-14"Batch 1 worker 自动创建"基于对设计的误解，应当关闭：
- Foreman 自主创建合适 worker 是**正确行为**，不是缺陷
- 真正的问题是 ARCH-1（submit 无法表达 assignment）和 ARCH-3（re-suggest 绕过 Foreman）
- 引擎为 batch 2-3 自动创建泛型 worker 才是需要修正的异常行为
