#### 结果维度评分：2/5

## 七、后续改进

### FIX-E2E-1 auto-process agent 匹配失败（P0）✅ 已修复

**状态**：已修复（v12-run2 验证通过）
**修复**：orchestrator `process_batch_suggestion()` 增加 group peer actor fallback。当 pool 评估 reject 所有任务时，回退到 group 内 enabled peer actors 做 round-robin 分配。
**验证**：v12-run2 中 3 个 batch 全部 approved，4/4 任务全自动闭环。

### FIX-E2E-2 手工 approve/assign CLI（P1）

**优先级**：P1
**影响维度**：体验
**触发实例**：v12-run1 Foreman 反馈："When auto-process fails, foreman should be able to manually approve and assign tasks via CLI."
**验收标准**：auto-process 失败后，Foreman 能通过 CLI 手工推进任务状态。

### FIX-E2E-5 verification checks 强度不足以拦截设计缺陷（P1）

**优先级**：P1
**影响维度**：结果
**预期分数变化**：结果 2→4

**触发实例**：
> v12 两次运行中，4/4 任务 verification_passed（compile + import/help checks），但 Codex 对抗审查发现 2 个 CRITICAL：并发写入丢数据（storage.py:24）和损坏 JSON 崩溃（storage.py:51）。verify gate 的 checks 无法覆盖这类设计级缺陷。

**根因**：plan.yaml 的 verification.checks 只做了编译和基础功能检查（`py_compile`、`--help`、`import`），不包含边界条件测试。Worker 产出的代码通过了这些浅层检查但仍有 CRITICAL bug。

**改进方案**（三选一或组合）：
1. **Ralph validate 规则增强**：增加 `W_VERIFICATION_MISSING_NEGATIVE_TEST` 规则，当 checks 只有 compile/import 类型时 warn，要求至少一个 behavior test
2. **plan.yaml acceptance_criteria → checks 自动推导**：Ralph 从 acceptance_criteria 文本中推导应有的 negative test（如"持久化"→ 需要损坏恢复测试）
3. **后置对抗审查 gate**：在 verification_passed 后增加可选的 Codex/AI 对抗审查步骤，在 engine 内拦截代码级 CRITICAL

**验收标准**：下一轮 E2E 中，verification 层面能检出或要求覆盖损坏输入和错误路径。

### FIX-E2E-6 Worker 代码健壮性引导（P2）

**优先级**：P2
**影响维度**：结果
**预期分数变化**：结果 +1

**触发实例**：
> v12 两次运行，不同 worker（codex/claude）产出的代码都有相同的两个 CRITICAL：无锁并发写入 + 无损坏 JSON 恢复。说明这不是单个 worker 的问题，而是 task goal_behavior 缺少健壮性要求。

**根因**：plan.yaml 的 goal_behavior 只描述 happy path 功能，没有要求 worker 处理错误恢复和并发安全。

**改进方案**：在 worker prompt 模板中增加标准健壮性要求（错误恢复、原子写入、输入校验），或由 Ralph validate 检查 goal_behavior 是否包含错误处理要求。

**验收标准**：Worker 产出的持久化代码包含 JSON 解析异常处理。
