## 一、用户需求原文

### 1.1 Ralph Agent 层

> 有个比较重大的改进就是我想给 ralph 添加一个 agent 层，无论是之前 ralph 改进方案里反复提到的当前 ralph 架构无法解决语义相关问题，还是 ralph 后续要负责的工作流监督问题，通过单纯的静态条件是很难灵活处理的，所以需要有一个 agent 进行协助处理，在发现 ralph 的不足时，优先做 ralph 的调整，尽量减少 agent 的干预，但 agent 还是要有，以此保证 ralph 的灵活性，同时也让改进更多的落实到 ralph 本身，而不是 agent，这个 agent 可选择是否启用，默认是启用的，选择 gemini cli 的 flash 模型，就用现在项目的持久化 agent 来做

### 1.2 验证与执行分离

> 得把验证和执行分开进行……结果相对固定、可预计的通过 ralph 判断，不可预期、不稳定的交给 agent，这个就由 foreman 在 plan.yaml 里显式说明分配给 ralph 验证还是分配给 agent 验证吧，关于测试输入和测试输出执行 agent 都不知道，只在验证失败后得到反馈要求重试

### 1.3 验证用例要求

> 拿到 Foreman 预设的测试用例跑一遍再判断输出，如果有错误给出反馈，测试用例不能使用静态 pytest，必须是和实际使用时高度相似的模拟输入得到的准确模拟输出，如果有误反馈给 worker，反馈内容就是描述哪里不满足，出现什么问题

### 1.4 Agent 审查范围

> 只看 Ralph 标记为"超出结构校验范围"的部分

### 1.5 "超出范围检查项清单"的性质

> 维护一个"已知超出范围的检查项清单"……静态的，工作流过程中不变

### 1.6 Agent 可信度定位

> 由于模型本身比较轻量，可信度本来就一般，仅作为参考，这个在 agent 的语义描述中要说明，不要完全相信

### 1.7 Agent 误判兜底

> 限制重试 2 次……并且由于模型本身比较轻量，可信度本来就一般，仅作为参考

### 1.8 改进闭环

> 实际是独立进行的，而不是在工作流内进行的，工作流内是固定的，但是在经过一次完整实践后，由 foreman 评估 ralph 的使用问题并写入到 ralph 的后续改进，而改进理念就是做出的改进尽量是对 ralph 做改进

### 1.9 Agent 不读代码

> 先做成不读代码的

### 1.10 改进产出

> 追加到 问题清单-v5-ralph.md

### 1.11 Codex 的角色

> codex 能力够强，作为外部审查，用来发现 ralph+agent 后的结果的不足，在实际工作流中不触发

### 1.12 Foreman 自主判断验证方式

> foreman 自己判断（ralph 验证还是 agent 验证），不需要这么麻烦

### 1.13 独立运行要求

> 由于 ralph 需要在脱离这个项目的情况下也能运行，所以这个 agent 也要可以直接启动而不用别的创建 workflow 所需的前置条件

### 1.14 设计哲学

> ralph 预期成为一个强大的审查监督系统，但承认其不完美与开发的困难，由 agent 作为辅助和过渡工具对 ralph 进行补强，但不能因为 agent 这一本身强大的工具的存在和 ralph 改进的逐渐困难而懈怠了对 ralph 的不断优化改进

### 1.15 任务粒度与模块化

> 单纯以文件拆分不现实，现在的计划是按照独立模块分，每个 agent 负责的都是足够小、便于确认是否正确和验收的任务，将 agent 作为完成任务的黑盒，实现接受输入(任务需求)->agent 执行->输出一个由 agent 完成的模块->模块在给定输入下给出预期输出，然后再把所有模块进行拼接有机结合

### 1.16 并行任务解耦

> 并行任务应该在任务规划阶段就统一输入输出接口规范，然后在并行过程中由于使用模拟输入，所以不必等待依赖项完成再进行

### 1.17 分阶段执行与自动拼接

> 把一开始的分阶段任务按功能分，功能内部模块化并行，每完成阶段性任务就把所有模块自动拼接，这样更加可靠

### 1.18 拼接代码作为并行任务

> 把拼接后的主代码也作为一个并行任务，假设所有模块按照计划的接口提供的前提下编写功能，这个的验收等待本阶段所有任务包括这个主文件都完成后再开始

### 1.19 Worker 求助机制

> 可以求助并由 foreman 委派 codex 处理（直接帮 Worker 写代码解决问题）

### 1.20 用户参与边界

> 除非由于多次重试交由 foreman 处理，foreman 也无法处理并把问题标记为人工处理，否则用户无需参与

### 1.21 Foreman 规划迭代

> 先生成草稿 → Ralph 验证不过 → Foreman 修改 → 再验证

### 1.22 Phase 间串行

> 先严格串行，后续再尝试部分并行

### 1.23 计划一次性生成

> 一开始就和 Phase 1 一起生成好的（所有 Phase 的计划一次性生成）

### 1.24 交付判定

> verify gate 都完成，且进行一次全部都拼接完成后的全流程端到端验证

### 1.25 E2E 验证执行者与时机

> 由 foreman 执行，拼接完成后生成（测试用例）

### 1.26 阶段验证失败处理

> Foreman 自己分析错误信息（定位问题模块），让那个 Worker 修

### 1.27 升级链

> Worker 遇到问题 → 求助 Foreman → Foreman 委派 Codex 处理 → Codex 也搞不定 → 标记人工处理

### 1.28 接口不匹配处理

> 反馈 foreman 处理，不过这个需要由 ralph 进行约束，不应该发生

### 1.29 两阶段拆分（v0.3 新增）

> 做成两阶段：先由 Ralph 进行任务拆分（保留已有的依赖分析、写冲突检测、并行调度能力），AI 得到拆分完的任务后再由 Foreman 进行模块化拆分。阶段按功能分，功能之间的并行和之前的任务拆分是类似的。

## 二、全流程蓝图

### 2.1 全景视图

```
用户 (自由文本, CLI/Web/飞书)
  │
  ▼
CLI AI (对话交互, 需求澄清, 独立角色)
  │  明确需求后转交
  ▼
Foreman AI (唯一决策者)
  │
  ├─① 需求分析与明确
  │
  ├─② 生成 plan.yaml (所有 Task 一次性生成)
  │     - 按功能分 Task，声明依赖关系 (depends_on) 和写范围 (claimed_paths)
  │     - 每个 Task 声明 verification_mode: ralph|agent
  │
  ├─③ 第一阶段拆分：Ralph 任务拆分与并行调度
  │     plan 草稿 → Ralph validate (40+ 结构规则)
  │                → Ralph suggest (依赖分析 + 写冲突检测 + 优先级排序)
  │                → Ralph Agent 审查超出范围项
  │     → 不通过 → Foreman 修改 → 再验证
  │     → 通过 → Ralph 输出可并行的 Task 批次
  │
  ├─④ 第二阶段拆分：Foreman 模块化拆分
  │     每个 Task (或同批次并行 Task):
  │       Foreman 拆为独立 Module
  │       - 统一模块间输入输出接口规范
  │       - 主代码/集成代码作为独立并行 Module
  │
  ├─⑤ 分批次执行 (批次间严格串行)
  │     Batch N (Ralph suggest 算出的一批可并行 Task):
  │       Task T1:
  │         Worker A: 模块 A ─┐
  │         Worker B: 模块 B ─┼─ 模块并行 (模拟 I/O, 不等依赖)
  │         Worker C: 模块 C ─┘
  │         全部完成 → 模块拼接 → Task verify gate
  │       Task T2: (与 T1 并行, 无写冲突)
  │         Worker D: 模块 D ─┐
  │         Worker E: 模块 E ─┘
  │         全部完成 → 模块拼接 → Task verify gate
  │       本批次全部通过 → 批次 E2E 验证
  │         → 通过 → Ralph suggest 算下一批 → 进入 Batch N+1
  │         → 不通过 → Foreman 分析 → 定位模块 → Worker 修
  │
  ├─⑥ 全流程 E2E 验证
  │     所有 Task 完成 → Foreman 生成 E2E 测试用例 → Foreman 执行
  │
  └─⑦ 交付
        所有 verify gate pass + 全流程 E2E pass → 完成
```

### 2.2 角色职责

| 角色 | 职责 | 决策权 |
|------|------|--------|
| **用户** | 提需求；处理人工升级 | 最终决策权 |
| **CLI AI** | 对话交互、需求澄清、调用 CLI 启动工作流 | 无（转交者） |
| **Foreman** | 需求分析、plan 生成、**模块化拆分**、集成拼接、E2E 验证、错误分析 | 工作流内唯一决策者 |
| **Ralph** | 静态规则验证、**任务拆分与并行调度**（依赖分析、写冲突检测、优先级排序）、标记超出范围项 | 无（校验者 + 调度者） |
| **Ralph Agent** | 语义审查超出范围项、执行模拟测试验证 | 无（建议者，仅供参考） |
| **Worker** | 执行模块开发，黑盒：输入(需求) → 输出(模块) | 无（执行者） |
| **Codex** | 帮 Worker 写代码解决问题；外部对抗审查 | 无（辅助者） |
| **Engine** | 状态管理 + 7 条不变量 pre-transition guard | 无（守卫者） |

### 2.3 升级链

```
Worker 遇到问题
  │
  ▼
Foreman 处理
  │  无法解决 → 委派 Codex 直接帮写代码
  │
  ▼
Codex 处理
  │  仍无法解决
  │
  ▼
标记人工处理 → 通知用户
```

### 3.2 运行时验证

```
┌─ 验证阶段 ──────────────────────────────────────┐
│                                                   │
│  Worker 报告完成 → verify gate                    │
│                                                   │
│  根据 plan.yaml 声明的 verification_mode 分流：    │
│                                                   │
│  [ralph 模式] 结果可预期、相对固定                 │
│    → Ralph 静态判断 (exit code 等)                 │
│    → pass/fail                                    │
│                                                   │
│  [agent 模式] 结果不可预期、不稳定                 │
│    → Ralph Agent 执行 Foreman 预设的模拟测试用例    │
│      (贴近真实使用的模拟输入 → 对比预期模拟输出)    │
│    → pass → done                                  │
│    → fail → 反馈 Worker                           │
│      (语义描述：哪里不满足、什么问题)              │
│      (标注"仅供参考，agent 判断可信度有限")        │
│           → Worker 重试 (上限 2 次)                │
│           → 仍 fail → 升级 Foreman 决策            │
│                                                   │
│  关键约束：                                        │
│    - Worker 全程不知道测试输入和预期输出            │
│    - 不用静态 pytest，必须是高仿真模拟输入/输出     │
│    - Agent 不读代码，纯基于输入输出判断             │
└───────────────────────────────────────────────────┘
```

### 3.3 执行阶段不变量

```
Engine pre-transition guard (7 条)：

  INV-1  NO_SILENT_APPROVAL           rejected → approved 必须经 Foreman 显式决策
  INV-2  FOREMAN_OWNS_ASSIGNMENT      每个 assignment 溯源到 Foreman 的 AssignmentRecord
  INV-3  CLEAN_RETRY                  retry 后旧 assignment 必须清理
  INV-4  NO_AUTO_DISPATCH             后续批次就绪时通知 Foreman，不自动分配
  INV-5  ASSIGNMENT_PERSISTED         所有 assignment 在 Engine ledger，无影子状态
  INV-6  NO_IMPLICIT_DECISION         Orchestrator 无未授权的 if-then 自动转换
  INV-7  NO_COMPLETE_WITHOUT_FRESH_SELF_TEST [新]
                                      Worker complete 必须附带当次 attempt 的自测结果
```

### 3.4 Ralph Agent 设计约束

| 约束 | 说明 |
|------|------|
| 模型 | Gemini CLI Flash，轻量级 |
| 生命周期 | 每个 workflow 一个实例；可脱离 workflow 独立启动 |
| 可选性 | 默认启用，可关闭（`--no-agent` 退回纯静态模式） |
| 审查范围 | 只看 Ralph 标记为"超出结构校验范围"的部分 |
| 代码访问 | 不读代码，基于 Ralph 输出 + plan 文本做语义推理 |
| 可信度 | 结果标注为"agent 建议，仅供参考" |
| 决策权 | 无。只能标记 + 转交 Foreman |
| 验证重试 | 上限 2 次，超过升级 Foreman |
| 基础设施 | 复用现有项目持久化 agent 机制，跳过 workflow 前置操作 |

### 3.5 "超出范围检查项清单"

- 静态配置文件，随 Ralph 版本发布
- 工作流过程中不变
- 初始内容来源于 `问题清单-v5-ralph.md` 二、已知局限：
  - RV-15：Ralph 新规则自身的 bug 无法自检
  - RV-18：goal_behavior 中引用的函数名可能不存在
  - RV-19：模型扩展可能破坏已有语义
  - RV-20：monitor wiring 调用位置可行性无法静态验证
  - RO-10n：verification 命令强度无法检测连接级/运行时语义 bug

### 3.6 改进闭环（工作流外）

```
完整实践后：
  Foreman 评估 Ralph 使用问题
       │
       ▼
  追加到 问题清单-v5-ralph.md
       │
  改进理念：
    1. 优先改 Ralph 静态规则
    2. 尝试把 agent 处理的语义问题转为 Ralph 规则
    3. 验证改进有效 → 保留
    4. 目标：持续减少 agent 干预

  Codex 角色：
    外部对抗审查，发现 Ralph+Agent 的不足
    不在工作流内触发

  设计哲学：
    Ralph 预期成为强大的审查监督系统
    承认不完美，agent 作为辅助和过渡
    不因 agent 强大而懈怠 Ralph 改进
```

## 四、两阶段拆分执行模型

### 4.1 两阶段拆分总览

```
┌─────────────────────────────────────────────────────────┐
│ 第一阶段：Ralph 任务拆分（保留已有调度能力）               │
│                                                          │
│ Foreman 的 plan.yaml:                                    │
│   Task T1 (depends_on: [], claimed_paths: [src/auth/])   │
│   Task T2 (depends_on: [], claimed_paths: [src/db/])     │
│   Task T3 (depends_on: [T1, T2], claimed_paths: [src/api/]) │
│   Task T4 (depends_on: [T3], claimed_paths: [src/web/])  │
│                                                          │
│ Ralph suggest() 输出：                                    │
│   Batch 1: [T1, T2]  ← 无依赖、无写冲突、可并行          │
│   Batch 2: [T3]      ← 等 T1+T2 完成                    │
│   Batch 3: [T4]      ← 等 T3 完成                       │
│                                                          │
│ 这就是之前优化的：                                        │
│   _unlock_score() → T1 和 T2 都解锁 T3，优先级高          │
│   _write_sets_conflict() → T1/T2 无写冲突，可以并行       │
│   _dependency_block_reasons() → T3 被 T1+T2 阻塞         │
└─────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────┐
│ 第二阶段：Foreman 模块化拆分                               │
│                                                          │
│ 对 Batch 1 中的 Task T1 (auth 功能)：                     │
│   Module T1-A: 登录逻辑 ─┐                               │
│   Module T1-B: 权限校验 ─┼─ 模块并行 (模拟 I/O)           │
│   Module T1-C: 主集成   ─┘                               │
│   统一接口规范 → 全部完成 → 拼接 → T1 verify gate         │
│                                                          │
│ 对 Batch 1 中的 Task T2 (db 功能)：                       │
│   Module T2-A: schema  ─┐                                │
│   Module T2-B: 迁移    ─┼─ 模块并行 (模拟 I/O)            │
│   Module T2-C: 主集成  ─┘                                │
│   统一接口规范 → 全部完成 → 拼接 → T2 verify gate         │
│                                                          │
│ T1 + T2 都通过 → 批次 E2E → Ralph suggest 下一批          │
└─────────────────────────────────────────────────────────┘
```

### 4.2 批次执行流程

```
Batch N (Ralph suggest 算出的一批可并行 Task)
  │
  ├─ 对每个 Task：Foreman 模块化拆分
  │    - 统一模块间输入输出接口规范
  │    - 主代码/集成代码作为独立并行 Module
  │
  ├─ Task 内模块并行执行：
  │    Worker A: 模块 A (模拟 I/O, 不等依赖)
  │    Worker B: 模块 B (模拟 I/O, 不等依赖)
  │    Worker C: 主代码/集成 (假设接口合规)
  │
  ├─ 模块全部完成 → 拼接 → Task verify gate
  │
  ├─ 本批次所有 Task 通过 → 批次 E2E 验证
  │    → 通过 → Ralph suggest 算下一批 → Batch N+1
  │    → 不通过 → Foreman 分析错误 → 定位模块 → Worker 修复
  │
  └─ 批次间严格串行 (后续可探索部分并行)
```

### 4.3 Worker 黑盒模型

```
每个 Worker 是一个黑盒：

  输入：任务需求 + 接口规范 + 模拟输入数据
    │
    ▼
  Agent 执行（Worker 内部过程对外不可见）
    │
    ▼
  输出：一个完成的模块
    - 模块在给定输入下给出预期输出
    - 模块遵守规划时定义的接口规范

  Worker 不知道：
    - 其他并行 Worker 的存在和进度
    - 自己模块的最终测试用例
    - 拼接后的全局上下文
```

### 4.4 并行解耦机制（两层）

```
第一层：Task 间并行安全（Ralph 负责）
  - Ralph suggest() 通过 claimed_paths 写冲突检测确保并行 Task 不写同一文件
  - 依赖图分析确保同批次 Task 无未满足依赖
  - 这是 Ralph 已有的、经过优化的能力

第二层：Module 间并行安全（Foreman 负责）
  ┌──────────┐     ┌──────────┐     ┌──────────┐
  │ 模块 A    │     │ 模块 B    │     │ 模块 C    │
  │          │     │          │     │          │
  │ 输入接口  │◄───►│ 输入接口  │◄───►│ 输入接口  │
  │ 输出接口  │     │ 输出接口  │     │ 输出接口  │
  └──────────┘     └──────────┘     └──────────┘
        ▲                ▲                ▲
        └────────────────┴────────────────┘
                  统一接口规范

  - 各 Worker 使用模拟输入独立开发，不等待依赖
  - 接口不匹配由 Ralph 在规划阶段约束（不应发生）
  - 万一发生 → 反馈 Foreman 处理
```

### 4.5 全流程 E2E 验证

```
所有 Task 完成（所有批次执行完毕）
  │
  ▼
Foreman 生成全流程 E2E 测试用例 (拼接完成后生成)
  │
  ▼
Foreman 执行 E2E 验证
  │
  ├─ pass → 交付完成
  └─ fail → Foreman 分析 → 定位 → 修复 → 重新验证
```

## 五、Codex 对抗审查结论（2026-04-04）

### 5.1 设计意图强度评级

| 强度 | 设计意图 |
|------|---------|
| STRONG | DI-4 负向不变量优先于正向流程、DI-5 运行时保障先于编译期规则 |
| ADEQUATE | DI-1 Foreman 唯一决策者、DI-3 失败显式暴露、DI-6 验收=不变量满足、DI-8 上下文锚点、DI-9 评估标准对齐 |
| WEAK | DI-2 Daemon 纯执行层、DI-7 Findings 结构化约束、DI-10 子 agent 自验证义务 |

### 5.2 漂移风险排序

| 排名 | 设计意图 | 主要风险 |
|------|---------|---------|
| 1 | DI-2 Daemon 纯执行层 | Orchestrator 未结构性缩为纯状态机，最易被加业务分支 |
| 2 | DI-1 Foreman 唯一决策者 | submit/failure/ready 多协议形态，路径间不一致 |
| 3 | DI-7 Findings 结构化约束 | 问题清单里仍是"可选字段 + warning"，门槛不够硬 |

### 5.3 已识别盲点（Codex 发现，用户确认纳入）

| 编号 | 盲点 | 说明 |
|------|------|------|
| BP-1 | 异步幂等/陈旧响应拒绝缺失 | 迟到的 BatchAssignmentFailed 回复可能污染新 attempt |
| BP-2 | Liveness 只是 gap 不是约束 | Foreman 不回 inbox 时 workflow 无限挂起 |
| BP-3 | 统一 assignment contract 缺失 | submit 路径修好但 failure/ready 路径少传 decision_id |
| BP-4 | 自验证证据真实性 | Worker 可能复用旧结果或跑弱自测骗过 gate |
| BP-5 | 动态 DAG 变更版本治理 | 动态拆分后旧依赖作废/claimed_paths 冲突重算未定义 |

### 5.4 已采纳的调整

| 调整 | 内容 |
|------|------|
| DI-10 前移 | 从 Phase 5 移到 Phase 4 之后（Phase 4.5 或合并） |
| DI-10 改写为负向不变量 | INV-7: NO_COMPLETE_WITHOUT_FRESH_SELF_TEST |
| 5 个盲点全部纳入 | 作为方案的已识别问题，需在后续 Phase 中解决 |
| 验证与执行分离 | 由 agent 独立执行验证，Worker 不知道测试内容 |

## 六、对齐讨论 Q&A 原文

### Q&A-1：Ralph Agent 的核心架构

**Q (Claude)**: 确认核心架构——Ralph 处理不了的上报给 Agent，Agent 发现模式反馈回 Ralph？

**A (用户)**: 核心架构有误。ralph 系统在接收到 plan 后，ralph 进行任务验证拆分，完成后先交给 ralph agent 进行审查，重点关注问题清单 v5 中提到的 ralph 无法解决的语义问题，对于无法解决的语义问题，处理分为两种，解决前通过 agent 进行辅助判断，和 ralph 验证结果一起返回并标注为 agent 建议，在改进过程中尝试把无法解决的问题转为可解决的写入 ralph 并验证，验证更改有效后保留。

### Q&A-2：验证与执行分离

**Q (Claude)**: Worker 完成任务后，self_test 不由 Worker 自己跑，而是由 Ralph（或 Ralph Agent）在独立环境跑？

**A (用户)**: 是的。结果相对固定、可预计的通过 ralph 判断，不可预期、不稳定的交给 agent，这个就由 foreman 在 plan.yaml 里显式说明分配给 ralph 验证还是分配给 agent 验证。关于测试输入和测试输出执行 agent 都不知道，只在验证失败后得到反馈要求重试。

### Q&A-3：Ralph Agent 的触发条件

**Q (Claude)**: Ralph Agent 介入的触发条件是什么？

### Q&A-33：Ralph 任务拆分能力的保留（v0.3 新增）

**A (用户)**: 但是之前 ralph 兼顾规则检查和任务拆分，现在似乎把任务拆分去掉了，但是这个任务拆分也是优化了挺久的了。

**Q (Claude)**: 蓝图按功能分阶段、模块并行的模型确实不需要动态调度，因为 Phase 内所有模块在规划阶段就解耦了。有两条路：A 保留 Ralph suggest 在 Phase 内部动态调度，B 确认废弃但把关键逻辑迁移到 Foreman。

**A (用户)**: 我想保留，但是没有很好的方法。（经 Codex 讨论后提出方案：Ralph 做计划质量审计 + 降级调度安全网）

**A (用户)**: 那还是做成检查阶段能否并行吧，阶段按功能分，功能之间并行和之前的任务拆分是不是比较像。
