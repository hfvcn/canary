## 3. 和 Foreman/Worker 的交互关键点（外部 AI 审查时重点看这里）

### 3.1 PlanContext 冻结模式（#1 的根据）

```python
# src/cccc/daemon/foreman/ralph_service.py:50-65
@dataclass(frozen=True)
class PlanContext:
    plan_path: Path
    plan_source: bytes       # ← 冻在 register 时的 bytes
    plan_digest: str
    registered_at: float
    semantic_provider: Optional[SemanticProvider]
    semantic_failure_reason: Optional[str]

    def runtime_plan(self, engine):
```

**后果**：workflow 运行中作者修改 `plan.yaml`（补 suppress、改 flow、加 task）——Foreman 全程用旧快照。**有显式测试 `tests/test_foreman_workflow.py:1688` 依赖此语义**，所以改成"自动 reread"会破测。

```python
    header_lines = [
        "[Foreman Assignment]",

        f"Title: {task.title}",

    if task.goal_behavior:          header_lines.append(f"\nGoal: {task.goal_behavior}")

    if task.verification and task.verification.command:
        header_lines.append(f"\nVerification Command: {task.verification.command}")
    # …
    sections = ["\n".join(header_lines)]
    if worker_prompt_text:  sections.append(f"Worker Assignment:\n{worker_prompt_text}")    # ← 全量塞

    if ctx is not None and semantic_provider is not None:
```

### 4.3 第二阶段（11 项）— v1 Codex 原创；v2 评审修正后定稿

#### 4.3.1 plan/validation provenance integrity（v2 第 2 波 + 第 8 波）

**#1 `W_REGISTERED_PLAN_STALE` + completion-side digest guard** · warning + hard-block · ~80-140 LOC（评审修正后）
- **锚点**：`ralph_service.py:50-65`、`ralph_service.py:156-173`、`workflow_orchestrator.py:1464-1549`（on_task_completed）、`workflow_orchestrator.py:1614-1628`（_auto_sync_plan_state，**fresh disk load**）、**测试依赖 `tests/test_foreman_workflow.py:1688`**
- **问题**：v1 原始问题 —— Foreman 注册 plan 时 pin bytes，作者中途改 plan.yaml 不会生效
- **v2 追加问题**（四份评审共识）：validate 走冻结 plan，但 `_auto_sync_plan_state()` 另走 `load_plan(plan_path)` 读磁盘写 state。如果磁盘 plan 已改，冻结 plan 的 task_id 会被 filter 静默丢弃，ledger 和 plan.state 会脑裂
- **v2 设计**：
  1. 保留 frozen snapshot 语义（不自动 reread，不破 `tests/test_foreman_workflow.py:1688`）
  2. `validate` 路径 —— 磁盘 plan digest 与冻结 digest 不一致时报 `W_REGISTERED_PLAN_STALE` warning
  3. **completion 边界（新）** —— 在 `on_task_completed` / `_auto_sync_plan_state` 写账本前，比对当前磁盘 plan digest vs 冻结 digest；不一致时默认 **hard block**（evidence 包含 registered/current digest），通过 `--force-stale-complete`（或 CLI 等价选项）显式 override
  4. 同时写入 ledger event `workflow.plan_digest_divergence` 供 audit

**#9 Validation Ledger Schema Parity** · observability · ~60-100 LOC（评审修正后）

#### 4.3.2 prompt path · worker 面（v2 第 3-4 波）

**#10 Prompt Budgeter for Foreman Assignments** · UX/robustness · ~120-200 LOC（评审修正后，**#2/#4 前置**）
- **锚点**：`workflow_orchestrator.py:1176-1235`
- **问题**：`_build_task_prompt` **零 size cap / 零截断策略**
- **v2 设计**（四份评审一致要求）：
  1. 预算单位为 **token**，不是 char
  2. **保底区（mandatory minima，不可截断）**：`Task ID / Title / Goal / Acceptance Criteria / Verification Command / Do-not-ignore issues / Recommended tests / Forbidden Flows`
  3. **优先级**（gpp-8 给出）：`assignment contract > blockers > verification command > recommended tests > condensed semantic focus > raw semantic context > context store`
  4. **降维而非硬截断**（gedt-8 要求）：先 summarize（symbol signature 级），再截断原文；被降维/截断的内容要在 prompt 中显式声明 `[CONTEXT DEGRADED: <section>, <reason>]` 消除 LLM 脑补
  5. **omission manifest**：prompt 末尾或日志中输出本次截断的完整 manifest，供审计
- **预防失败**：#2 加了 digest 后 prompt 继续膨胀；worker 被截断 context 制造幻觉；保底字段被挤掉

**#2 Prompt Task Issue Digest** · UX · ~80-120 LOC（评审修正后）
- **锚点**：`workflow_orchestrator._iter_task_validation_issues()`（已存在，见 `workflow_orchestrator.py:1323-1335`）、`workflow_orchestrator.py:1176-1235`（但没注入 prompt）
- **问题**：orchestrator 知道 Ralph 对每个 task 报了什么 issue，但 worker prompt 没展示
- **v2 inclusion policy**（actionability-first，四份评审共识推翻 v1 的 severity-first）：
  1. 先按 **`action_owner`** 过滤：`worker` 或 `shared` 才进 prompt；`author` 专属（如 CMP-* 结构类）不发给 worker
  2. 再按 **actionability 维度**分配：`1 条 blocking fact + 1 条 execution-risk + 1 条 verification-risk` 的配额式选择（gp-8-h），剩余额度再按 severity + stable ordering
  3. 同类内偏"会改变执行策略"（`S_*`、`W_VERIFICATION_*`、路径交集等）；不放重复 / 整理类 hint

| **Suppress Lease 迁移（v2 新）** | 旧 suppress 没有 `owner/reason/expiry`，一次性强制会破存量 | silent 兼容旧 suppress；仅对**新**声明强制 lease metadata；`W_SUPPRESS_EXPIRED` 先以 hint rollout，observer 后再决定升级 |
| **finding confidence/source 维度（v2 新）** | 升级规则后 #5 / CMP-6 对 provider 降级场景敏感 | confidence 三级 `exact/heuristic/unknown` 写入评审决策；`H_SEMANTIC_COVERAGE_DEGRADED` 在 provider 不可用时显式告知，而非让结果静默变"干净" |
