## 〇、给外部审查者的上下文

> **重要**：本节是为没有代码库访问权限的外部审查者准备的。
> 如果你正在审查第九节的实施规划，请先完整阅读本节，否则你很可能会像上一轮审查者一样——分析看起来很到位，但实际偏离了项目的真实需求和约束。

### 0.1 CCCC 是什么

CCCC（Collaborative Code Coordination Center）是一个 **AI Agent 多人协作中枢**。它不是一个普通的开发工具，而是一个让多个 AI Agent（运行在不同 runtime 上，如 Claude、Codex、Gemini）**作为一个团队协作完成软件工程任务**的系统。

核心概念：
- **Group**：类似 IM 群聊，但具备执行/交付能力。每个 Group 有一个 append-only ledger（事实流）
- **Actor**：Group 中的参与者。第一个启用的 actor 自动成为 **Foreman**（管理者），其余为 **Peer**（执行者）
- **Daemon**：单一后台进程（ccccd），是所有状态写入的唯一权威。管理 actor 生命周期、消息路由、工作流调度
- **Runner**：Actor 的运行方式。PTY（终端，有 shell 访问）或 Headless（纯 API）

架构分层：
```
Ports（入口）: Web UI (React) | CLI | IM Bridge (飞书等) | MCP Server
    ↓
Daemon（守护进程）: IPC Server | Delivery | Automation | Runners
    ↓
Kernel（内核）: Group | Actor | Ledger | Inbox | Permissions
    ↓
Contracts（契约层）: Pydantic 数据模型，版本化
```

### 0.2 Ralph-Foreman-Worker 三层架构

这是 CCCC 的工作流子系统，目标是让 AI 自主完成"需求→拆解→并行执行→验证→交付"全流程：

```
Ralph（观察层）  →  分析依赖、建议并行 batch、执行验证
     ↓ batch suggest
Foreman（控制层）→  评估 Agent Pool、分配任务、追踪进度、决策
     ↓ task assignment
Worker（执行层） →  执行具体编码任务、上报 evidence
     ↑ verification result
Ralph ←————————  验证 Worker 产出是否符合预期
```

### 0.3 当前代码的真实状态（这是最关键的部分）

**上一轮修复（27 个 Task, +2381/-450 行）之后，代码的实际状态是：**

| 组件 | 代码状态 | 运行时状态 |
|------|---------|-----------|
| `RalphService` 类 | 存在（~420 行） | **死代码** — daemon 启动不创建实例，核心方法零调用者 |
| `WorkflowOrchestrator` | 存在（~950 行） | 被动 — 仅在收到 HTTP 请求时懒创建，无主动行为 |
| `AgentPoolManager` | 存在 | 未被使用 — 因为没有 batch 触发分配流程 |
| `ProgressReporter` | 存在 | 未产出 — 因为没有事件流入 |
| HTTP 路由 | 存在且可用 | **唯一活路径** — 但 handler 内部接线错误 |
| MCP Ralph 工具 | **不存在** | Foreman 无法通过 MCP 访问 Ralph 操作 |
| 飞书卡片模板 | 存在 | 未发送 — 因为 ProgressReporter 没有事件 |
| Capability YAML | 存在 | **未接入** — delivery 链路不调用 capability prompt builder |
| 独立 `ralph/` 包 | 存在（validator/scheduler/ipc） | 未被主仓使用 |

**关键接线错误：**
- `ralph_ipc_handler.py:723` 调用 `orchestrator.ralph.apply_task_event(event)` — 只更新 Ralph 内部状态
- 应该调用 `orchestrator.apply_task_event(event)` — 这才会触发 `on_task_completed`、飞书通知、batch 推进
- 这意味着即使手动触发了事件，闭环也是断的

**状态管理三处各写各的：**
1. `RalphService._task_statuses` — Ralph 自己的内存字典
2. `WorkflowOrchestrator._active_workflows` — orchestrator 自己的内存字典
3. `Context/cccc_task` — 独立的持久化任务系统（用不同的状态枚举）

**提示词系统两套不相通：**
1. `render_system_prompt()`（kernel/system_prompt.py）— 运行时实际使用，硬编码拼装
2. Capability YAML prompt builder（capability_ops/_prompt_builder.py）— 从 YAML 加载 fragments，但 delivery 不调用它

### 0.4 上一轮失败的根因（findings.md 摘要）

上一轮 4 波修复、27 个 Task、3 份独立审查的核心失败模式：

1. **验证标准太低**：所有 Task 只要求 `py_compile` / `tsc --noEmit` 通过。结果：2381 行代码全部编译正确，但 Ralph 全部功能是死代码
2. **按文件拆分任务**：按 "write_set 不重叠" 拆分并行。结果：每个文件内部正确，但没人负责"在 daemon 启动时创建 RalphService 实例"这种跨文件集成
3. **讨论精细度 vs 验证粗糙度不匹配**：讨论了 `hold_reason` vs `admin_hold` 命名，但没人问"daemon 启动后会发生什么"
4. **让 AI 扮演缺失组件**：让 Codex 扮演 Ralph 做任务拆分，掩盖了 Ralph 本身不存在的问题
5. **忽略用户核心判断**：用户从一开始说"去掉 MCP"，但团队花了大量时间讨论"MCP 应该保留哪些职责"

**核心教训：不可运行的代码，无论计划多精细、审查多严格，都只是假进展。**

### 0.5 项目负责人的核心意图

以下不是"优化建议"，而是**必须遵守的约束条件**（上一轮就是把这些当建议处理的，导致偏离）：

1. **验证 = 端到端真实运行，不是单元测试**
   - 验证场景是：给 Foreman 一个真实提示词，让它自主选择并实现一个前后端项目，观察整个工作流是否自主跑通
   - 不是 pytest mock 出一个 orchestrator 然后验证方法返回值

2. **MCP 是被替代的对象，不是优化的对象**
   - 核心路径走 HTTP API + CLI 命令
   - MCP 可以保留给需要的 runtime，但不是必需路径
   - Worker 的完成信号不依赖 MCP 通信的可靠性

3. **并行单元是"可独立验证的功能切片"，不是文件**
   - 切片有预期输入和预期输出，在规划阶段就约定好
   - 即使依赖任务未完成，也可以通过 mock 数据预验证
   - 两个切片只有在没有运行时交互时才能并行

4. **先跑通再扩展，不要在不可验证的状态下堆代码**
   - 上一轮的教训：先设计完所有数据模型 → 并行实现所有功能 → 最后发现接不起来
   - 正确做法：先让最简单的路径端到端跑通 → 在可运行的基础上逐步替换

5. **Worker 报完成不等于完成**
   - Worker 上报 "completed" 只是观察事件，必须经过 Ralph 验证（执行验证命令 + 核对预期输出）
   - 验证失败由 Foreman 决策（重试/标记失败/人工介入），不是自动重试

### 0.6 审查时应该关注什么

基于上一轮的失败模式，请重点审查：

**必须关注：**
- 每个 Phase 完成后，是否有**可运行的验证**（不是编译检查）
- 改动清单是否覆盖了**所有需要接线的位置**（不只是改一个文件的逻辑）
- Phase 之间的依赖是否正确，是否存在"Phase N 需要 Phase M 的产出但没声明依赖"
- 统一状态层是否真的能消除三处各写各的问题（而不是变成第四处写入点）
- 验证门控（verifying 状态）是否在所有路径上都被执行（不只是 happy path）

**容易犯的错误（上一轮的教训）：**
- ❌ 建议"先把数据模型设计完美再动手" — 上一轮就是这么失败的
- ❌ 建议"加更多抽象层/接口/适配器" — 最小改动优先，抽象后续再加
- ❌ 建议"用 mock 替代真实 daemon 做测试" — 负责人明确要求端到端真实运行
- ❌ 讨论命名/接口风格/设计模式但不讨论"这段代码会不会被执行到"
- ❌ 把 MCP 当作需要优化的核心路径（它是被替代的）

**有价值的审查方向：**
- ✅ Phase 0 统一状态层的接口设计是否足够支撑后续 Phase
- ✅ 验证逻辑（Phase 2）是否覆盖了 verification_command 执行失败、超时、expected_output 格式不匹配等边界情况
- ✅ Capability prompt 接线（Phase 3）的兼容性风险是否被充分处理
- ✅ 实施顺序是否最优，是否有可以进一步并行的 Phase
- ✅ 端到端验证场景（Phase 7）的成功标准是否可判定

## 一、Ralph 观察层断裂（根因级）

### R-1 MCP 工具层完全缺失
- **严重度**：Critical
- **现象**：Foreman 无法通过 MCP 访问任何 Ralph 操作（`ralph_batch_suggest`, `ralph_workflow_progress` 等）
- **根因**：`ports/mcp/handlers/` 中没有任何 Ralph 相关工具定义；Ralph 操作仅存在于 HTTP API（`ports/web/routes/workflow.py`）和 Daemon IPC 内部
- **验证**：`grep -r "ralph" src/cccc/ports/mcp/` → 零结果
- **影响**：Foreman 被迫退化为手动编排模式 — 自己分析依赖、决定 batch、创建 actor、发送 prompt
- **建议**：创建 MCP 工具 `cccc_workflow`，桥接 `ralph_batch_suggest`, `ralph_workflow_progress`, `ralph_task_event` 到 Foreman 可用的工具集

### R-2 无主动观察进程
- **严重度**：Critical
- **现象**：Ralph 不会自动监控 Git 提交或任务状态变更来触发 batch 建议
- **根因**：
  - 工作流文档描述 Ralph 为"外部 Python 守护进程"，但实际实现（`ralph_service.py`）是被动库类（docstring: "Not an external process; runs inside the daemon"）
  - `daemon/server.py` 中零次提及 Ralph — daemon 启动不创建 Ralph 实例
  - `suggest_ready_batch()` 存在但没有任何自动调用者（无 timer/cron/event loop/git hook）
  - `get_snapshot()` 显式返回 `"ralph_service_not_wired"` — 代码自身承认未接线
- **影响**：所有 batch 调度、依赖分析、冲突检测功能都成为死代码
- **建议**：在 daemon 启动时初始化 RalphService；添加事件驱动触发 — 当 `cccc_task` 状态变更时自动调用 `suggest_ready_batch()`

### R-3 Foreman Prompt 与可用能力不匹配
- **严重度**：High
- **现象**：Foreman 被指示执行它没有工具完成的操作
- **根因**：`task_management.yaml:37` 告诉 Foreman "审阅 Ralph 的 ready/pending workflow，并决定 approve / modify / defer / reject"，但 Foreman 的 MCP 工具集中没有任何 Ralph 相关工具
- **影响**：Foreman 的 system prompt 包含无法执行的指令，增加了 LLM 的困惑度
- **建议**：要么添加对应的 MCP 工具（推荐），要么在 Ralph 未接线时从 prompt 中移除这些指令

### R-4 task_management.yaml 未进入 Prompt 注入链路
- **严重度**：High
- **来源**：codex-backend-1 深度分析
- **现象**：`task_management.yaml` 中的 Foreman 职责描述（包括 Ralph 审阅指令）实际上可能未被注入到 Foreman 的 system prompt 中
- **根因**：
  - 实际 prompt 注入路径是 `delivery.inject_system_prompt` → `render_system_prompt()`（`kernel/system_prompt.py:92-254`）
  - `render_system_prompt()` 本身不读取 capability YAML 文件
  - capability prompt builder 存在于另一个体系中（`daemon/ops/capability_ops/_prompt_builder.py`），但未找到 `task_management` 被该链路调用的证据
- **影响**：即使修复了 R-1/R-3 的工具问题，如果 capability YAML 不在注入链路上，Foreman 仍然看不到相关指令
- **建议**：确认 capability prompt fragment 的注入链路，确保 `task_management.yaml` 的 foreman 段落被正确注入

### R-5 事件回流链绕过 Orchestrator（闭环断裂）
- **严重度**：High
- **来源**：codex-backend-1 深度分析
- **现象**：即使 task_event 被提交，Orchestrator 的内部状态也不会正确更新
- **根因**：
  - `ralph_ipc_handler.py:723-724` 中 `handle_ralph_task_event()` 直接调用 `orchestrator.ralph.apply_task_event(event)`
  - 这只更新了 `RalphService._task_statuses`
  - 绕过了 `WorkflowOrchestrator.apply_task_event()` 中的 `on_task_completed/on_task_failed` 分支（`workflow_orchestrator.py:830-848`）
  - 因此 ProgressReporter 不会收到完成/失败通知，飞书卡片不会发送，batch 完成检查不会触发
- **影响**：即使外部硬触发了 Ralph 链路的一部分，事件闭环也是断的 — worker 完成不会推进工作流状态
- **建议**：`handle_ralph_task_event()` 应调用 `orchestrator.apply_task_event(event)` 而非 `orchestrator.ralph.apply_task_event(event)`

### R-6 架构双轨漂移
- **严重度**：Medium
- **来源**：codex-backend-1 深度分析
- **现象**：Ralph 存在两套未统一的架构设计
- **根因**：
  - 文档/IPC 客户端将 Ralph 设定为"外部 Python 守护进程经 IPC 推送 batch"（`ralph/ralph/ipc/client.py`）
  - 新代码将 Ralph 改为"daemon 内部服务"（`ralph_service.py` docstring: "Not an external process"）
  - 两边各做了一半：外部接口壳在，内部 service 壳也在，但没有一个默认激活的主动 driver
  - `auto_process` 在 Web route 中默认为 `False`（`workflow.py:31`），需要外部显式触发
- **影响**：开发者无法确定 Ralph 的正确使用方式 — 是应该启动外部进程，还是通过 API 触发内部服务？
- **建议**：统一为一种架构并完整实现。推荐内部服务模式（更简单），但需要补全事件驱动 + MCP 工具 + 自动初始化

## 二、工具与权限系统问题

### T-1 cccc_task assignee 权限系统缺陷
- **严重度**：High
- **现象**：Foreman 通过 `cccc_task(action=update, assignee="codex-backend-1")` 分配任务时被拒
- **错误信息**：`"Permission denied: peer cannot reassign task to codex-backend-1"`
- **根因**：权限检查将 Foreman 错误识别为 "peer"，导致 assignee 更新被拒
- **影响**：Foreman 的核心职责（任务分配）无法通过正式 API 完成，只能在 notes 字段手写分配信息
- **建议**：Foreman 角色应始终拥有任务分配权限；检查 `cccc_task` 中的角色识别逻辑

### T-2 cccc_message_send priority 枚举不一致
- **严重度**：Medium
- **现象**：Foreman 发送 `priority="high"` 消息时失败
- **错误信息**：`"priority must be 'normal' or 'attention'"`
- **根因**：MCP 工具 schema 声明 priority 可选值为 `["low", "normal", "high", "urgent"]`，但实际 API 仅接受 `"normal"` 或 `"attention"`
- **影响**：首次使用 priority 参数时必定失败，浪费一轮调用
- **建议**：统一 MCP schema 定义与实际 API 接受的枚举值

## 三、多 Agent 并行执行问题

### P-1 并行 Worker 文件冲突无保护
- **严重度**：High
- **现象**：codex-backend-1 和 gemini-frontend-1 同时修改 `api.ts`, `types/index.ts`, `useBookmarks.ts`，最后写入者覆盖前者
- **根因**：
  - 无文件级锁定或冲突检测机制
  - Worker 任务分配时未声明 `claimed_paths`（文件所有权）
  - Ralph 的 `detect_write_set_conflicts()` 存在但从未被调用（参见 R-1, R-2）
- **影响**：gemini 的完整版 api.ts 被自身的简化版覆盖（可能为了通过 build）；codex 的 integration fix 又覆盖了 gemini 的版本。可能丢失工作。
- **建议**：
  1. 短期：Foreman 在任务分配时明确声明每个 Worker 的可修改文件范围
  2. 中期：激活 Ralph 的 `claimed_paths` + `detect_write_set_conflicts()` 机制
  3. 长期：考虑 git branch 隔离（RalphService 已有 `create_worktree()` 但从未使用）

### P-2 前后端 API 契约缺失
- **严重度**：High
- **现象**：后端 `/api/bookmarks?search=...` vs 前端 `/bookmarks/search?q=...`；后端 `tags: string[]` vs 前端 `tags: Tag[]`
- **根因**：并行开发前后端时没有共享的 API 契约文档。两个 Worker 独立设计了不同的接口。
- **影响**：集成阶段需要额外的修复轮次（本项目用了 2 轮 codex fix）
- **建议**：
  1. Foreman 在分配并行前后端任务前，先生成并共享 API Schema（如 OpenAPI spec 或简化的接口文档）
  2. 可考虑在工作流中增加 "Contract Phase" 步骤
- **注**：此问题超出 Ralph 的设计范围，需要额外的 contract-first 工作流机制

## 四、Worker 行为控制问题

### W-1 Worker MCP 通信不可靠（Runtime 差异）
- **严重度**：High
- **现象**：
  - gemini-frontend-1：最终通过 `cccc_message_send` 回报，但有显著延迟
  - codex-backend-1：多数情况下不通过 MCP 回报（仅有 1 次主动报告），但确实执行了任务
- **根因**：
  - Worker 通过 system prompt 注入获取任务内容（消息被注入上下文），而非主动读取 MCP inbox
  - 不同 runtime 对 MCP 工具的支持和使用倾向不同
  - Worker prompt 中 `cccc_message_send` 回报是建议性的，非强制性的
- **影响**：Foreman 无法依赖 inbox 轮询跟踪进度，必须主动检查文件系统来判断工作状态
- **建议**：
  1. Worker system prompt 应强制要求完成后通过 MCP 回报
  2. 提供可靠的 "worker done" 信号机制（如通过 `cccc_task` 状态变更触发）
  3. 区分 "delivered to runtime context" vs "read via MCP inbox"

### W-2 Worker 超范围执行（Scope Creep）
- **严重度**：Medium
- **现象**：
  - codex-backend-1 被分配 T004（DB schema），实际完成了 T004-T008（整个 Phase 1，5 个任务）
  - gemini-frontend-1 被分配 T009（scaffold），额外完成了 types + api + hooks
- **根因**：Worker contract 说"只执行分配范围"但无强制机制。LLM 倾向于"多做一些"以求完整性。
- **影响**：
  - 正面：加速交付（Phase 1 一次搞定）
  - 负面：Foreman 失去细粒度控制；超范围产出可能与其他 Worker 冲突（本项目中确实发生了）
- **建议**：在 Worker prompt 或任务分配中明确区分 `scope_policy: strict | flexible`

### W-3 Worker 偏离技术规格未上报
- **严重度**：Medium
- **现象**：规格要求 SQLAlchemy 2.x，codex 选择了 aiosqlite（更轻量但不符合规格），未向 Foreman 上报
- **根因**：Worker prompt 未要求在偏离规格时必须先向 Foreman 申请确认
- **影响**：如果规格有强制性（如团队技术标准），会导致返工
- **建议**：Worker prompt 增加规则：偏离技术规格时必须先通过 `cccc_message_send` 向 Foreman 报告并获得确认

### W-4 unread_count 指标误导
- **严重度**：Low
- **现象**：codex-backend-1 持续显示 `unread_count > 0`，但实际已执行任务
- **根因**：消息通过 system prompt 注入传递到 runtime 上下文，不通过 MCP inbox 的 `mark_read` 机制
- **影响**：Foreman 无法通过 `unread_count` 判断 Worker 是否已接收任务
- **建议**：区分 "delivered to runtime context"（已投递） vs "read via MCP inbox"（已读取）两种状态

## 七、观点与后续计划

### 核心观点

**一味追求静态测试（py_compile, pytest, tsc）不能发现项目实际运行时的问题。**

本轮修复的 27 个 Task 全部通过了 py_compile 和 tsc 验证，但实际运行测试暴露出：
- Ralph 全部功能是死代码（daemon 不初始化、无 MCP 工具、无事件触发）
- 事件回流路径写错（handler 调了 ralph 而非 orchestrator）
- 权限修复改错了代码路径（permissions.py vs context_ops）

**这些问题不可能被静态测试捕获。** 代码语法完全正确，类型完全一致，但端到端流程是断的。

### Ralph 验证闭环的设计初衷

Ralph 的核心理念不是跑 `pytest`，而是：
1. **贴近实际场景的验收** — 不是"函数返回值对不对"，而是"daemon 启动后 API 能响应、前端能渲染、Foreman 能调用工具"
2. **验收不通过则重试** — Ralph 检测到 VerificationResult=failed，自动触发 Worker 重做，直到通过
3. **验收标准应该是可执行的命令** — 不是人在页面观察，而是脚本能自动判定

### 工作流过于笨重的问题

当前工作流必须由人在页面操作才能测试端到端流程。这导致：
- AI 改完代码后只能做静态验证，无法自验
- 每次验证都需要人手动启动 daemon → 创建 group → 添加 actor → 观察结果
- AI 和人之间形成了"写代码 → 编译通过 → 人去测 → 发现不工作 → 再写代码"的低效循环

**应该设计成 AI 可通过命令直接完成整个工作流的运转和验证：**
```bash
# AI 应该能做到
cccc test-workflow --scenario "batch-suggest-and-complete"
# 而不是需要人在浏览器上一步步操作
```

### 去掉 MCP，回归直接工具调用

MCP 从一开始就是计划去掉的，不是优化的对象。目标架构：
- AI 通过 CLI 命令或 HTTP API 直接调用工具，不经 MCP 协议
- 提示词引导 AI 按正确顺序和方式使用工具
- Ralph 验证闭环作为最后一道保障 — 验收不通过则重试
- 不同 runtime (Claude/Codex/Gemini) 都走相同的 CLI/HTTP 路径，消除 runtime 差异

实际测试已经证明 MCP 的问题：每次全量加载开销大、codex 几乎不主动用 MCP 回报、MCP 作为唯一集成协议过于脆弱。

### 任务并行化必须重新设计

按文件拆分并行已被证明不可行。本轮 27 个 Task 按 write_set 无交集拆分，结果是每个文件内部正确但彼此孤立，没人负责接线。

**正确的并行单元是"可独立验证的功能切片"**，不是文件：
- 一个切片可能跨 5+ 个文件，但它是一个不可分割的端到端功能
- 切片有明确的输入和输出，是一个黑盒 — 怎么实现是其次的，接入正确输入后得到符合预期的输出才是关键
- 两个切片如果没有运行时交互，才能真正并行
- 每个切片完成后必须通过运行时验证（不是 py_compile），证明"给定输入 X，系统输出 Y"

并行任务的 AI 之间天然是相对独立的，按文件拆分会放大这种独立性，导致代码彼此孤立。把子任务定义为有明确输入输出的黑盒，才能确保并行产出能被集成 — 因为验收标准不是"文件改了"而是"接口行为正确"。

### 验证基础设施应先于功能开发

当前的顺序是"先写功能 → 发现没法验证 → 补验证"。应该反过来：先有一个能跑的端到端验证命令（哪怕只验证最简单的场景），然后所有功能开发都以"这个命令能通过"为验收标准。这个验证命令本身就是 Ralph 验证闭环的第一个用户。

### 每个设计文档必须附带可执行的验证场景

`ralph-foreman-workflow.md` 描述了 8 个 Phase 的生命周期，但没有一个可执行的验证步骤。后续重新规划时，每个设计文档都应该在末尾附上"验证场景"：用什么命令、期望什么输出、怎么判断通过/失败。写不出验证场景的设计还不够具体。

### 8.2 统一状态枚举（D-5 细化）

合并 Context 系统 (`planned/active/done/archived`) 和 workflow 系统 (`pending/running/completed/failed/blocked`)：

```
planned     — 任务已规划，尚未就绪
ready       — 依赖满足，可被分配
assigned    — 已分配给 Worker，等待启动
running     — Worker 正在执行
verifying   — Worker 报完成，等待 Ralph 验证（关键新增状态）
completed   — Ralph 验证通过，任务完成
failed      — 执行失败或验证失败且不可自动重试
blocked     — 需要人工/外部介入
archived    — 已归档（长期管理用）
```

**流转规则：**
```
planned → ready          # Ralph batch suggest 发现依赖满足
ready → assigned         # Foreman 批准并绑定 Worker
assigned → running       # Actor 实际启动
running → verifying      # Worker 上报 completed evidence
verifying → completed    # Ralph 验证通过
verifying → failed       # 验证失败 + Foreman 决定不重试
verifying → ready        # 验证失败 + Foreman 决定重试
running → failed         # Worker 上报执行失败
any → blocked            # 需要人工介入
completed → archived     # 长期归档
```

**关键约束：** 只有 `completed` 状态才能解锁后继任务的依赖。`verifying` 不能解锁。

### 8.3 功能切片 Schema（D-10 细化）

扩展现有 `TaskRef`（`contracts/v1/ralph_ipc.py:51-59`），不新建模型：

```python
class TaskRef(BaseModel):

    title: str = ""
    type: Literal["frontend", "backend", "general"] = "general"
    depends_on: List[str] = []
    claimed_paths: List[str] = []

    acceptance_criteria: str = ""     # 验收标准（怎么判断做完了）
```

**核心设计原则（负责人强调）：**
- 在任务规划阶段就约定好每个子任务的预期输入和预期输出
- 即使依赖任务还没完成，也可以通过预先约定好的数据结构对数据进行模拟并进行预先验证
- `verification_command` 负责"怎么跑"，`expected_input/output` 负责"拿什么数据跑、预期看到什么"

```python
def verify_completion(self, task_id: str, changed_files: List[str], task_ref: TaskRef) -> VerificationResult:
    checks = []

    # Step 1: Build — py_compile changed .py files
    py_files = [f for f in changed_files if f.endswith('.py')]
    if py_files:
        result = run_command(f"python -m py_compile {shlex.join(py_files)}", timeout=30)
        checks.append({"name": "build", "passed": result.exit_code == 0, "stderr": result.stderr})

    # Step 2: verification_command — 退出码判定（核心验证）
    if task_ref.verification_command:
        result = run_command(task_ref.verification_command, timeout=120)
        checks.append({"name": "verification", "passed": result.exit_code == 0, "stderr": result.stderr})

    # expected_output 不做运行时精确匹配，定位为契约文档 + mock 数据源
    overall = "passed" if all(c["passed"] for c in checks) else "failed"
    return VerificationResult(overall_outcome=overall, checks=checks, ...)
```
