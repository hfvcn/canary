这是一份工程深度极高、复盘极其深刻的上下文。你总结的“按文件拆分会导致精致的死代码”和“编译通过不等于功能可用”切中了多智能体协作编程的最核心痛点。

Ralph 目前在“图结构拓扑”上做到了极致，但由于缺乏“代码视力”，导致校验有盲区；而基于 LSP 的 Serena 拥有确定性的代码视力。两者的结合是系统走向真正可用的关键拐点。

基于“先跑通一条路径、保持架构纯洁性”的原则，我对你提出的 6 个讨论点给出以下落地方案设计：

---

### 1. 集成架构：依赖注入（Dependency Injection）与双态模式

**核心冲突**：Ralph 是无状态、纯计算、毫秒级的纯函数 CLI；而 Serena 依赖 LSP（如 pyright），有几秒的冷启动开销，且需要维护工作区状态。如果直接在 Ralph 核心硬编码拉起 Serena，会破坏 Ralph 的优雅设计。

**推荐方案：抽象适配器 + 环境隔离**

1. **协议层分离**：在 Ralph 内部定义一个纯粹的接口协议（如 `SemanticProvider`），仅包含 `check_symbol_exists`, `get_references` 等纯查询方法。Ralph 依然是纯计算函数，只依赖此协议。
2. **MVP 阶段（CLI 按需模式）**：
   引入 `--semantic` 标志。当执行 `ralph validate plan.yaml --semantic` 时，**CLI 的入口层（而非核心层）**负责启动 `SerenaAgent`，付出 3-5 秒的启动代价，将其包装为 `SemanticProvider` 注入给 `validate` 函数。执行完毕后 CLI 负责销毁 LSP 进程。对于动辄几十秒大模型生成的 Foreman 来说，增加几秒校验时间完全可以接受。
3. **终态阶段（Daemon 托管模式）**：
   在未来的任务调度阶段，由现有的 Orchestrator/Daemon 在后台长驻一个复用的 Serena 实例。当 Orchestrator 频繁调用 `ralph.suggest()` 时，直接传入该实例的引用，实现毫秒级的调度。

---

### 2. 能力优先级：MVP 聚焦“防御死代码”

千万不要试图一次性实现 7 个能力。应严格按照“拦截破坏性缺陷 > 优化调度并行度 > 锦上添花”来排序。

**P0（MVP 绝对核心）：强制闭环，解决“死代码”与“假进展”**
* **能力 1：符号存在性验证**。这是成本最低的试金石（解决 RV-18 局限）。如果计划声称要修改 `auth.login`，Serena 一查没有，立刻打回。
* **能力 3：跨文件原子性检查（最核心杀手锏）**。直接终结“精致的死代码”。机制如下：
  如果任务 A 修改了某接口的**签名**，Serena 查出该接口有 15 处调用。Ralph 将强制校验：这 15 处调用所在的文件，**是否全部被当前任务或其下游依赖任务的 `claimed_paths` 所覆盖？** 如果漏掉任何一个，必定导致编译或运行报错，此时直接抛出 Error，逼迫 Foreman 补全“接线”任务。

**P1（后续迭代）：安全调度**
* **能力 2：符号级冲突检测**。在 `suggest` 中，打破单纯的文件路径锁。如果两个任务改了不同文件，但在引用树上交汇于同一个核心接口（导致隐式冲突），将其标记为 `deferred`。
* **能力 5：死代码下线验证**。验收阶段确认被删除代码的引用计数归零。

**P2（暂缓）：启发式增强**
* **能力 4、6、7**（依赖推断、权重评分、验证范围优化）容易受到 Python 动态性的干扰产生噪音，建议在核心防线稳固后再探索。

---

### 3. plan.yaml 扩展：引入结构化的“语义契约”

**必须扩展**。如果依靠 Ralph/Serena 去用自然语言从 `goal_behavior` 里“猜”符号，违背了 Ralph 的确定性初衷。必须通过字段契约向规划者（Foreman）施压。

**推荐设计：引入带 `action` 的可选字段**

```yaml
tasks:
  - id: "T1"
    claimed_paths: ["src/auth/handler.py"]
    symbol_changes:                      # 新增的可选字段
      - symbol: "src.auth.handler.login" # 绝对路径或相对路径
        action: "modify_signature"       # 关键枚举：create | delete | modify_signature | modify_body
```

**为什么 `action` 的区分是灵魂所在？**
* 如果 `action: modify_body`：表示只修改内部实现。Ralph 仅校验符号存在性，**不触发**沉重的调用链检查。
* 如果 `action: modify_signature` 或 `delete`：表示结构破坏性修改。Ralph **强制触发**能力 3，找出所有 References 并严格核对 `claimed_paths` 覆盖面。
* **向后兼容**：不填该字段，Ralph 平滑退化为纯文本结构校验。

---

### 4. 确定性边界：如何驾驭 Python 的高动态性？

Python 的 duck typing、`getattr`、动态 `import` 决定了 LSP 的宿命：**大概率没有假阳性（查到的引用都是真的），但必然存在假阴性（有些动态引用查不到）。**

这决定了定级原则：**LSP 提供强证据（阳性）就判死刑（Error），缺乏证据（阴性）只给警告（Warning）。**

* **必须是 Error（阻断执行，打回重做）：**
  * `E_SYMBOL_NOT_FOUND`：声明要改的符号不存在（LSP 找不到大概率就是幻觉）。
  * `E_UNCOVERED_REFERENCES`：Serena **已经发现**了静态调用方，但不在计划覆盖范围内（这是 100% 会导致崩溃的死代码）。
* **只能是 Warning（最佳努力，允许放行）：**
  * `W_ZERO_REFERENCES_ON_DELETE`：下线任务中，LSP 没找到引用。但这不代表没有动态路由调用，只能给 Warning，依靠后置的 E2E 测试兜底。
  * **泛型误判的豁免**：如果修改的函数叫 `save()` 且无 Type Hint，LSP 可能错将全局所有的 `save()` 当作引用。必须允许在 `plan.yaml` 中通过 `suppress: [E_UNCOVERED_REFERENCES]` 强行豁免。

### 5. 三层（四层）校验模型：完美的职责漏斗

引入 Serena 后，各层的职责变得前所未有的清晰，彻底释放了 LLM 的算力负担：

1. **第一层：物理拓扑层（Ralph 纯结构校验，<0.1s）**
   * *回答*：图有环吗？孤岛？YAML 格式对吗？
2. **第二层：代码事实层（Ralph + Serena，~3s）**
   * *回答*：声称的符号存在吗？所有静态调用链都被计划包裹了吗？
   * *价值*：把过去 Codex 兼职做“人肉编译器”的工作转化为确定性规则。
3. **第三层：业务逻辑层（Codex / LLM Agent，~30s）**
   * *Prompt 优化*：“低级拼写、符号存在性和基础引用链**已由底层工具（附报告）验证**。请你仅专注于审查 API 业务语义是否合理、测试用例是否覆盖了边缘分支。”
4. **第四层：运行时层（Worker 验证执行 / E2E 测试，分钟级）**
   * *回答*：实际跑通了吗？Exit Code 是 0 吗？

### 6. 关键风险与陷阱管理

**陷阱 1：增加 Foreman 的心智负担导致幻觉**
* **风险**：强迫 Foreman 在写计划时凭空拼写精确的 `symbol`，它很容易编造不存在的路径，导致反复校验失败卡死。
* **对策**：在 Foreman 的规划阶段（生成 YAML 之前），必须给它挂载 Serena 的只读 Tool（如 `get_symbols_overview` 和 `find_symbol`）。让规划 AI **“睁着眼睛看真实代码树”** 来写计划，而不是盲写。

**陷阱 2：重命名风暴（Rename Storm）**
* **风险**：如果要改一个底层通用类，Serena 查出 500 个引用点。Ralph 强行要求将 500 个文件全部列入计划，系统将瘫痪（变成巨大的单体任务）。
* **对策**：为规则设定阈值。当未覆盖引用数大于（例如）20 个时，不抛 Error，而是降级为 `W_MASSIVE_REFACTOR` 警告，提示规划者此修改属于全局重构，应使用自动化重构 Worker 工具，而跳过常规的文件级 Claim 校验。
