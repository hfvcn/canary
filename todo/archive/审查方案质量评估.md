  ---
  gpp — 最高质量，结构化深度审查

  优点：

  1. 找到了原方案真正的盲点。assignment_id / lease_id 这个问题是三份审查中唯一一个我和 Codex 都没发现的关键缺陷——stop 后旧 worker 的迟到 completed 会覆盖新
  assignment。这一条就值回整篇审查。
  2. 每个质疑都附带"为什么"和"更合适的方案"。不是空洞地说"这不好"，而是给出具体的替代设计（kind+reason_code+snapshot、ralph_task_event
  统一入口、受限服务主体、tab registry）。几乎每个方案都是可以直接实现的。
  3. 代码引用精确。提到 chat_support_ops.py:57、group_lifecycle_ops.py:101、ralph_ipc.py:51、workflow.py:135、workflow_orchestrator.py:491
  等——说明确实读了代码并追踪了调用链，不是凭概念推演。
  4. 知道什么该改什么不该改。没有建议推翻整个架构，而是在现有结构上做收敛。比如建议 ralph_task_event 而不是"重写整个 IPC"，建议 resolve_group_runtime_context()
  而不是"换框架"。
  5. 波次重排虽然被否决，但否决理由它自己其实也暗示了——它说"先收敛契约"，但同时也说"后面修一个坏一个"，这说明它理解止血的紧迫性，只是优先级判断不同。

  缺点：

  1. Wave 重排（Phase A→F）过于理想化，如果按它的顺序，止血要等契约收敛完才开始，实际上会拖 1-2 周。
  2. 对三层状态模型（desired_state/runtime_state/admin_hold）的改动面估计偏乐观，没有充分考虑到所有 lifecycle ops 的改动连锁反应。

  结论：这是一份专家级审查。写审查的人对这类多 Actor 调度系统有架构经验，并且花了时间读代码。

  ---
  gro — 最低质量，搜索驱动的泛化建议

  核心问题：几乎没有读过项目代码。

  1. "搜索结果显示"反复出现。全文多处 搜索显示、搜索确认、基于搜索最佳实践、搜索中多篇文章称。这是典型的搜索增强 LLM
  输出模式——把通用最佳实践往具体项目上套，不考虑是否适用。
  2. 断言没有依据：
    - "Wave 1 验收时间缩短 50%" — 凭什么？这个数字是编的
    - "吞吐不降反升" — 在 worktree 需要重写整个 worker cwd/验证/合并链路的前提下，这个断言忽略了实现成本
    - "1-2 天即可验证 worktree PoC" — 低估了至少一个数量级
  3. 建议和项目实际脱节：
    - 推荐 SSE/WebSocket 替代轮询：当前系统 daemon 通过 Unix socket + JSON line 通信，前端通过 HTTP 轮询。引入 SSE 要改 daemon server、route、前端 store
  的整个数据流。这不是"改个 endpoint"的事。
    - 推荐 Git worktree 作为 Wave 2 核心：当前 runner (pty/headless) 都假设 worker 在同一 cwd 工作。改成 worktree 要改 runner 初始化、scope
  管理、文件监控、验证路径、前端文件展示。
    - 推荐 @dnd-kit/sortable + rectSortingStrategy + KeyboardSensor：这是从教程里抄来的，和 Board Tab 的实际数据模型无关。
  4. 没有发现任何原方案的盲点。gpp 发现了 assignment_id 缺失，gedt 发现了安全风险，gro 发现了什么？——它只是用通用建议替换了具体方案。
  5. 被采纳项为零。在讨论中没有任何唯一来自 gro 的建议被采纳。worktree 被记为"长期方向"，但这在我们原方案里已经有了（Wave 4+）。

  结论：这是一份搜索拼凑的伪审查。信噪比极低，核心价值接近零。

  ---
  gedt — 中等质量，有亮点但部分脱离实际

  优点：

  1. 安全视角有价值。指出 by="system" 是"严重安全反模式"并提到 prompt injection 风险——这个角度 gpp 也有但 gedt 说得更直接。虽然最终采纳的是 gpp
  的受限服务主体方案（更灵活），但 gedt 的安全警告强化了这个方向。
  2. 被动 IO 探针是独创贡献。"Tool Executor 发现 Worker 在调用任何底层动作时自动刷新活跃时间"——这是三份审查中唯一被独立采纳的 gedt 建议。实用且可行。
  3. 前端 Store 直连 + Discriminated Union 的表述比 gpp 更具体。虽然 gpp 也提了 tab registry，但 gedt 把 useWorkspaceStore(state => state.tasks)
  直接写出来了，可读性更好。

  缺点：

  1. OCC 乐观并发的核心断言不成立。"LLM 极其擅长处理文本 Diff" — 这个断言没有证据支撑。LLM 能读
  diff，但"可靠地在代码中自动解决合并冲突"是另一回事。在生产环境把正确性外包给模型是不可接受的。
  2. desired_state 模型虽然方向对，但低估了改动面。建议"彻底分离配置与状态"、"在运行时 .state 库中引入 desired_state"——这实际上要重写整个 actor
  生命周期管理。它把这当成一个简单替换，但实际上是 Wave 3 级别的重构。
  3. "介入式抢救 (Poke)"在当前架构下不可行。"向 Worker 强行注入一条高优系统 Prompt"——当前 pty runner 和 headless runner 都没有从外部注入 prompt
  的接口。这不是加个函数就能做的，需要 runner 架构变更。
  4. 5 个质疑中有 2 个核心方案被否决（OCC、Poke），采纳率 60%，低于 gpp 的 ~90%。

  结论：有思考深度但对项目实际约束了解不足。适合作为"理想方向参考"，不适合直接指导实现。
