# Findings — CCCC 工作流实践教训

> 来源：2026-03-26 ~ 2026-03-28 的 CCCC 工作流修复全过程
> 参与方：Claude (Opus 4.6) + Codex (GPT-5.4) + 3 份独立审查 (gpp/gro/gedt) + 用户实际测试
> 执行量：4 波修复, 27 个 Task, 44 文件, +2381/-450 行

---

## 教训一：编译通过不等于功能可用

27 个 Task 全部通过了 `py_compile` 和 `tsc --noEmit`，但用户实际测试发现 Ralph 的全部功能是死代码。

**具体表现**：
- `RalphService` 类存在，但 daemon 启动不创建实例
- `suggest_ready_batch()` 方法存在，但没有任何调用者
- `claimed_paths` 字段已加到 `TaskRef`，但 MCP 工具不存在所以 Foreman 无法传入
- `get_snapshot()` 返回 `"ralph_service_not_wired"` — 代码自己承认了自己是死代码

**根因**：我们的验证标准是"文件能编译"，而不是"功能能运行"。静态验证只能证明语法正确和类型一致，无法证明代码在运行时会被执行。

**教训**：验证的最低标准应该是"从入口到出口，这条路径能走通"。在没有端到端验证能力之前，不应该信任任何静态检查的结果作为"完成"的依据。

## 教训二：按文件拆任务会产生精致的死代码

我们用 Ralph 式的依赖分析拆分任务："这个文件的 write_set 和那个不重叠，所以可以并行"。每个 Task 都在自己的文件范围内做得很好，但没人负责把它们接起来。

**具体表现**：
- Worker-A 在 `ralph_service.py` 里实现了 RalphService
- Worker-1A 在 `workflow_orchestrator.py` 里接入了 RalphService
- Worker-1B 在 `workflow.py` 里改了 route
- 但没有任何 Task 负责"在 daemon 启动时创建 RalphService 实例"
- 也没有任何 Task 负责"在 MCP handler 里注册 Ralph 工具"

**根因**：端到端功能需要多个文件协作，但我们按"文件不冲突"拆分，每个 Task 只看自己的文件。集成层（daemon 启动、MCP 注册）不属于任何一个 Task 的 write_set。

**教训**：任务拆分不应该只按文件依赖，还应该按端到端流程。每个功能至少需要一个"接线 Task"，负责确保各个组件在运行时真正连接。

## 教训三：讨论的精细度和实际验证的粗糙度严重不匹配

4 轮 Claude×Codex 讨论 + 3 份独立审查，产出了 21KB 的方案文档，讨论了：
- `hold_reason` 还是 `admin_hold`（命名）
- `service:*` 前缀 vs `Role.ORCHESTRATOR`（权限模型）
- `kind + reason_code + snapshot` vs 扁平结构（API 格式）
- OCC vs single_writer vs claimed_paths vs worktree（并发策略）

但没有人问过：
- "daemon 启动后会发生什么？"
- "Foreman 的第一个 MCP 调用是什么？"
- "从用户在飞书发需求到 Worker 开始写代码，中间经过哪些步骤？每步谁触发？"

**根因**：讨论聚焦在数据模型和接口设计（静态结构），而非运行时行为（动态流程）。这是架构讨论的常见陷阱 — 花大量时间在"东西长什么样"上，忽略了"东西怎么动起来"。

**教训**：任何方案讨论应该从"描述一次完整的用户场景从头到尾怎么走"开始，而不是从"这个数据结构应该有哪些字段"开始。

## 教训四：让 AI 扮演缺失的组件会掩盖问题

用户一开始就指出："让 Codex 扮演 Ralph 做任务拆分，发现不了 Ralph 本身的问题"。我们后来意识到了这一点，补了 `ralph_service.py`，但仍然没有让 Ralph 真正运行。

**具体表现**：
- Codex 扮演 Ralph 做了很好的依赖分析和并行拆分
- 但真正的 Ralph 需要 MCP 工具注册、daemon 初始化、事件驱动触发
- 这些都是 Codex 扮演时不需要面对的问题

**根因**：模拟和实现有本质区别。模拟只需要输入和输出正确，实现需要整个运行环境正确。

**教训**：如果一个组件不存在，正确的做法是先让它的最小版本真正运行起来，而不是让另一个 AI 假装它存在。一个能运行的空壳比一个不能运行的完整实现有价值得多。

## 教训五：Codex/AI Worker 是忠实的执行者，不是集成验证者

每个 Codex Worker 严格做到了被分配的任务：
- 修改指定文件 ✓
- py_compile 通过 ✓
- 不碰其他文件 ✓

但没有任何 Worker 做了：
- "启动 daemon 看看我的改动有没有效果"
- "调用一下我刚注册的 handler 看看返回什么"
- "从 Foreman 的视角试一下这个工作流能不能走通"

**根因**：我们给 Worker 的约束是"只改这些文件，验证编译通过"。Worker 忠实执行了指令，但指令本身没有要求运行时验证。

**教训**：如果验收标准只是"编译通过"，那产出的质量上限就是"能编译的代码"。验收标准必须包含运行时行为验证，否则不管投入多少 Worker，产出都是不确定的。

## 教训六：工作流本身必须可被自动化测试

当前 CCCC 工作流的测试只能通过人在 Web UI 手动操作。这意味着：
- AI 改完代码只能做静态检查，不能自验
- 人必须手动走一遍 daemon→group→actor→workflow 才能发现问题
- 形成"写代码→编译通过→人去测→发现不工作→再写代码"的低效循环

**对比**：如果存在一个命令如 `cccc test-workflow --scenario "batch-suggest-and-complete"`，AI 可以在每次改动后自动验证，不需要人介入。

**教训**：如果你构建的系统不能被自动化测试，那修复这个系统的过程也不能被自动化。在设计系统时，"如何测试这个系统"应该和"系统如何工作"同等重要。

## 教训七：先跑通一条路径，再扩展功能

我们的做法是：先做完所有的数据模型设计 → 再并行实现所有功能 → 最后才发现接不起来。

正确的做法应该是：
1. 先让最简单的路径从头到尾跑通（哪怕只有硬编码）
2. 在可运行的基础上逐步替换硬编码为真实实现
3. 每一步都保持端到端可运行

**具体来说**：应该先让 `daemon 启动 → RalphService 初始化 → 一个 MCP 工具可用 → Foreman 能调用 → 返回一个硬编码结果` 这条路走通，然后再去实现 claimed_paths、依赖门控、三层状态等功能。

**教训**：一个能跑的最小闭环 > 十个不相连的完整模块。增量构建在可运行基础上的功能，而非先画完蓝图再一次性接线。

## 教训八：审查的盲区和审查的价值

Wave 3 的联合审查（我 + Codex）确实发现了 7 个代码级问题并修复。但审查聚焦在"这段代码的逻辑对不对"，没有审查"这段代码会不会被执行到"。

审查发现了：
- handler 调用路径错误（R-5）— 修了
- enabled/desired_state 不同步 — 修了
- context_ops 权限过宽 — 修了
- claimed_paths 在 IPC 入口丢失 — 修了

审查没发现：
- daemon 不初始化 RalphService（R-2）
- MCP 工具层完全缺失（R-1）
- task_management.yaml 可能不在 prompt 注入链路（R-4）

**教训**：代码审查能发现逻辑错误，但发现不了集成缺失。"这段代码对不对"和"这段代码有没有被用到"是两个不同的问题，后者需要运行时验证。

## 教训九：用户一开始就说了正确答案，但被讨论淹没了

用户在最初就提出了三个关键判断，每个都在后续被验证为正确：

1. **"由 Codex 扮演 Ralph 终究和真正使用 Ralph 有区别"** — 我们认可了这一点但只补了一个骨架类，没有让它真正运行。最终所有 Ralph 功能确实是死代码。

2. **"要把 MCP 转成一般工具，通过提示词和 Ralph 来引导 AI 使用"** — 我们讨论了"MCP 职责收缩"和"transport-neutral 服务"，但实际执行时仍然在 MCP 框架内打转（讨论加什么 MCP 工具、怎么注册 MCP handler）。用户的意图是**去掉 MCP 而非优化 MCP** — AI 应该直接通过 CLI/HTTP 调用工具，靠提示词引导正确使用，靠 Ralph 的验证闭环保障结果正确。MCP 的每次全量加载开销、runtime 差异导致的不可靠通信（codex 几乎不用 MCP 回报）、以及它作为唯一集成协议的脆弱性，都证明了用户的判断。

3. **"工作流太笨重，不利于 AI 直接端到端测试"** — 我们在修完 27 个 Task 后才发现这一点，但用户在讨论 Ralph 拆分时就已经隐含了这个观察。

**教训**：当用户基于实际使用经验提出架构级判断时，不要把它当作"一个优化建议"去讨论和折中，而应该作为约束条件直接纳入方案的出发点。我们花了大量讨论时间来收敛"MCP 应该保留哪些职责"，而用户的答案从一开始就是"MCP 应该被替代"。

## 教训十：后续工作的前置条件

在继续写功能代码之前，以下四件事必须先完成：

### 1. 验证基础设施先于功能开发

先有一个能跑的 `cccc test-workflow` 命令（哪怕只验证最简单的场景），然后所有功能开发都以"这个命令能通过"为验收标准。这个验证命令本身就是 Ralph 验证闭环的第一个用户。

### 2. 并行化的正确单元是"可独立验证的功能切片"，不是文件

"Foreman 能提交 batch suggest 并看到 progress 更新"是一个切片 — 跨 5+ 个文件但不可分割。这样的切片可以独立验证，也可以交给一个 worker 端到端完成。两个切片如果没有运行时交互，才能真正并行。

### 3. 去掉 MCP，改为 CLI/HTTP 直接调用 + 提示词引导 + Ralph 强约束

这是用户从一开始就明确的方向：
- AI 通过 CLI 命令或 HTTP API 直接调用工具，不经 MCP 协议
- 提示词引导 AI 按正确顺序和方式使用工具
- Ralph 验证闭环作为最后一道保障 — 验收不通过则重试
- 不同 runtime (Claude/Codex/Gemini) 都走相同的 CLI/HTTP 路径，消除 MCP 可靠性差异

### 4. 每个设计文档必须附带可执行的验证场景

不能只写"系统应该做什么"，必须同时写"用什么命令验证系统确实在做"。写不出验证场景的设计还不够具体。
