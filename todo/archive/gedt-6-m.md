**VERDICT**: `needs-attention`

**SUMMARY**:
The v5 optimization plan accurately diagnoses the system's design drift and establishes strong invariants. However, its execution sequencing introduces a deterministic self-lockup: deploying strictly blocking runtime monitors in Phase 1 for architectural flaws that are not fixed until Phase 4 and Phase 5 will instantly paralyze all workflows during the migration. Furthermore, the proposed asynchronous IPC handoffs (Option Z) lack concurrency control, introducing Time-Of-Check-To-Time-Of-Use (TOCTOU) races, and fail to define terminal DAG cascading, risking permanent liveness stalls.

**PRIMARY FINDINGS**:

- **[severity: critical] Phase 1 strict blocking creates an unrecoverable development deadlock**
  - File: `六、分阶段方案`, Phase 1 (P1-B) vs Phase 4 (P4-A) & Phase 5 (P5-G)
  - Confidence: 1.0
  - Body: Phase 1 introduces runtime monitors that explicitly execute "违规时阻断" (block on violation) for all 5 invariants. However, the system's underlying code will still violate them: `NO_AUTO_DISPATCH` (ARCH-3) is not fixed until Phase 4, and `CLEAN_RETRY` (ARCH-8) is not fixed until Phase 5. If Phase 1 enforces strict blocking, every single multi-step workflow or retry executed during Phase 2 and Phase 3 development will hit the legacy code, trigger a monitor violation, and hard-crash. The team will be physically unable to run E2E tests to validate their Phase 2/3 work.
  - Recommendation: Deploy Phase 1 monitors strictly in "Audit/Shadow Mode" (log violations and fail negative tests, but do not block runtime daemon execution). Toggle the active blocking mode for each invariant atomically only in the phase where its corresponding code fix is merged.

- **[severity: high] TOCTOU Race Condition in Option Z Late IPC Replies**
  - File: `六、分阶段方案`, Phase 2 (P2-C, Option Z 混合方案)
  - Confidence: 0.95
  - Body: Option Z introduces a system-side safety rail ("最长 N 分钟总等待") that transitions a task to `BLOCKED`. Because the Foreman AI operates asynchronously over IPC, its response latency is non-deterministic. If the N-minute timeout triggers in the Engine and transitions the task to `BLOCKED` *exactly* while Foreman's assignment reply is in-flight, the Orchestrator will process the delayed assignment. Without explicit precondition checks, it will blindly apply the assignment to a dead task, overwriting the `BLOCKED` state and corrupting the state machine.
  - Recommendation: Introduce a concurrency token (e.g., `decision_deadline_token`) generated by the daemon in the `BatchAssignmentFailed` message. Foreman must echo this token. The Engine must perform a Compare-And-Swap (CAS) to reject late replies if the token has expired.

- **[severity: high] State Tearing via Orchestrator Event Listener Blocking**
  - File: `六、分阶段方案`, Phase 1 (P1-B)
  - Confidence: 0.90
  - Body: Task P1-B attaches the monitor as an "事件监听器" (event listener) inside the `WorkflowOrchestrator` that "阻断" (blocks/throws errors). The Orchestrator handles side-effects (e.g., IPC dispatch, memory queue updates). If an external listener throws an exception mid-function inside the Orchestrator, it leaves the daemon in a torn, non-atomic state. The Engine (which section 4.1 declares as the "唯一权威" / sole authority) is completely bypassed in this enforcement.
  - Recommendation: Do not implement the monitor as an Orchestrator event listener. Embed the 5 invariant assertions directly inside `WorkflowEngine` as synchronous pre-transition hooks. The Engine itself must reject invalid transitions atomically, returning a clean `TransitionRejected` error before any side-effects occur.

- **[severity: medium] Localized `BLOCKED` state causes unhandled DAG starvation**
  - File: `六、分阶段方案`, Phase 2 (Option Z 混合方案)
  - Confidence: 0.90
  - Body: Option Z transitions individual tasks to `BLOCKED` and "通知用户" (notifies user). In a DAG execution engine, if a parent node is stuck in `BLOCKED` indefinitely (e.g., user is offline), its dependent child nodes are starved. The document specifies no cascading liveness rules. The overall workflow run will hang forever in memory, holding claims on worker actors initialized in parallel branches and leaking resources.
  - Recommendation: Define explicit cascading rules. If a task enters `BLOCKED`, the Engine must recursively transition downstream dependent tasks to `CANCELED` or `UNREACHABLE`. Define a secondary workflow-level TTL that forcefully terminates the entire DAG if user intervention is not received.

**STRUCTURAL PRESSURE TEST**:

- **[type: model] Dynamic Task Splitting invalidates Static Plan Verification**
  - Grounding: `Phase 2` Option Z ("(c) 拆分任务") vs `Phase 3` (Ralph 编译期规则) & `Phase 5` (reverse-check)
  - Why it matters: The system's entire security model relies on Ralph verifying a static `plan.yaml` before execution. However, Option Z authorizes the Foreman AI to dynamically mutate the DAG at runtime ("拆分任务" / split tasks). If Foreman generates new nodes at runtime, they bypass Ralph's compile-time structural checks (Phase 3). When Phase 5's `reverse-check` runs, it will flag the execution as a massive violation because the runtime DAG no longer matches the statically approved plan.
  - Better shape: Remove "(c) 拆分任务" from the allowed Option Z runtime actions, forcing Foreman to fail the workflow and propose a completely new static plan; OR formalize dynamic DAG mutation by requiring the Orchestrator to synchronously call Ralph's `verify` API on the dynamically generated sub-graph before the Engine accepts the split.
  - Confidence: 0.95

- **[type: sequencing] In-flight workflow corruption during ARCH-4 schema migration**
  - Grounding: `Phase 4` (P4-B: "删除 `_active_workflows` 影子状态；schema 迁移")
  - Why it matters: The plan treats removing the `_active_workflows` memory state and migrating the Engine schema as a static deployment step. If this Phase is deployed to a daemon with active, running workflows, those in-flight workflows will instantly lose their assignment context in memory. When worker AIs attempt to report completion, the Orchestrator will crash, permanently stranding the execution processes.
  - Better shape: Do not hard-delete `_active_workflows` immediately. P4-B must mandate a "drain" phase. New assignments must strictly use `TaskState`, but the daemon must retain a read-only fallback path to `_active_workflows` until all pre-existing in-flight workflows reach a terminal state.
  - Confidence: 0.90

- **[type: authority] Schizophrenic Foreman authority split across Phase 2 and 4**
  - Grounding: `Phase 2` (fixes ARCH-1/2 for initial batch) vs `Phase 4` (fixes ARCH-3 for subsequent batches)
  - Why it matters: The stated goal is to make Foreman the sole decision-maker. However, the plan splits the implementation. In Phase 2, Foreman handles initial task assignments, but auto-dispatch remains for subsequent DAG batches until Phase 4. Operating the system during this transition window trains the LLM on a contradictory mental model ("I must assign Step 1, but Step 2 magically assigns itself"). This will likely cause hallucinations and failures when Phase 4 finally removes the magic.
  - Better shape: Pull P4-A (ARCH-3 fix) into Phase 2. All assignment authority boundary shifts—whether for the first batch or subsequent tasks—should be executed simultaneously so the AI's contract and prompt remain consistent.
  - Confidence: 0.85
