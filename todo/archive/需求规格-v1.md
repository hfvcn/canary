## 二、统一状态枚举

合并 Context 系统 (`planned/active/done/archived`) 和 workflow 系统 (`pending/running/completed/failed/blocked`)：

```python
class TaskStatus(str, Enum):
    PLANNED = "planned"       # 任务已规划，尚未就绪
    READY = "ready"           # 依赖满足，可被分配
    ASSIGNED = "assigned"     # 已分配给 Worker，等待启动
    RUNNING = "running"       # Worker 正在执行
    VERIFYING = "verifying"   # Worker 报完成，等待 Ralph 验证
    COMPLETED = "completed"   # Ralph 验证通过，任务完成
    FAILED = "failed"         # 执行失败或验证失败（不可自动重试）
    BLOCKED = "blocked"       # 需要人工/外部介入
    ARCHIVED = "archived"     # 已归档（长期管理用）
```

**状态流转规则：**
```
planned → ready          # batch suggest 发现依赖满足
ready → assigned         # Foreman 批准并绑定 Worker
assigned → running       # Actor 实际启动
running → verifying      # Worker 上报 completed evidence
verifying → completed    # Ralph 验证通过
verifying → failed       # Ralph 验证失败 + Foreman 决定不重试
verifying → ready        # Ralph 验证失败 + Foreman 决定重试
running → failed         # Worker 上报执行失败
any → blocked            # 需要人工介入
completed → archived     # 长期归档
```

**关键约束：** 只有 `completed` 状态的任务才能解锁后继任务的依赖。`verifying` 不能解锁。

## 三、功能切片 Schema (TaskRef 扩展)

在现有 `contracts/v1/ralph_ipc.py:TaskRef` 上扩展，不新建模型：

```python
class TaskRef(BaseModel):
    # --- 现有字段 ---
    id: str
    title: str = ""
    type: Literal["frontend", "backend", "general"] = "general"
    depends_on: List[str] = []
    claimed_paths: List[str] = []

    # --- 新增 7 字段 ---
    goal_behavior: str = ""           # 目标行为（一句话描述做什么）
    acceptance_criteria: str = ""     # 验收标准（怎么判断做完了）
    verification_command: str = ""    # 自动化验证命令（Ralph 执行，判断退出码）
    expected_input: Dict[str, Any] = {}   # 预期输入（用于 mock 预验证）
    expected_output: Dict[str, Any] = {}  # 预期输出（用于核对行为正确性）

    # expected_input/output 格式:
    # {
    #   "format": "json",           # json / text / http_response
    #   "example": {...},           # 示例数据（必填，可直接用于 mock）
    #   "schema": {...},            # JSON Schema（可选，用于结构约束）
    # }
```

**设计原则：**
- `verification_command` 负责"怎么跑"
- `expected_input/output` 负责"拿什么数据跑、预期看到什么"
- 两者不混为一个字段
- 在任务规划阶段就约定好整个任务每个子任务的预期输入和输出
- 即使依赖任务还没完成，也可以通过预先约定好的数据结构进行 mock 预验证

## 四、实现要点（基于 Codex 分析）

### A. 统一状态层

**位置：** 新建 `src/cccc/kernel/workflow_state.py`
**持久化：** `group.path / "state" / "workflow/"`

**需要改动的写入点：**
1. `WorkflowOrchestrator._active_workflows` → 改为读写统一层
2. `ProgressReporter._state` → 改为从统一层读取投影
3. `RalphService._task_statuses` → 删除自有状态，只读统一层
4. `Context/cccc_task` → 降为投影层，不再承载执行态真相

**需要改动的读取点：**
1. `ralph_ipc_handler.py` 所有 handler → 从统一层读写
2. `workflow.py` HTTP routes → 从统一层出快照
3. `ProgressReporter` → 从统一层生成飞书卡片数据

### B. Ralph 验证闭环

**修复调用路径：**
- `ralph_ipc_handler.py:723` — 改为调用 `orchestrator.apply_task_event(event)` 而非 `orchestrator.ralph.apply_task_event(event)`

**验证逻辑：**
- 复用 `ralph/ralph/validator/build_test.py` 的 `BuildTestValidator`
- 第一阶段最小集：`py_compile <changed .py files>` + `task.verification_command`
- 不使用 `ValidatorConfig.default_for_python()` 的默认 git diff 命令
- 核对 `expected_output` 是否匹配实际输出

**验证失败处理：**
- 记录 `verification_attempts`, `last_verification`, `retry_reason` 到统一状态
- 通知 Foreman 决策：重试（verifying → ready）/ 标记失败（verifying → failed）/ 人工介入（→ blocked）
- `blocked` 仅用于人工/外部阻塞，不用于可自动重试的验证失败

### C. Capability Prompt 接线

**需要改动的三个 delivery 调用点：**
1. `delivery.py` — `deliver_message_with_preamble()`
2. `delivery.py` — `flush_pending_messages()` 的 preamble 分支
3. `delivery.py` — `inject_system_prompt()`

**推荐方案：**
- 新建 `render_actor_prompt()` helper，统一入口
- 组装顺序：身份/作用域头 + capability YAML fragments + group preamble override + worker_prompt
- delivery、CLI、测试都只切这一个入口

**capability YAML 更新：**
- `task_management.yaml` 状态词改成新枚举
- Foreman fragment：写清 verify gate 规则、核心路径是 HTTP/CLI
- Peer fragment：只能报告 evidence/changed_files，不得自称 done
- Common fragment：写入 7 字段切片约束

**兼容风险：**
- CLI `cccc prompt` 直接依赖 `render_system_prompt()`
- 多组测试 (`test_system_prompt_memory.py` 等) 依赖旧函数
- `CCCC_PREAMBLE.md` 和 `worker_prompt` 需保留为 base prompt 或独立 fragment

### D. claimed_paths 复用

- 将 `_normalize_claimed_path()`, `_write_sets_conflict()`, `_paths_overlap()` 从 `ralph_service.py` 抽到 `kernel/claimed_paths.py`
- 统一状态层和 RalphService 共用
- `suggest_ready_batch()` 改为从统一层获取运行中任务集合

### E. HTTP 金路径（已存在路由）

现有路由 (`ports/web/routes/workflow.py`)：
- `POST /api/v1/groups/{group_id}/workflow/batch/suggest` — 提交 batch
- `POST /api/v1/groups/{group_id}/workflow/batch/process` — 处理 pending batch
- `GET /api/v1/groups/{group_id}/workflow/progress` — 查询进度
- `POST /api/v1/groups/{group_id}/workflow/task/completed` — 报告完成
- `POST /api/v1/groups/{group_id}/workflow/task/failed` — 报告失败

**需要补充：**
- CLI 薄包装：`cccc workflow submit/status/verify`

### F. Hot Reload

开发工作流时支持 daemon 热重载，代码改动后自动生效，无需手动重启。

## 五、验证场景

### 端到端测试场景

**提示词（发给 Foreman）：**
> 这是一个测试项目，用于测试 CCCC 工作流效果。
> 参考文档：docs/ralph-foreman-workflow.md
> 你的任务是在遵守工作流提示词的前提下，自行选择一个复杂度中等、包含前后端的项目去实现。
> 在完成项目的同时，对工作流进行检查和评价，指出认为不合理的地方以及没有按预期运行的工作流机制。

**成功标准：**
1. Foreman 自主规划：拆解为功能切片（含 7 字段），选择 Worker
2. Ralph batch suggest：计算依赖和 claimed_paths，建议并行 batch
3. Foreman 批准 batch，Worker 被分配并启动
4. Worker 执行完毕，上报 evidence
5. Ralph 验证：执行 verification_command + 核对 expected_output
6. 状态正确流转：planned → ready → assigned → running → verifying → completed
7. 下一 batch 自动推进
8. 飞书通知在关键节点发出
9. Foreman 最终产出工作流评价报告
