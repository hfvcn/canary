### 0.1 CCCC 是什么

CCCC 是一个 AI Agent 多人协作中枢，让多个 AI Agent（Claude、Codex、Gemini 等）作为一个团队协作完成软件工程任务。

核心角色：
- **Foreman**：管理者 AI，负责需求拆分、任务分配、进度跟踪
- **Worker**：执行者 AI，接受任务并实现功能
- **Ralph**：工作流引擎，负责任务调度（依赖分析+write-set冲突检测）和验证（verify gate）
- **Daemon**：后台进程，是所有状态写入的唯一权威

### 0.2 发生了什么

过去 5 天经历了完整的问题发现→修复→验证循环：

| 阶段 | 内容 | 结果 |
|------|------|------|
| Day 1-2 | 4 轮方案讨论 + 3 份独立审查 + 27 个 Task 并行修复 | 所有 Task 通过 py_compile/tsc |
| Day 3 | 第一轮 E2E 测试（LinkVault 项目） | 发现 Ralph 全部是死代码 |
| Day 4 | 第二轮 E2E 测试（Kanban 项目） | 确认 Ralph 闭环未接通，但数据模型修复有效 |
| Day 5 | Ralph 独立化 + 修复计划生成 + Claude-Codex 联合审查 | 产出独立 Ralph CLI + 经审查的修复计划 |

### 0.3 核心教训（详见 todo/findings.md）

1. **编译通过不等于功能可用** — 27 个 Task 全过 py_compile，但 Ralph 在运行时完全不可达
2. **按文件拆任务会产生精致的死代码** — 没有 Task 负责"在 daemon 启动时创建 RalphService"
3. **讨论精细度和验证粗糙度不匹配** — 21KB 方案讨论聚焦数据模型，零人问"daemon 启动后会怎样"
4. **用户从一开始就说了正确答案** — 用户说"去掉 MCP"，我们讨论的是"优化 MCP"

### 0.4 本轮新产出

**独立 Ralph CLI**（`src/cccc/ralph/`）：一个脱离 CCCC daemon 可独立运行的任务规划校验器。

```bash
ralph validate plan.yaml     # 结构性检查（依赖图、覆盖率、集成缝隙）
ralph suggest plan.yaml       # 输出可并行批次 + 阻塞原因
ralph verify plan.yaml --task T1  # 执行验证命令
ralph explain plan.yaml --task T1 # 解释任务为什么被阻塞
```

**设计原则**：
- 文件驱动：plan.yaml 是唯一真相源，Ralph 只读不改
- 无状态：每次传入完整上下文（tasks + state），结果可重放
- 零 daemon 依赖：只用 stdlib + pydantic + pyyaml

## 二、Codex 审查中的关键发现

> 以下发现来自 Codex 对代码的实际审查，修正了问题清单 v3 中的部分判断。

### 2.1 "Ralph 完全是死代码"不精确

问题清单 v3 说"daemon 不初始化 RalphService"。Codex 审查发现：
- `get_orchestrator(group_id, project_root=...)` 会 lazy-init `WorkflowOrchestrator`
- `WorkflowOrchestrator.__init__()` 会实例化 `RalphService`
- verify gate 在 `apply_task_event()` 里存在且会切到 `verifying` 状态

**精确判断**：后端代码大体可用，问题是**默认路径根本不会到达它**。Worker 被 prompt 引导到 `cccc_message_send` 报告完成，这条路径不触发 verify gate。

### 2.2 最高 ROI 的改动是改 prompt，不是改后端

- CLI 命令已存在（`cccc workflow submit/status/verify/retry/fail`、`cccc task complete`）
- HTTP routes 已存在
- 验证链已存在
- **真正断裂的是 AI 看到的指令**

### 2.3 验证命令可能是假的

第一版计划中，两个任务的 verification 引用了不存在的函数（`build_system_prompt`、`build_preamble`）。Ralph validate 报告 "valid" 但这些命令实际会失败。

**教训**：Ralph 当前无法验证 verification_command 是否可执行，只做结构性检查。这是已知限制。

## 四、Ralph 工具当前能力与已知限制

### 4.1 Ralph 的检查规则（共 27 条）

**图结构**：E_DUPLICATE_TASK_ID, E_DEP_UNKNOWN, E_DEP_SELF, E_DEP_CYCLE, W_DISCONNECTED_COMPONENTS, W_ISOLATED_TASK

**字段完整性**：E_MISSING_CLAIMED_PATHS, E_MISSING_VERIFICATION, W_EMPTY_ACCEPTANCE, W_GLOBAL_WRITE_CLAIM

**验收强度**：E_NO_CROSS_TASK_VERIFICATION, W_WEAK_VERIFICATION_ONLY, E_MISSING_INTEGRATION_SPINE, W_VERIFICATION_BEHAVIOR_MISMATCH

**契约匹配**：E_CONSUMER_WITHOUT_PROVIDER, E_CONSUMER_FROM_UNKNOWN, W_PROVIDER_UNUSED, W_CONSUME_WITHOUT_DEP, W_DEP_WITHOUT_CONSUME

**关键覆盖**：E_CRITICAL_ENTRYPOINT_UNOWNED, E_CRITICAL_FLOW_UNCOVERED, E_CRITICAL_FLOW_ENTRYPOINT_UNOWNED, E_CRITICAL_FLOW_LEVEL_TOO_WEAK

**禁止流**：E_FORBIDDEN_FLOW_UNCOVERED, E_FORBIDDEN_FLOW_LEVEL_TOO_WEAK

**问题覆盖**：E_UNCOVERED_REQUIRED_ISSUE

**集成缝隙**：W_CROSS_BOUNDARY_WITHOUT_GLUE, W_IMPLICIT_SERIALIZATION

### 4.2 已知限制

1. **无法验证 verification_command 是否可执行** — Ralph 检查结构，不跑命令。第一版计划中两个验证命令引用了不存在的函数，Ralph 没抓到（Codex 审查发现）
2. **suggest 算法是顺序贪心** — 按任务顺序单遍加入，可能给出次优批次（如先选了全局写的任务会挡住其他可并行任务）
3. **契约检查只做名字匹配** — schema_hint 字段存在但未使用，无法检测类型不匹配
4. **无 role-based 规则** — TaskSpec 有 role 字段（leaf/integration/verification）但 validator 尚未据此强化检查

### 5.5 标记为架构方向（后续计划）

以下来自审查的建议方向正确，但超出本轮 scope，标记为后续：

1. **状态迁移权威收敛** — daemon 内部应有唯一 canonical 入口处理任务完成，CLI/MCP/HTTP 都委托给它（gp-4, gpp-4）

**解读**：
