## 六、根因定位

### 已解决（本轮之前）
- FIX-1 plan→engine 元数据传递 → ✅ 本轮确认 10/10 字段完整传递
- FIX-2 结构化下发 → ✅ Worker 自动收到任务说明
- FIX-3 DAG 门控 → ✅ 严格按 depends_on 解锁，无 batch 阻塞
- FIX-5 verification 语义 → ✅ failed/passed/skipped 正确区分

### 新发现

**ROOT-1: Verification checks 只能验证"存在"不能验证"正确"**
- 根因：grep/compile-check 无法发现调用顺序 bug（如 CSV timing）
- 影响：3 个 CRITICAL 全部逃逸出 verification gate
- 建议：对 integration 任务增加 behavioral checks（如读 CSV 文件验证字段非空）

**ROOT-2: 验证命令未经本地预检**
- 根因：Ralph validate 检查 plan 结构但不 dry-run 验证命令
- 影响：`--no-fatal-infos` 不存在导致 Batch 1 全批假失败
- 建议：Ralph validate 新增 W_VERIFICATION_COMMAND_PRECHECK 规则

**ROOT-3: Assignment 决策缺少结构化记录**
- 根因：Ledger 只记录 assigned_by，不记录 assignment_reason
- 影响：#6 边界检查项无法完全判定
- 建议：batch_approved 事件增加 assignment_reason 字段

## 七、后续改进及对应实例

### [FIX-27] 验证命令本地预检

**优先级**：P0
**影响维度**：过程 + 体验
**预期分数变化**：过程 3.5→4, 体验 4→4.5

**触发实例**：
> v11 实战中，plan.yaml 的 verification.checks 使用 `dart analyze --no-fatal-infos`，该 flag 在本地 Dart SDK 不存在。Batch 1 全部 5 个任务首次 verification_failed，浪费 ~5 分钟。
> Foreman 反馈："The biggest time waste. Ralph should pre-validate verification commands."

**根因**：Ralph validate 检查 plan 结构（依赖、路径、contracts）但不检查 verification.checks.command 是否可执行。

**改进方案**：Ralph validate 新增 `W_VERIFICATION_COMMAND_PRECHECK` advisory rule，对每个 check command 做 `which`/syntax 检查。

**验收标准**：下一轮实战中，不可执行的验证命令在 validate 阶段被 warning 提示。

---

### [FIX-28] Assignment 决策理由记录

**优先级**：P1
**影响维度**：过程
**预期分数变化**：过程 3.5→4.5

**触发实例**：
> v11 Codex 过程审查：#6 判定"无证据"，因为 ledger 中 assigned_by="planner" 但无选人依据。
> Codex 评语："assignment 存在但缺少可审计的 Foreman 决策证据链。"

**根因**：batch_approved 事件只记录 who assigned，不记录 why。

**改进方案**：`cccc workflow submit --assignments` 增加可选 `--assignment-reason` 参数，写入 batch_approved 事件的 assignment_reason 字段。

**验收标准**：下一轮实战中，batch_approved 事件含 assignment_reason 字段，Codex 过程审查 #6 可给完全正面判定。

### [FIX-29] Plan 热重载

**优先级**：P1
**影响维度**：体验
**预期分数变化**：体验 4→4.5

**触发实例**：
> v11 Foreman 发现 `--no-fatal-infos` 问题后修改了 plan.yaml，但已提交的 workflow 使用缓存的旧命令。
> Foreman 反馈："Editing plan.yaml after submission has no effect on verification."

**根因**：Workflow engine 在 submit 时快照 plan，后续修改不自动同步。

**改进方案**：workflow submit 时若 workflow_id 已存在且 plan 文件 mtime 变化，自动更新缓存的 verification commands。

**验收标准**：修改 plan.yaml 的 verification.checks 后，下次 verify 使用新命令。

### [FIX-30] Force-complete 命令

**优先级**：P1
**影响维度**：体验
**预期分数变化**：体验 +0.5

**触发实例**：
> v11 T5 E2E 验证因 legacy 文件 dart analyze 失败，Foreman 手动验证代码正确后无法直接完成任务。
> Foreman 反馈："No cccc workflow force-complete command exists."

**根因**：Verify gate 失败后只能通过 retry → re-complete 间接路径。

**改进方案**：增加 `cccc workflow force-complete TASK_ID --reason "..."` 命令，记录 manual_override 事件。

**验收标准**：Foreman 可直接覆盖 verify gate 失败，ledger 有审计记录。

### [FIX-31] Write-set 冲突详情输出

**优先级**：P2
**影响维度**：体验
**预期分数变化**：体验 +0.25

**触发实例**：
> v11 Foreman 反馈："Ralph suggest 输出 claimed_paths_conflict:batch 但不说明是与哪个任务冲突。"

**验收标准**：suggest 输出含冲突任务对和冲突文件。

### 综合评价

v11 是 CCCC 工作流的首次真实项目实战。17 个 task 的 Flutter 增强项目在 25 分钟内完成，所有工作流机制（validate → suggest → submit → auto-dispatch → DAG gating → verify gate → sync-state）端到端运行正常。

**核心成就**：
- 16/16 实现任务 worker 代码首次正确（零代码 bug 需 retry）
- DAG 门控 + write-set 冲突序列化完美运行
- Plan 元数据 100% 传递到运行时
- 所有失败显式暴露，无 silent fallback

**核心不足**：
- 3 个 CRITICAL bug 逃逸出 verification gate（grep-level 检查无法发现 timing/state bug）
- Verification 命令未预检导致最大时间浪费
- Assignment 决策链不够结构化

**结论**：工作流系统在真实项目上证明了协调和执行能力，但验证能力仍有提升空间 — 从"验证代码存在"进化到"验证行为正确"是下一个里程碑。
