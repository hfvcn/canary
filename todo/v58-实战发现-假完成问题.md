### 问题 1 追查：AF 引擎为什么还是 legacy

**代码追踪**：
- `workflow_orchestrator.py:240-247`：`_af_engine_enabled()` 检查 env var → 返回 True

出口 3 (line 178-180): pre-dispatch fail → return False (WARNING log)

## v59 — Ralph validate 检测能力缺口（step-3 Codex review 暴露）

> 以下为 Codex 能沿调用链识别、而 `ralph validate` 当前无法检测的系统性缺口。
> 这些是缺失的 validate 规则 / 未检查的不变量，归档前需补成 detection rule。
>
> step-3 Codex review 摘录："FC-1 和 FC-4 现在最容易再次出现'测试全过但真实行为不变'的
> 假完成；FC-3 次之；FC-2 本质上只是回归锁，不是 Layer-6 行为修复；FC-5 方向对，但必须
> 卡在顶层检查结果上。" —— 这些都是 validate 当前 detect 不到、需补成 check/rule 的盲区。

#### DG-1: validate 无法检测"修复落在非活跃执行路径"（active-path reachability）

Codex 沿调用链判定 FC-1 改的 `_acquire_auto_agent()`（agent_pool.py:253-272）只在 AF
路径触发，而 v58 实际跑的是 legacy 主链（`process_batch_suggestion → assign_tasks →
create_or_reuse_agent → create_agent_for_task`，runtime 取自 `model.runtime`）。
`ralph validate` 只检查 claimed_paths 是否被测试 cover，**不验证被修改的 symbol 是否在
当前活跃执行路径上可达**（legacy vs AF 双引擎）。

缺失规则：active-path reachability check —— 对声称"修复运行时行为"的 task，验证其
claimed symbol 从当前默认 entrypoint（含引擎分支选择）有真实 call-chain 可达，否则
warning（fix-on-dormant-path）。这是"假完成"Layer-4→Layer-6 跃迁的核心盲区。

#### DG-2: validate 无法检测"跨并行路径的默认值漂移"（default drift across paths）

同一语义兜底默认值 `model_runtime or "claude"` 同时硬编码在 agent_pool.py:268 和
assignment_actor_registration.py:41-45 两处；只改一处会留漏网点。`ralph validate` 无规则
检测**同语义常量/默认值在多条并行代码路径中的一致性**。

缺失规则：semantic-default consistency check —— 识别同类默认值（runtime/model 兜底）的
多点定义，task 修改其一时提示其余同语义点（default-value-drift）。

#### DG-3: validate 无法检测"静默降级分支无可观测信号"（silent-degradation-without-signal）

`try_af_execution` 三个 fallback 出口与 `_should_run_af_execution()==False` 分支均静默
回退 legacy，仅 debug 日志、无 event/ERROR。`ralph validate` 无规则要求**降级 / fallback /
except-swallow 分支必须发出可观测信号**（事件或 ≥WARNING 日志）。

缺失规则：observable-fallback check —— 对带 fallback/return-False/except-pass 的执行
路径，要求存在对应的 ledger event 或 warning 级日志，否则 warning（silent-fallback）。

#### DG-4: validate 无法检测"守卫置于被守卫副作用下游"（guard-after-effect ordering）

FC-4 的 `_check_section_substantive` 若放在 `emit_workflow_terminal()`（先于
`_write_workflow_evaluation` 执行）之后，则 `workflow.completed` 已发出，门形同虚设。
`ralph validate` 无规则验证**gate/check 必须排在其所要守卫的副作用之前**。

缺失规则：guard-ordering check —— 当 task 声称"阻断 X"（block/gate/阻断），验证 check
调用点位于 X 的 emit/commit 副作用之前，否则 warning（guard-downstream-of-effect）。

- **更新 B5（真因，三层叠加）**：读端断 + 数据反 + 关键词命名空间不通。三层一起修才闭合：
  读端把 rating 纳入打分；数据让 codex strengths 覆盖执行 task type 且评 5.0、claude 收窄为
  审查/前端、清野生条目与禁用残留分。实测 `cccc model suggest backend → codex` 方算真生效。

### 仍未闭合（诚实标注，避免又一次假完成）

- foreman 若完全不走该流程、手动 `cccc actor add --runtime claude`，按用户要求不加闸门/
  不改 prompt，仍不强制——设计上接受，依赖流程被消费。
- AF `execute_bundle` 在真 daemon 下驱动真 worker 的端到端仍未验证（单测是合成完成）。
- codex 的 5.0 是把用户明示评价编码进去（sample_count=1），非真实样本累积。

### 误会模式分析（给检查机制——本节真正目的）

把上面每次误会并排看，形状高度一致：

1. **每次都"以为改了 X 就好"，每次都被真实路径实测推翻**（A1→A2、B1→B2→B4→B5）。
   规律：判断"是否完成"用的是**代码/单测/文档推断**，不是**真实主路径实跑证据**。
   → 检查机制应要求：声称"修复运行时行为"的交付，必须附真实路径产物（如 `cccc model
   suggest` 实际输出、`[af] execution done` 日志、E2E transcript），不接受"单测绿 + 代码在"。
2. **误会几乎都源于采信现成结论**（A1 信 line 164、B1 信 P0 表、B4 信"只是读端断"）。
   → 对 tracker/历史里的"不可用 / 条件不满足 / 只差一点"，应默认怀疑、独立追链验证
   （对应 DG-1 active-path reachability、DG-3 silent-fallback）。
3. **真因常是多层叠加**（B 是三层），只修第一层就交付 = 新的假完成。
   → "找到一个原因"≠"找全原因"；改完必须回到**最初症状**、用真实路径复测它是否真消失。
4. **"写了不读 / 命名空间不通"这类"组件齐全但链路断"反复出现**（评价闭环、AF 接线）。
   → 对应共性模式"函数存在≠被调用"，检查应验证从 entrypoint 到消费端的完整调用/数据链。

### 假完成层次自检（沿用本文档层次模型）

交付前逐条问：行为真改变了吗（Layer 6）、失败会阻断而非降级吗（Layer 7）、是否回到
最初症状用真实路径复测过？任一为否即未完成——FC-3/FC-1 当初都卡在这里却被标记完成。

### 最终结论：从检查机制出发

**采纳 Codex 视角：改检查机制是一次性投入、持续收益；改 Claude 认知是持续投入、
边际收益递减。** Claude 的认知错误每次不同（v53 没接主路径、v55 加标签、v56
compile 不 execute、v58 改可观测性），但检查机制的缺陷是同一个——**不验证
主路径行为是否真正改变**。改一个检查规则（DG-1 active-path reachability）
可以阻断所有这些不同的 Claude 认知错误。

**最终归因（按改进 ROI 排序）：**

| 因素 | 占比 | 角色 | 改进 ROI |
|------|------|------|----------|
| C. 检查机制 | 35-40% | 放大器——让单次错误跨 session 存活 | **最高**：一次性规则改进持续阻断同类逃逸 |
| B. Claude 认知 | 35-40% | 发动机——产生错误的理解和 plan | 中等：每次犯新错误，需持续约束 |
| A. plan.yaml | ~20% | 传导器——把认知错误编码为可执行指令 | 较低：是 B 的产物，B 改了 A 自然改善 |

### 检查机制改进优先级

按 ROI 从高到低：

1. **DG-1 active-path reachability**（最高优先）
   对声称"修复运行时行为"的 task，验证其 claimed symbol 从当前默认 entrypoint
   （含引擎分支选择）有真实 call-chain 可达。能阻断全部 AF 类假完成。

2. **suppress_codes 白名单化**
   禁止 suppress：`W_VERIFICATION_BEHAVIOR_MISMATCH`、
   `W_INTEGRATION_NO_PRODUCTION_CALL_EVIDENCE`、
   `W_INTEGRATION_TASK_SHALLOW_VERIFICATION`。
   这三个是假完成的最后防线，被 Claude 自己写的 plan 合法关闭。

3. **DG-3 observable-fallback**
   对带 fallback/return-False/except-pass 的执行路径，要求存在 ledger event
   或 ≥WARNING 日志。能阻断 AF 静默回退 legacy 的模式。

4. **verification 必须含行为证据命令**
   plan 的 verification command 不能只是 pytest，必须包含主路径产物检查
   （如 `cccc model suggest` 输出、daemon 日志中的引擎标记）。

5. **DG-2 semantic-default consistency**
   同语义默认值（如 `model_runtime or "claude"`）在多处定义时，
   修改其一需提示其余同语义点。

6. **DG-4 guard-ordering**
   声称"阻断 X"的 check 必须位于 X 的 emit/commit 副作用之前。

7. **归档行为证据定位化**
   `flow_improvement_check` 的归档不只认"行为确认"字样，
   还应要求引用具体证据文件或日志位置。

## 附录：现有检查机制完整描述（供外部分析）

> 本节描述 CCCC/Ralph 项目的全部检查层，供无法读取代码库的外部 AI
> 理解现有检查能力和盲区，以便给出改进建议。

### 系统架构概览

CCCC 是一个多 agent 协作框架，其中：
- **Foreman**（Claude Opus）是领导者，负责阅读需求、编写 plan.yaml、创建 worker、提交 workflow
- **Worker**（Codex 或 Claude）是执行者，按 plan 中的 task 编写代码和测试
- **Ralph** 是质量保障工具链，包含 validate（静态计划验证）、flow（流程状态机）、suggest（并行建议）

开发流程分两种：
1. **Solve Flow**（修复流程）：本地修复问题，6 步：理解→计划→Codex 评审→记录缺口→Codex 执行→生成 guide
2. **E2E Flow**（实战流程）：端到端 agent 协作测试，9 步（0-8）：代码基线→环境准备→任务提交→监控等待→Codex 评审→报告合成→清单更新→复盘→清理

### 检查层 1：plan.yaml 静态验证（`ralph validate`）

plan.yaml 是任务计划文件，定义 tasks（任务）、dependencies（依赖）、claimed_paths（声称修改的文件）、
verification（验证方式）、critical_flows（关键流程）、forbidden_flows（禁止流程）。
`ralph validate plan.yaml` 运行 150+ 条静态检查规则，分为以下类别：

#### 1.1 结构规则（structural.py，17 个 check 函数）

检查 plan 的图结构和字段完整性：

| 规则 | 检查内容 | 产出 code | 能检测 | **不能检测** |
|------|---------|-----------|--------|-------------|
| 图结构 | 重复 task ID、未知依赖、自依赖、依赖环、孤立任务 | E_DUPLICATE_TASK_ID / E_DEP_CYCLE 等 | 结构性死锁 | 语义依赖问题 |
| covers 图 | verification.covers 引用的 task 是否存在且顺序正确 | E_COVERS_UNKNOWN_TASK | 引用错误 | covers 是否真有意义 |
| 字段完整性 | claimed_paths / verification / acceptance_criteria 是否存在 | E_MISSING_CLAIMED_PATHS | 缺字段 | 字段内容质量 |
| 路径引用 | goal_behavior 中提到的文件是否在 claimed_paths 中 | W_CLAIMED_PATH_INCOMPLETE | 遗漏声明 | 路径是否真实存在 |
| 共享文件 | 多个 task 共享同一文件时是否有完整验证覆盖 | W_SHARED_FILE_PARTIAL_VERIFICATION | 覆盖缺口 | 验证是否真正执行共享文件的所有路径 |
| 集成脊柱 | 是否存在 integration role 的 task 来桥接跨边界依赖 | E_MISSING_INTEGRATION_SPINE | 缺少集成任务 | 集成任务是否真的验证了跨模块调用 |
| 角色约束 | integration/verification/leaf role 的约束是否满足 | W_LEAF_ROLE_IS_INTEGRATOR | 角色分配错误 | 角色分配是否语义正确 |
| 早期集成 | 集成检查点是否足够早 | W_NO_EARLY_INTEGRATION_CHECKPOINT | 集成过晚 | 检查点位置是否真正合理 |

#### 1.2 覆盖规则（coverage.py，40+ 个 check 函数，最大文件）

检查验证覆盖的深度和广度：

| 规则 | 检查内容 | 产出 code | 能检测 | **不能检测** |
|------|---------|-----------|--------|-------------|
| 验证强度 | 是否有跨 task 的 integration/e2e 验证 | E_NO_CROSS_TASK_VERIFICATION | 纯单元测试计划 | 跨 task 验证是否真正有意义 |
| 浅层验证 | integration task 是否只有 unit/compile 验证 | W_INTEGRATION_TASK_SHALLOW_VERIFICATION | 验证层级不匹配 | 浅层验证对特定 task 是否足够 |
| 集成声称证据 | integration 验证是否引用了 claimed_paths | W_INTEGRATION_CLAIM_EVIDENCE_MISSING | 缺少路径引用 | 引用是否对应真实测试覆盖 |
| **生产调用证据** | integration 测试中是否有生产代码的 import+调用证据 | W_INTEGRATION_NO_PRODUCTION_CALL_EVIDENCE | **缺少生产调用** | **只查 import 不查调用链可达性；不区分活跃/休眠路径** |
| 验证行为匹配 | 验证是否覆盖 claimed_paths 和 goal_behavior | W_VERIFICATION_BEHAVIOR_MISMATCH | 目标与验证不匹配 | 验证是否真正匹配行为意图 |
| 关键流程覆盖 | critical_flows 是否有足够的所有权和测试覆盖 | E_CRITICAL_FLOW_UNCOVERED | 关键流程无测试 | 覆盖是否语义有意义 |
| 禁止流程覆盖 | forbidden_flows 是否有拒绝测试 | E_FORBIDDEN_FLOW_UNCOVERED | 禁止流程无测试 | 拒绝测试是否真正有效 |
| 验收标准覆盖 | acceptance_criteria 关键词是否出现在验证命令中 | W_ACCEPTANCE_COVERAGE_GAP | 验收与验证脱节 | 关键词匹配 ≠ 实质覆盖 |
| 失败路径 | 是否至少有一个预期失败的 check | W_NO_FAILURE_PATH | 缺失失败测试 | 失败路径是否现实 |

**关键盲区**：`_check_integration_call_evidence`（coverage.py:312）是最接近检测"假完成"的规则——

#### 1.7 suppress_codes 抑制机制

plan.yaml 可以声明 `suppress_codes: [CODE1, CODE2, ...]` 来抑制特定 warning/error。
被抑制的 issue 从 error/warning 降级为 hint（不再阻断验证），消息前缀加 `[suppressed]`。

**不可抑制的 codes**（安全关键，无论是否在 suppress_codes 中都保持原始严重级别）：
`E_SECURITY_CRITICAL_FLOW_SUPPRESSED`、`W_REVIEWER_SIGNOFF_MISSING`、
`W_CRITICAL_FLOW_WORKER_ONLY_VERIFICATION`、`W_CRITICAL_FLOW_NO_INDEPENDENT_REVIEW`、
`W_AUTH_PRIVILEGED_ROLE_FIELD`、`W_AUTH_TYPE_CAST_UNGUARDED`、
`W_RBAC_WRITE_ENDPOINT_UNCOVERED`、`W_RBAC_FLOW_AUTH_UNVERIFIED`、
`W_SIGNOFF_STRUCTURE_WEAK`。

**关键问题**：以下三个 code 与假完成直接相关但**可以被 suppress**：
- `W_VERIFICATION_BEHAVIOR_MISMATCH`（目标说改行为，验证只跑单测）
- `W_INTEGRATION_NO_PRODUCTION_CALL_EVIDENCE`（集成 task 无生产调用证据）
- `W_INTEGRATION_TASK_SHALLOW_VERIFICATION`（集成 task 只有浅层验证）

当前的 plan.yaml 确实抑制了这三个 code（见 plan.yaml:47-91 的 suppress_codes 列表），
这是假完成能逃逸的直接通道。

### suppress_codes 治理缺陷

当前 suppress_codes 机制的核心问题：

1. **任何 warning 默认可抑制**——只有 11 个安全相关 code 不可抑制
2. **suppress_codes 由 Claude（plan 编写者）自行决定**——等于让被检查者自己关闭检查
3. **无过期/审批机制**——虽有 `suppress_instances` 的 `owner`/`expiry` 字段，但使用率为零
4. **与假完成直接相关的 3 个 code 全部可抑制**：
   - `W_VERIFICATION_BEHAVIOR_MISMATCH`
   - `W_INTEGRATION_NO_PRODUCTION_CALL_EVIDENCE`
   - `W_INTEGRATION_TASK_SHALLOW_VERIFICATION`

## 附录 B：工作流蓝图原始设想与现状差距

> 本节描述用户在 2026-04-04 定义的工作流蓝图（`todo/工作流蓝图.md`）核心思想，
> 以及与当前实现的差距。蓝图的验收分层设计包含了解决假完成问题的全部答案，
> 但中间层从未实现。**用户希望按照蓝图思路推进改进。**

### 蓝图核心思想：模块化并行 + 接口解耦 + 黑盒验收

#### 设计哲学

- Ralph 预期成为强大的审查监督系统，承认不完美，由 Agent 作为辅助和过渡
- 不因 Agent 强大而懈怠 Ralph 的改进——优先把 agent 处理的语义问题转为 Ralph 规则
- Codex 作为外部对抗审查，发现 Ralph+Agent 的不足，不在工作流内触发

#### 两阶段拆分模型

```
第一阶段：Ralph 任务拆分（已有能力）
  plan.yaml 草稿 → Ralph validate（150+ 规则） → Ralph suggest（依赖图+写冲突检测）
  → 输出可并行的 Task 批次

第二阶段：Foreman 模块化拆分（❌ 未实现）
  每个 Task → 拆为独立 Module → 统一模块间接口规范
  → Task 内模块使用模拟 I/O 并行执行，不等待依赖
```

#### Worker 黑盒模型

蓝图要求每个 Worker 是严格的黑盒：

```
输入：任务需求 + 接口规范 + 模拟输入数据
  → Agent 执行（内部过程不可见）
输出：一个完成的模块
  → 模块在给定输入下给出预期输出
  → 模块遵守规划时定义的接口规范

Worker 不知道：其他并行 Worker 的存在/进度、最终测试用例、全局上下文
```

#### 并行解耦机制（两层）

```
第一层：Task 间并行安全（Ralph 负责）——已实现
  - ralph suggest() 通过 claimed_paths 写冲突检测确保并行 Task 不写同一文件
  - 依赖图分析确保同批次 Task 无未满足依赖

第二层：Module 间并行安全（Foreman 负责）——❌ 未实现
  - 各 Worker 使用模拟输入独立开发，不等待依赖
  - 接口不匹配由 Ralph 在规划阶段约束（不应发生）
  - 万一发生 → 反馈 Foreman 处理
```

#### 蓝图的验收分层设计（层层递进）

```
模块级验收：给定输入 → 预期输出（Worker 黑盒验证，可自动化对照）
Task 级验收：模块拼接 → Task verify gate（接口匹配验证）
批次级验收：本批次全部 Task 通过 → 批次 E2E（集成验证）
全局级验收：所有批次完成 → 全流程 E2E → 交付
```

#### 执行阶段不变量（Engine 7 条 guard）

```
INV-1  NO_SILENT_APPROVAL       rejected→approved 必须经 Foreman 显式决策
INV-2  FOREMAN_OWNS_ASSIGNMENT   每个 assignment 溯源到 Foreman 的 AssignmentRecord
INV-3  CLEAN_RETRY               retry 后旧 assignment 必须清理
INV-4  NO_AUTO_DISPATCH          后续批次就绪时通知 Foreman，不自动分配
INV-5  ASSIGNMENT_PERSISTED      所有 assignment 在 Engine ledger，无影子状态
INV-6  NO_IMPLICIT_DECISION      Orchestrator 无未授权的 if-then 自动转换
INV-7  NO_COMPLETE_WITHOUT_FRESH_SELF_TEST  Worker complete 必须附带当次自测结果
```

#### 升级链

```
Worker 遇到问题 → Foreman 处理 → 委派 Codex 写代码 → Codex 也搞不定 → 标记人工处理
```

#### 改进闭环（工作流外）

每次完整实践后：Foreman 评估 Ralph 使用问题 → 追加到问题清单 →
优先改 Ralph 静态规则 → 尝试把 agent 语义问题转为规则 → 持续减少 agent 干预。

### 蓝图偏移现状（full tracker 记录）

| 设计要素 | 状态 | 说明 |
|---------|------|------|
| Task 间 DAG 调度 | ✅ 完成 | `ralph suggest` 能算并行批次 |
| 验证 ralph 模式 | ✅ 完成 | verify gate 跑 pytest/compile |
| 验证 agent 模式 (mock_tests) | ✅ BP-1 | mock_tests 结构存在 |
| Worker 黑盒模型 | ⚠️ BP-3 基础 | Worker 能接任务执行，但无接口规范+模拟 I/O |
| **Task 内模块化拆分** | **❌ BP-2** | **完全未实现** |
| **模块拼接 + 批次 E2E** | ⚠️ BP-5 部分 | 批次 E2E 有框架但模块拼接不存在 |
| **并行解耦第二层** | **❌ BP-4** | **完全未实现** |

### 差距的本质：缺了整个中间层

蓝图的并行提速逻辑是：

```
大任务 → 拆成独立模块 → 模块并行 → 拼接 → 验收
```

现实是：

```
大任务 → 直接交给 Worker 整体做 → 只跑 pytest
```

缺了"拆"和"拼接"两步，导致：

1. **子任务不够小**——Worker 拿到的是整个 Task（如"实现 auth 模块"），不是有明确
   接口的小模块（如"实现 login 函数，输入 `{username, password}`，输出 `{token, expiry}`"）
2. **没有接口规范约束**——并行 Worker 各自理解需求，拼接时接口不匹配只能靠人发现
3. **验收没有输入输出对照**——蓝图要求"模块在给定输入下给出预期输出"，
   现实只看"pytest 退出码 0"
4. **中间验证层完全缺失**——模块级、Task 级、批次级验收全部空白，
   只有最底层（pytest）和最顶层（人工 E2E 观察）

### 蓝图中间层与假完成问题的映射

蓝图缺失的中间层，恰好是假完成的逃逸通道：

| 假完成案例 | 蓝图中间层如何拦住 |
|-----------|------------------|
| AF 组件存在但未接入主路径 | **Task 级拼接验证**：AF 组件"拼接"到 orchestrator 时，`_af_pool_manager()` 读错对象会立即暴露——因为拼接后要跑接口匹配验证 |
| 模型选择只写不读 | **批次级 E2E**：第一个批次完成后，`cccc model suggest backend` 返回 None 而非 codex，会被批次 E2E 自动对比出来 |
| 复盘 check 只查关键词 | **模块级输入输出对照**：给定输入"复盘内容"→ 预期输出"含 8 个维度"，黑盒验证自动检查 |
| 代码兜底改了一处漏另一处 | **接口规范约束**：如果"默认 runtime"是一个声明了 provides 的接口，所有 consumes 端都会被检查 |
| suppress_codes 绕过检查 | **批次级 E2E 独立于 plan**：即使 plan suppress 了 warning，批次 E2E 的行为断言不受 suppress 控制 |

### AgentFlow 整合架构（2026-05-24，补充设计）

在蓝图基础上，后续增加了 AgentFlow（AF）整合设计，将执行调度从 CCCC 自研
迁移到 AF 框架：

```
层                    Owner                 职责
Plan & Validation     CCCC Ralph            plan 生成、静态验证、discipline、DAG 依赖
Strategy & Policy     CCCC Foreman          角色/模型决策、actor lease、审批
DAG Scheduling        AgentFlow Orchestrator 依赖满足、ready frontier、并发控制、retry
Execution Transport   CCCCActorRunner       持久 actor 会话投递、terminal event 等待
Verification          CCCC VerificationGate  最终验收权威（Ralph checks + security）
Trace & Evaluation    AF RunStore + CCCC    trace 收集、评分聚合、agent 进化
```

分配权两段 gate：AF 判断 node 是否 ready → CCCC AgentPoolManager.acquire() 判断是否有 actor lease。
最终完成权：AF `node_completed` = 执行完成；CCCC verification passed = 任务完成。

AF 整合的现状：接线 bug 修复后（v59）AF 引擎首次真正执行，但暴露了
`auto_complete_after_send=True`（fire-and-forget）的设计级问题（AF-07），
导致 override→dispatch→fail 死循环。AF 整合仍未真正闭合。
