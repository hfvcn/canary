## 〇、起因

### 用户提出的问题

> 在最近一段时间，先是完成了 Ralph 这个用于规范计划生成、并行化拆分、工作流监督的基础系统，然后开启了"优化 Ralph → 优化主项目 → 将优化过程中发现的 Ralph 漏洞更新"的循环。现在主项目也能正常跑通，后续优化效果还算不错。
>
> 但是在今天停下来进行检查之后，发现项目发生了跑偏的情况。事实上 Ralph 本身的设计就是在一定程度上通过这个系统减少执行的跑偏，所以这次跑偏以及检查出来的问题是十分宝贵的。
>
> 我们必须重新检查整个项目，规划后面的优化路径，并尽可能的把 findings.md 里的教训纳入 Ralph 的监督之中。至于要怎么做，你可以持续和 Codex 讨论，给出一个双方都无异议的方案。

### 遇到了什么问题

项目在 v1→v4 的四轮 E2E 实战迭代中，评分从 1.8/5 稳步涨到 3.3/5，形成了一个看似健康的循环：优化 Ralph → 用 Ralph 推动主项目修复 → 把过程中发现的 Ralph 漏洞回写。每一轮的即时反馈都不错——计划更完整了、validate 通过了、测试数量越来越多、问题清单不断推进。

但停下来从设计边界反向检查后，发现**分数的提升部分靠的是系统偷偷替 Foreman 做决策**——三次渐进偏移把"匹配失败应暴露"悄悄改成了"系统自动兜底"，把 rejected 静默改成 approved，把后续批次绕过 Foreman 直接自动分配。更严重的是，这些偏移被写进了文档作为"目标架构"，偏移本身被固化了。

同时发现 20 条 findings 虽然写下来了，但并没有真正约束执行——AI 更常见的模式是先犯错、复盘时说"这印证了某条 finding"。教训文档退化成了事后解释库，而不是事前约束库。

这是 Finding #18（连续正反馈制造虚假繁荣）的典型表现：同一套方法同时负责推进、验收、解释结果，缺少独立的逆向检查，局部改进共同制造了"进展很多"的错觉。

### 这个方案是怎么来的

1. **Claude 全面诊断**：读取 findings.md、问题清单、设计偏移记录、E2E 评估报告、Ralph 改进清单，分析项目现状
2. **Claude-Codex 第一轮讨论**：Claude 提出初始方案，Codex 进行对抗式审查，指出顺序反了（编译期规则先于运行时修复 = 安全剧场）、缺少运行时监控层、测试编码了偏移、评分标准与正确性矛盾，并识别出两个上位矛盾
3. **Claude-Codex 第二轮讨论**：带用户反馈回到 Codex，对 6 个分歧点逐一达成共识
4. **4 份独立审查**（gedt / gp / gpp / groh）+ 代码核实（Claude Sonnet + Codex）：6 条核心代码声明全部确认，8 条 A 类发现全部采纳，16 条 B 类发现采纳 13 条、延后 3 条
5. **方案修订**：基于审查结果修订 Phase 结构、监控器架构、ARCH 优先级、不变量数量、Option Z 设计

### 本文档的目的

本文档是上述过程的最终产出，回答三个问题：
1. 项目现在在哪里（现状诊断）

## 一、项目背景

### 1.1 CCCC 是什么

CCCC（Claude-Codex-Claude-Collaboration）是一个工作流编排系统，让多个 AI agent 协作完成软件工程任务。

核心架构是三层：

```
用户（提需求、配置模型、干预）
  │
  ▼
Foreman AI（规划者 + 决策者）
  │  ralph validate   → 结构校验计划
  │  ralph suggest    → 计算可并行批次
  │  cccc workflow submit → 提交任务 + 指定分配 + 下发 Policy
  ▼
CCCC Daemon（执行引擎 + 状态管理，无业务决策）
  ├── WorkflowOrchestrator → 执行 Foreman 的决策
  ├── WorkflowEngine       → 状态机（唯一权威）+ pre-transition 不变量守卫
  ├── Ralph (daemon 内)    → verify gate + 运行时监控
  │
  ▼
Worker AI（执行者，可以是 Claude/Codex/Gemini 等）
  │  cccc task complete → 报告完成 → 触发 verify gate
```

### 1.2 Ralph 是什么

Ralph 是计划校验器 + 任务调度器 + 执行时验收器，有两个存在形式：

**独立 CLI 工具**（脱离 daemon 使用）：
- `ralph validate plan.yaml` — 40+ 条结构性校验规则（依赖图、字段完整性、契约匹配、关键流覆盖等）
- `ralph suggest plan.yaml` — 基于依赖图 + 写集冲突检测计算可并行批次（两阶段拆分的第一阶段）
- `ralph verify plan.yaml --task T1` — 执行验收命令

**daemon 内组件**：
- `RalphService` — 观察层，执行 git 操作和验收命令
- `WorkflowMonitor` — 运行时告警层（当前是纯函数 + warn-only，尚未接入 Engine）
- verify gate — 任务完成后立即验收，不合格驳回

**Ralph Agent 层**（v5.2 新增，蓝图 v0.3）：
- Gemini CLI Flash 模型，每个 workflow 一个实例，可脱离 workflow 独立启动
- 只审查 Ralph 标记为"超出结构校验范围"的部分（基于静态的"超出范围检查项清单"）
- 不读代码，基于 Ralph 输出 + plan 文本做语义判断
- 结果标注为"agent 建议，仅供参考"，无决策权，只能标记 + 转交 Foreman
- 默认启用，可关闭（`--no-agent` 退回纯静态模式）
- 运行时验证：对 `verification_mode: agent` 的任务执行 Foreman 预设的模拟测试用例
- 验证重试上限 2 次，超过升级 Foreman

### 1.3 经验证的工作流程（v5.2 更新为两阶段拆分）

```
Foreman 生成 plan.yaml
  → 第一阶段：Ralph 任务拆分 (validate + suggest + Ralph Agent 审查)
  → 第二阶段：Foreman 模块化拆分 (Task 内拆 Module, 统一接口规范)
  → 分批次执行 (Ralph suggest 控制批次, Module 并行)
  → 验证 (ralph 模式 / agent 模式分流)
  → 全流程 E2E
```

关键约束：
- 计划必须经过 Ralph validate（结构保障）+ Ralph Agent（语义补强）才能执行
- Ralph 负责 Task 层面的并行安全（依赖分析 + 写冲突检测 + 优先级排序）
- Foreman 负责 Module 层面的解耦（统一接口规范 + 模拟 I/O）
- Codex 作为外部对抗审查，不在工作流内触发，发现 Ralph+Agent 的不足
- 验证模式由 Foreman 在 plan.yaml 中声明：`verification_mode: ralph|agent`

### 2.3 发现的设计偏移（核心问题）

v4 实战后的代码调查 + 文档对比 + 会话溯源，发现系统在迭代中发生了渐进式设计偏移：

**设计意图**：Foreman 是唯一决策者，orchestrator 只执行 Foreman 的决策，失败应显式暴露给 Foreman。

**实际行为**：orchestrator 会自动创建 worker、静默把 rejected 改成 approved、后续批次绕过 Foreman 直接分配。

#### 偏移时间线

| 阶段 | 事件 | 性质 |
|------|------|------|
| 03-26~28 | 讨论聚焦数据模型，没有定义"谁创建 worker""无匹配时怎么处理" | 设计未明确 |
| 03-29 | agent pool 匹配失败 → 加了 `_fallback_to_group_actors()` | **第一次关键偏移** |
| 03-30 | ralph-foreman-workflow.md 把 fallback 写成"目标架构" | 偏移被固化进文档 |
| 04-01 | E-2 能力扩展"模型注册表驱动分配"进一步耦合 | 偏移加深 |
| 04-03 | v4 实战 FIX-14 讨论，发现 batch 2-3 引擎自动创建 worker 才是异常 | **偏移被发现** |

#### 偏移的深层根因

| 深层根因 | 表现 |
|---------|------|
| **负向不变量缺失** | 系统有"应该怎么做"的正向流程，几乎没有"绝不能自动做什么"的硬约束 |
| **失败暴露通道缺失** | 无匹配时缺少"向 Foreman 发结构化失败消息并等待"的路径；直接 fallback 更容易实现 |
| **成功判据偏向"先跑通"** | 成功信号是"E2E 通过、batch approved"，不是"决策权仍在 Foreman" |
| **命名有误导性** | `create_or_reuse_agent()`、`created_by="foreman"` 混淆了系统代执行和 Foreman 显式决策 |
| **实现反向塑造文档** | 文档重写总结当前可运行实现，而非回到原意校准实现 |
| **AI 天然偏向最短闭环** | 在意图未形式化时，AI 自然朝"最少报错、最快通过 E2E"收敛 |

#### ARCH 系列问题清单

| 编号 | 问题 | 代码位置 | 严重度 | 修复 Phase |
|------|------|---------|--------|-----------|
| ARCH-1 | `workflow submit` 无 assignment 字段 | `ralph_ipc.py:TaskRef`（extra="ignore" 丢弃额外字段） | P0 | Phase 2 |
| ARCH-2 | `_fallback_to_group_actors()` 静默把 rejected 改为 approved | `workflow_orchestrator.py:397` | P0 | Phase 2 |
| ARCH-3 | `_resuggest_ready_tasks()` 后续批次自动分配（`auto_start_agents=True`） | `workflow_orchestrator.py:1147` | P1 | Phase 4 |
| ARCH-4 | Engine 只存 `agent_id`，缺完整 assignment provenance；`_active_workflows` 影子状态 | `workflow_state_types.py:40`，`orchestrator:181` | P1 | Phase 2（最小）→ Phase 4（完整） |

## 三、实践教训（Findings）

项目积累了 20 条根本性教训。以下按与本方案的相关性分组。

### 3.1 关于验证和集成的教训

| # | 教训 | 核心要点 |
|---|------|---------|
| 1 | 编译通过不等于功能可用 | 验证最低标准应是"从入口到出口路径能走通" |
| 2 | 按文件拆任务会产生精致的死代码 | 正确单元是"可独立验证的功能切片"，不是文件 |
| 6 | 验证基础设施应先于功能开发 | 先有端到端验证命令，再以"能通过"为验收标准 |
| 7 | 代码审查发现逻辑错误，发现不了集成缺失 | "代码对不对"和"代码有没有被用到"是两个问题 |
| 9 | 先跑通一条路径，再扩展功能 | 一个能跑的最小闭环 > 十个不相连的完整模块 |
| 13 | 结构性校验通过不等于计划无缺陷 | Ralph（结构校验）和 Codex（代码审查）互补，不能互替 |

### 3.2 关于设计边界和失败处理的教训

| # | 教训 | 核心要点 |
|---|------|---------|
| 5 | 用户一开始就说了正确答案 | 用户基于实际经验的架构判断应作为约束条件，不是"一个优化建议" |
| 14 | 问题可能不在项目内部 | 当内部修复反复不生效时，退一步问行为是否由外部配置决定 |
| 15 | 改了一半的迁移比没改更危险 | 迁移必须覆盖完整生命周期，没有充分证据不要归因到更深层面 |
| 16 | 只有正向流程不够，关键边界必须写成负向不变量 | "系统绝不能自动做什么"比"系统应该怎么做"更重要 |
| 17 | 失败不能显式抛回决策者，系统会自然滑向 silent fallback | 失败处理是架构一等公民，不是补充逻辑 |

### 3.3 关于工作方法本身的元教训（最关键）

| # | 教训 | 核心要点 |
|---|------|---------|
| 11 | 对规划 AI 要求过高 + 验收机制不足 | Ralph 应逐步引导计划到合规状态，不是指望一步到位 |
| 12 | 长上下文下 AI 陷入局部最优，丢失全局视角 | 遇到"新问题"时先回查原计划——可能只是还没做到的部分 |
| 18 | 连续正反馈制造虚假繁荣 | 同一套方法同时负责推进、验收、解释结果 = 没有真正的检查 |
| 19 | Findings 不会自动约束 AI | 教训文档只有在被主动对照时才有约束力，否则退化成事后解释 |
| 20 | 问题清单驱动执行会压制上位矛盾识别 | 清单是执行工具不是思考替代品，必须定期中断检查问题定义本身 |

### 3.4 Findings 的核心困境与解法

**当前困境**：20 条 findings 存在于 `findings.md`，但 AI 在执行中不会主动检查，退化成事后解释库。

**v5.1 解法**：findings 升级为计划 YAML 的结构化字段，由 Ralph 校验。详见 Phase 3。

## 四、目标架构（修正后的设计意图）

### 4.1 职责分离（v5.2 更新：两阶段拆分 + Ralph Agent）

```
┌──────────────────────────────────────────────────────────┐
│ Foreman AI（唯一决策者）                                  │
│                                                          │
│  决策范围：                                               │
│  • 生成 plan.yaml（按功能分 Task，声明依赖和写范围）       │
│  • 第二阶段拆分：Task 内模块化拆分（统一接口规范）         │
│  • 选择哪个 actor 执行哪个任务（workflow submit 时指定）   │
│  • 创建持久化 actor（cccc actor add --worker-prompt）     │
│  • 收到"无合适 agent"时决定如何处理（Policy 范围内）      │
│  • 收到"后续任务已就绪"时决定下一批分配 + 模块化拆分      │
│  • 提交 RetryPolicy（max_retries, timeout_mins）          │
│  • 声明每个 Task 的 verification_mode: ralph|agent        │
│  • 模块拼接 + E2E 验证                                    │
└──────────────┬───────────────────────────────────────────┘
               │ AssignmentRecord[] + RetryPolicy
               ▼
┌──────────────────────────────────────────────────────────┐
│ CCCC Daemon（纯执行 + 状态管理，无业务决策）               │
│                                                          │
│  WorkflowEngine（状态机 + 不变量守卫）：                   │
│  • 所有状态转换入口内置 pre-transition guard              │
│  • 违规时直接 TransitionRejected，不写入任何副作用         │
│  • AssignmentRecord 持久化在 Engine（权威唯一来源）        │
│                                                          │
│  WorkflowOrchestrator（执行驱动，无决策）：                │
│  • 接收 Foreman 提交（已含 AssignmentRecord）             │
│  • 按 Engine 状态执行转换，不含 if-then 自动决策           │
│  • 无合适 actor → BatchAssignmentFailed → Foreman inbox  │
│  • 后续批次就绪 → TasksReadyForAssignment → Foreman inbox │
│  • 不创建 worker，不做静默 fallback，不自动兜底            │
│                                                          │
│  WorkflowMonitor（告警/审计，事后）：                     │
│  • 事后审计违规，输出 violation ledger                    │
│  • 不做控制面决策                                         │
│                                                          │
│  Ralph (daemon 内)：                                      │
│  • 第一阶段拆分：validate + suggest（任务拆分与并行调度）  │
│  •   依赖分析 + 写冲突检测 + _unlock_score 优先级排序     │
│  •   输出可并行执行的 Task 批次                            │
│  • verify gate（任务完成 → 验收 → 通过/驳回）             │
│  • stall detection（超时检测）                             │
│  • 标记"超出结构校验范围"的项目 → 转交 Ralph Agent        │
│                                                          │
│  Ralph Agent (Gemini Flash, 可选)：                       │
│  • 语义审查 Ralph 标记的超出范围项                         │
│  • 运行时验证：执行 verification_mode:agent 的模拟测试     │
│  • 不读代码，结果标注"仅供参考"                           │
│  • 无决策权，只能标记 + 转交 Foreman                      │
└──────────────────────────────────────────────────────────┘
```

**两阶段拆分执行流程**：
```
Foreman 生成 plan.yaml (Task 级, 含 depends_on + claimed_paths)
  → Ralph validate (40+ 结构规则) + suggest (并行批次计算)
  → Ralph Agent 审查超出范围项
  → 不通过 → Foreman 修改 → 重新验证
  → 通过 → 输出 Batch 1: [T1, T2], Batch 2: [T3], ...
    → 对每个 Batch:
      → Foreman 对每个 Task 做模块化拆分 (统一接口规范)
      → Module 并行执行 (模拟 I/O)
      → 模块拼接 → Task verify gate
      → 批次 E2E
      → Ralph suggest 下一批
```

### 4.3 AssignmentRecord 结构

Foreman 在 `workflow submit` 时下发，Engine 持久化在 ledger 事件中，是 INV-2 的可验证基础：

```python
@dataclass
class AssignmentRecord:
    task_id: str
    actor_id: str
    decision_id: str           # Foreman 决策事件 ID，用于溯源
    decided_by: str            # "foreman" | "user"
    decision_reason: str       # 人类可读的分配理由
    constraint_snapshot: dict  # 分配时的约束集（模型能力要求等）
    assigned_at: str           # ISO 8601 时间戳
    assignment_attempt_id: str # 本次分配的唯一 ID，用于 CAS 去重
```

### 4.4 Option Z 重试协议（Foreman Policy 模式）

当无合适 agent 时（或其他需要 Foreman 决策的失败场景），系统发结构化消息给 Foreman AI，Foreman 自行决策。系统只执行 Foreman 的决策，并在 Policy 边界内终止：

**Foreman 提交时附带 RetryPolicy**：
```yaml
retry_policy:
  max_retries: 2           # Foreman 授权的最大重试次数
  timeout_mins: 10         # Foreman 授权的最长等待时间
  # Daemon 保留物理极值兜底：30min 全局 SLA timeout，超时转 BLOCKED
```

**失败时系统发给 Foreman 的消息格式**：
```
任务 T 无合适 agent（已尝试 N 次，剩余配额 M 次）。
约束集：{...}
你可以：
  (a) 放宽约束并重新 submit（请附新 AssignmentRecord）
  (b) 通过 cccc actor add 创建新 actor，再重新 submit
  (c) 标记任务为 BLOCKED（其下游任务将被级联取消）
```

Foreman AI 以结构化动作回复。Daemon 不在这三个选项之外做任何自主判断。

**动态任务拆分约束**：若 Foreman 选择拆分任务（非以上三选项的扩展），新子图必须在接受前同步调用 Ralph API 完成内联校验，校验通过才进入 Engine。

**BLOCKED 的 DAG 级联规则**：任务进入 BLOCKED 时，Orchestrator 向所有并行 sibling 任务发取消信号；workflow 级 TTL 触发时整体 BLOCKED + 通知用户；BLOCKED 任务可通过 `cccc workflow unblock <task_id>` 显式解封。

### 4.5 Agent Pool 定位修正

**Agent Pool 是模型能力信息库，不是自动分配引擎。**

| 职责 | 归属 |
|------|------|
| 存储模型能力描述（擅长/不擅长/context window）| Agent Pool |
| 存储 Foreman 实践评估 | Agent Pool |
| 决定用哪个模型创建 worker | **Foreman** |
| 创建持久化 actor | **Foreman**（通过 cccc actor add） |
| 无合适 agent 时自动 fallback | **❌ 不应发生** |
| 自动创建泛型 worker | **❌ 不应发生** |

### Phase 1：运行时监控层

**上下文锚点**：Ralph 当前只在编译期工作。ARCH 系列问题全是运行时行为。这个 Phase 补上缺失的运行时不变量断言层。

**关键架构决策（审查确认）**：
1. **监控器必须是 Engine pre-transition guard，不是 Orchestrator 事后调用**。当前 `workflow_monitor.py` 是纯函数 + warn-only，被 Orchestrator 在 `on_task_completed()` 等处事后调用，状态已写入后再检查无法回滚。正确做法：6 个不变量断言直接嵌入 `WorkflowEngine` 的状态转换入口（`approve_batch`、`report_worker_started`、`report_worker_completion` 等），违规时返回 `TransitionRejected`，不产生任何副作用。
2. **必须先 Observe-only，不能立即阻断**。当前系统依赖 `_fallback_to_group_actors`（ARCH-2）和 `_resuggest_ready_tasks`（ARCH-3）才能完成 E2E。如果 Phase 1 立即部署阻断模式，系统无法跑通任何工作流，Phase 2 的修复无法被验证。

**三档 rollout 语义**：

| 档位 | 行为 | 切换条件 | 恢复命令 |
|------|------|---------|---------|
| `observe` | 记录 violation ledger，不阻断 | Phase 1 部署时 | — |
| `warn` | 记录 + 结构化警告到 Foreman inbox | 人工切换，用于过渡期 | — |
| `block` | 拒绝状态转换（TransitionRejected），workflow 进入 SAFE_PAUSE | ARCH 修复完成后逐条切换 | `cccc workflow resume <id>` |

**不变量声明**：*Phase 1 完成后，6 个不变量以 observe 模式在 Engine 入口运行，系统开始记录 violation ledger，建立偏移基线。Phase 1 结束时应能看到 INV-1、INV-4、INV-6 有大量违规记录（因为偏移代码还在）。*

| 编号 | 任务 | 具体内容 | 验收 |
|------|------|---------|------|
| P1-A | 实现 Engine pre-transition guard | 在 `WorkflowEngine` 状态转换入口实现 6 条不变量检查，初始模式 observe | 6 个 guard 存在，不阻断，记录 violation |
| P1-B | 定义三档 rollout | 实现 observe/warn/block 切换机制 + 恢复命令 `cccc workflow resume` | 切换命令可用 |
| P1-C | Finding 衍生行为检查 | Finding #17 → 检测失败被静默吞掉；Finding #15 → 检测新旧路径同时活跃 | 行为检查运行 |

## 七、上位矛盾与长期方向

### 7.1 Orchestrator 应该是纯状态机（已有硬触发条件）

**矛盾**：当前 Orchestrator 同时包含执行逻辑和业务决策逻辑。Phase 2/4 移除了最明显的决策，但 Orchestrator 中可能仍残留隐式决策。

**触发条件**（满足任一即立项启动重构，见 P4-F）：
1. Phase 4 后仍有任一 invariant 违规源于 Orchestrator 内部 if-then 分支
2. 新功能需同时改 Orchestrator/Monitor/Engine 三处才能维持决策边界
3. assignment/retry/readiness 三类事件仍有一类无法只靠 Engine 权威还原

### 7.2 静态计划验证 vs 动态执行现实（v5.2 部分化解）

**矛盾**：Ralph 在计划提交时验证，但执行是动态的。

**v5.2 化解方案**：两阶段拆分模型让 Ralph 重新参与运行时——每个批次完成后 Ralph `suggest()` 动态计算下一批可并行 Task，而不是一次性静态规划所有执行顺序。Ralph Agent 在运行时验证阶段也提供语义判断。Phase 5 的 `reverse-check` 作为离线审计兜底——工作流完成后，对比计划声明的不变量与执行日志。

### 7.3 Liveness 缺口（已识别，延后设计）

当前 6 条不变量全是 safety 类（禁止某些行为）。缺少 liveness 维度（保证某些行为最终发生）：
- `EVENTUAL_VISIBILITY`：每个 task 必须在 SLA 内进入 done/failed/blocked，带明确 owner
- `BOUNDED_ESCALATION`：无 actor/Foreman 不响应/verify 超时等情况必须在边界时间内升级

这是真实缺口，但 SLA 参数和升级路径设计需要专项讨论，不在当前 Phase 范围内。
