## 一、结果指标（2/5）

**审查者**：Codex（对抗式代码审查，read-only sandbox）

### CRITICAL

1. **[frontend/src/api.ts:44 + NoteDetail.tsx:53 + backend/routers/tags.py:12] 标签接口前后端契约不一致**
   - 后端 `POST /notes/{id}/tags` 返回 `NoteResponse`，前端按 `Tag` 处理并塞进 `note.tags`
   - 复现：详情页新增标签后，数组混入 note 对象，`TagBadge` 读取 `tag.name` 得到 `undefined`
   - 删除时把 `note.id` 当 `tagId` 发送，**标签主流程直接坏掉**
   - 影响：critical_flow `tag_management` 不可用

### WARN

2. **[schemas.py:23,45] 空标题绕过** — `NoteCreate(title='<script>alert(1)</script>')` 先通过非空检查再被清洗成空串
3. **[schemas.py:7,11] XSS 过滤表面** — `data:` URI、事件属性 `<img onerror=...>`、编码变体 `java&#x73;cript:` 均可通过。当前前端无 sink，但 API 会持久化危险 payload
4. **[main.py:11 + conftest.py:43] 测试被 lifespan 污染** — `pytest` 实际结果 4 passed / 22 errors，app lifespan 触发生产 engine 无视 override
5. **[notes.py:36] PUT 无并发保护** — 静默覆盖，编辑场景丢数据
6. **[models.py:25 + tags.py:48] 孤儿标签永久保留** — `/tags` 返回 `note_count=0` 脏数据

### OK

- SQL injection：ORM 参数绑定，安全
- Foreign key constraints：PRAGMA per-connection 正确
- Frontend XSS sinks：无 dangerouslySetInnerHTML，无动态 href

## 六、根因定位

### 已解决（代码已修复但 v17 未充分验证）
- **RO-38** structural digest 排除 state 字段 — 代码正确但本轮未触发场景
- **RO-37** challenge mode 三层实现 — 代码正确且已运行，但暴露了假阳性问题

### 未解决
- **RO-39** manual completion auto-advance — 可能被 verify gate cwd bug 掩盖，需修复 cwd 后重新验证

### 新发现
- **RO-41** verify gate 在 daemon cwd 而非项目根目录执行 `ralph verify`
  - 根因：RalphService.verify_completion() 未传递 project_root 给 ralph verify 调用
  - 影响：所有验证直接 FileNotFoundError，P0 级
- **RO-42** challenge verification 假阳性
  - 根因：Agent 对抗审查做纯静态分析，不执行代码，对实际存在的验证逻辑误判为"未实现"
  - 影响：正确代码被连续拒绝 3 次，浪费 ~5 分钟
- **RO-43** auto-dispatch 状态丢失
  - 根因：task 失败/重试后 assignment_batches 的 DAG 状态未恢复
  - 影响：首次 auto-dispatch 后所有后续自动化失效

## 七、后续改进及对应实例

### [RO-41] verify gate cwd 修复

**优先级**：P0
**影响维度**：过程 + 体验
**预期分数变化**：过程 2→3, 体验 3→4

**触发实例**：
> v17 实战中，T1 completion 触发 verify gate，但 `ralph verify` 在 `~/.cccc/` 目录执行，报 `[Errno 2] No such file or directory: 'plan.yaml'`。4 次验证全部因此失败。

**根因**：RalphService.verify_completion() 调用 ralph verify 时未设置 cwd 或传递 `--project-root`

**改进方案**：在 verify_completion() 中使用 scope_key 对应的项目根目录作为 cwd

**验收标准**：下一轮实战中，verify gate 能找到 plan.yaml 并执行真实验证

### [RO-42] challenge verification 降低假阳性

**优先级**：P1
**影响维度**：过程 + 体验
**预期分数变化**：过程 +0.5, 体验 +0.5

**触发实例**：
> v17 T1：challenge verifier 声称"Empty titles not rejected"，实际 schemas.py:24 有 field_validator；声称"Script tags not sanitized"，实际 schemas.py:8 有 re.sub。3 次假阳性导致 T1 最终 failed。

**根因**：challenge verifier 做纯 LLM 静态分析而非代码执行验证

**改进方案**：
1. challenge 模式先执行 worker 的 verification.checks（compile + test），只有全部通过后才启动 Agent 对抗审查
2. Agent 审查时传入 checks 执行结果作为上下文，减少误判
3. 考虑让 Agent 审查可以执行简单的反例测试脚本

**验收标准**：challenge verifier 不再对已通过 compile+test 的代码产生"功能未实现"的假阳性

### [RO-43] auto-dispatch 故障恢复

**优先级**：P1
**影响维度**：过程 + 体验
**预期分数变化**：过程 +1, 体验 +0.5

**触发实例**：
> v17 T1 首次 auto-dispatch 成功，但 T1 失败/重试后 auto-dispatch 丢失状态。T2-T5 全部需要 Foreman 手工 `cccc send`。

**根因**：task 失败后 assignment_batches 的 DAG 状态未恢复到可重调度状态

**改进方案**：task retry 后保留 auto-dispatch 配置，retry 成功后继续执行 _resuggest_ready_tasks()

**验收标准**：task 失败/重试后，auto-dispatch 继续工作，下游任务自动推进

## 八、综合评分：2.3/5

v17 相比 v16 **退步**（3.0→2.3），主要原因是 verify gate cwd bug（RO-41）这个新 P0 问题。该 bug 破坏了整个验证链路，导致 Foreman 被迫手工绕过所有工作流机制。

**积极面**：
- RO-37 challenge mode 首次在真实场景中运行，验证了三层架构（validate warning + engine auto-upgrade + Agent 审查）的可行性
- Worker 可靠性达到 100%（claude runtime vs v16 PTY 的 14%）
- ralph validate 迭代 5 次显著提升了计划质量

**消极面**：
- verify gate cwd bug 是致命的基础设施问题，单独拖垮了过程分
- challenge mode 假阳性使 T1 卡住 ~5 分钟
- 结果分退步到 2/5（标签 CRITICAL + 测试污染）
- RO-38/RO-39 未能充分验证

**下一步优先级**：
1. P0：修复 RO-41 verify gate cwd
2. P1：修复 RO-42 challenge 假阳性（先执行 checks 再 Agent 审查）
3. P1：修复 RO-43 auto-dispatch 故障恢复
4. 修复后启动 v18 验证
