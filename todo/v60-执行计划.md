# v60 执行计划：假完成问题系统性修复

> 基于 v58 假完成调查结论 + 四份外部建议（gedt-9/gedt-9-plan/gp-9/gpp-9）综合制定
> 核心策略：不试图让 AI 不犯错，而是用机制逼迫系统交出 Layer 6（真实行为改变）的证据

---

## M0：立即止血，冻结假完成归档入口

目标：阻止新的假完成继续进入 full tracker。

### 1. 重新定义"完成"状态

所有修复项必须标记为以下状态之一：

| 状态 | 含义 | 是否可归档 |
|------|------|----------|
| implemented | 代码已写、测试通过 | 不可归档 |
| path-connected | 主路径已调用，有 call-chain 证据 | 不可单独归档 |
| runtime-ready | 运行时条件满足，真实执行过 | 不可单独归档 |
| behavior-verified | E2E 或主路径命令证明行为改变 | 可归档 |
| fail-closed | 失败时会阻断或发出可观测信号 | 高风险项必须满足 |
| archived | 行为证据完整，已移入 full tracker | 最终状态 |

`pytest passed` 只能证明 implemented，不能证明 completed。

### 2. 归档必须附结构化证据

不接受"已验证""E2E 确认"等纯文字声明。每个归档项必须填写：

```yaml
issue_id:
original_symptom:         # 最初的失败现象
claimed_fix:              # 声称的修复内容
changed_paths:            # 实际修改的文件
active_entrypoint:        # 当前默认入口
active_path_trace:        # 从入口到修改点的调用链
runtime_conditions:       # 运行时条件是否满足
verification_commands:    # 用于验证行为的具体命令
expected_behavior:        # 预期行为
observed_behavior:        # 实际观察到的行为
fallback_behavior:        # 失败/降级时的行为
evidence_locations:       # 日志/transcript/event 的具体路径
regression_test:          # 回归测试命令
archive_decision:         # 归档理由
```

没有这份 evidence bundle，不允许从短清单移入 full archive。
`flow_improvement_check.py` 应强制解析此结构，缺必填字段即阻断。

### 3. 收回 suppress_codes 豁免权

将以下三个 warning 硬编码升级为不可抑制：

- `W_VERIFICATION_BEHAVIOR_MISMATCH`
- `W_INTEGRATION_NO_PRODUCTION_CALL_EVIDENCE`
- `W_INTEGRATION_TASK_SHALLOW_VERIFICATION`

只要 task 声称修改了主干逻辑，就必须写出涉及生产调用的测试。
plan 编写者不得自行免除集成验证责任。

### 4. 建立假完成隔离区

把 AF 引擎、模型选择、评价闭环、WORKFLOW_EVALUATION、suppress_codes 这些
曾经反复假完成的项目全部移入 `false-completion-quarantine` 清单。
每一项必须重新证明**原始症状是否消失**——不接受"代码改了""函数存在"。

### 5. 反推诿锁死机制

若某个问题在 Tracker 中连续 2 轮被标记为"不在本次范围/已知局限"，
状态机自动将其升级为 P0-Blocker。在此修复并提供行为证据前，
冻结生成任何新 Plan 的权限。

## M1：补 Ralph/Flow 检查规则

目标：把 Codex/人工能发现的问题固化成 Ralph 自动规则。

### 1. DG-1：active-path reachability（最高优先级）

升级 `_check_integration_call_evidence`，从当前系统活跃入口构建调用连通图。
被修改的 symbol 必须从默认 entrypoint（含引擎分支选择）可达。

应覆盖的场景：

| 场景 | 检测名 |
|------|--------|
| 新函数写好了，但 orchestrator 没调用 | `fix-on-dormant-path` |
| AF 路径改了，但当前默认仍走 legacy | `inactive-engine-path` |
| 只改 compile path，execute path 没变 | `compile-without-execute` |
| guide 改了，但运行时代码不读 | `doc-only-behavior-claim` |
| record/write 端有了，但 read/consume 端没有 | `write-without-consumer` |

验收用例应包括一个"AF 组件存在但主路径不调用"的 fixture，
必须让 `ralph validate` 失败。

**博弈风险提示**：静态 AST 分析可被 Agent 通过插入死分支（如 `if FORCE_RUN: call()`）绕过。
DG-1 作为第一道防线仍值得实现（拦住非故意遗漏），但不能作为唯一验证手段。
应搭配 M1.5 的行为证据门和 M4 的固定回归场景，形成多层拦截。

### 2. DG-3：observable-fallback

AST 扫描所有 `except: pass`、`return False`（核心控制流）及兜底常量。
强制要求该作用域内必须存在 `>= WARNING` 日志或 `emit(Event)` 调用。

对 AF 引擎，不能再出现 `CCCC_AF_ENGINE_ENABLED=1` 但实际静默回到 legacy。
若 AF 不可用，要么阻断，要么发出明确事件：

```
af.execution_unavailable
af.runtime_not_ready
af.fallback_to_legacy_explicit
```

### 3. DG-4：guard-ordering

声称"阻断 X"的检查，必须在 X 的副作用之前执行。

| 声称阻断的对象 | gate 必须位于 |
|-------------|-------------|
| `workflow.completed` | emit completed event 之前 |
| 写入 archive | archive commit 之前 |
| actor dispatch | dispatch side effect 之前 |
| WORKFLOW_EVALUATION 完成 | terminal event 之前 |

### 4. DG-2：semantic-default consistency

同一语义默认值不能散落在多个文件里各自硬编码。建立 semantic defaults registry：

```yaml
semantic_defaults:
  executor_runtime:
    canonical: codex
    allowed_overrides:
      - security_review
      - frontend_aesthetic_review
    definitions:
      - agent_pool.py
      - assignment_actor_registration.py
      - actor_cli.py
```

task 修改其中一个定义点时，Ralph 必须提示其它同语义定义点。

### 5. verification 行为证据门

涉及运行时行为的 task，plan 的 verification 不得仅为 `pytest`。
必须至少包含一个主路径命令：

```bash
cccc model suggest backend
cccc workflow run ...
grep "execution_engine: af" daemon.log
grep "[af] execution done" daemon.log
cccc group events <group_id>
```

### 6. review adoption check

每条 Codex review finding 必须有 accepted / rejected / deferred 状态和原因。
不允许 review 提了问题但 plan 完全不回应。

## M2：闭合三条当前主路径问题

目标：用真实路径证据关闭 AF、模型选择、复盘三条反复假完成的链路。

### A. AF 引擎：从"能启动"改成"正确完成"

| 项目 | 改法 | 验收 |
|------|------|------|
| worker 完成权 | AF node 不能在 send 后自动 complete，必须等待 terminal event | 日志显示 dispatch → worker terminal → verification passed |
| auto_complete | 废除 `auto_complete_after_send=True`（fire-and-forget），重构 CCCCActorRunner 为 suspend-until-terminal | node 挂起直到 Worker 抛回 Terminal Event |
| fallback | 所有 AF→legacy 回退必须发事件和 warning/error | ledger 中有 fallback reason |
| verification gate | AF completed 不等于 CCCC task completed | 只有 verification gate 通过才 emit task complete |
| runtime readiness | `_af_runtime_ready()` 必须验证真实 pool/actor/gateway 可用 | 不允许 env var 单独代表可用 |
| 重复派发保护 | attempt_id + lease 机制防止 override→dispatch→fail 死循环 | 无重复 dispatch |
| 严格模式 | E2E 测试环境下 AF 不可用应 fail-closed 而非降级 legacy | E2E 中 AF 缺失直接失败 |
| E2E 证据 | 跑一条真实 workflow | 输出中明确出现全部以下标记 |

AF 完整验收命令链：

```
CCCC_AF_ENGINE_ENABLED=1
workflow started
execution_engine: af
[af] dispatch started
[af] worker terminal received
[af] verification passed
[af] execution done
no duplicate dispatch
no silent legacy fallback
```

### B. 模型选择：从"Guide 建议"改为"流程消费"

| 项目 | 改法 | 验收 |
|------|------|------|
| 读端闭合 | `actor add` 默认路径先调用 `model suggest` 或同等选择函数 | actor 创建日志包含 model_selection_decision |
| 数据修正 | codex 覆盖 backend/general/code_execution 等执行类 task type；claude 收窄到 review/frontend/aesthetic | `cccc model suggest backend` 返回 codex |
| 命名空间统一 | task type 与 strengths 关键词统一：backend、general_execution、code_change、security_review | 无命名空间不通导致的匹配失败 |
| enabled 过滤 | disabled model 不参与候选 | 测试覆盖 enabled=false |
| rating 消费 | `select_model_for_task` 必须读取 foreman_rating | rating 变化影响 suggest 结果 |
| override 留痕 | 显式 `--runtime claude` 不硬拦，但必须记录 override reason 和 selector-bypass event | 复盘可审计 |
| E2E 验证 | 跑实际 workflow，看 worker runtime 分布 | 默认执行 worker 应主要为 codex |

不通过 system prompt 强化"请用 codex"。应让模型选择流程本身成为 actor 创建路径的数据来源。

### C. WORKFLOW_EVALUATION / 复盘：空章节阻断 workflow.completed

| 项目 | 改法 | 验收 |
|------|------|------|
| 内容检查前置 | 在 `workflow.completed` 之前检查 evaluation 内容 | 空章节阻断 completed |
| 八维复盘强制 | runtime 选择、codex/claude 分工、agent 数量、安全审查、review 证据、Foreman 自评、rating 读写、prompt 改进 | 缺任一维度失败 |
| rating 真执行 | 不只查 "rating" 字样，要查 registry 时间戳和 model usage 记录 | registry 有本轮更新 |
| 复盘影响下一轮 | 评价结果必须被模型选择或 agent 规划读取 | 下一轮 `model suggest` 能体现评分变化 |
| 激活死代码 | `_check_placeholder_content()` 必须被实际调用 | 空章节/占位符阻断 |

验收标准：

```
空 WORKFLOW_EVALUATION.md → workflow.completed 被阻断
只有标题的复盘 → step-7 check failed
有 rating 但无 runtime 分析 → step-7 check failed
有 review 文件但未采纳/未解释 Codex findings → review step failed
```

## M3：落地蓝图中间层——模块化拆分 + 接口 + 黑盒验收

目标：在 pytest 和人工 E2E 之间补齐 Module/Task/Batch 三层验收。
Worker 不再"既当运动员又当裁判"。

### 1. 引入 module_specs

每个 Task 先被 Foreman 拆成多个 Module，每个 Module 必须有固定结构：

```yaml
tasks:
  - id: T1
    goal: ...
    modules:
      - id: T1.M1
        purpose:
        interface:
          provides:
            name:
            input_schema:
            output_schema:
          consumes:
            - name:
              schema:
        mock_inputs:
          - name:
            value:
        expected_outputs:
          - name:
            value:
        black_box_tests:
          - command:
            expected:
        integration_contract:
          upstream:
          downstream:
        completion_evidence:
          required:
            - module_io_passed
            - schema_contract_passed
            - self_test_fresh
```

### 2. 四层验收体系

| 层级 | 谁负责 | 验收方式 | 不允许通过的情况 |
|------|--------|---------|--------------|
| Module 级 | Worker | 给定 mock input，输出 expected output | 只提交代码、无 I/O 证据 |
| Task 级 | Foreman / Ralph | 模块拼接 + consumes/provides 契约测试 | 模块各自通过但拼不上 |
| Batch 级 | Orchestrator / Ralph | 当前 frontier 全部完成后跑批次 E2E | 单个 task 绿但批次行为不变 |
| Global 级 | E2E Flow | 全流程场景验证 | tracker 归档但症状仍复现 |

### 3. Worker 输入收窄

Worker 不应拿到"修整个系统"的大任务，而应拿到：

```
模块目标
接口规范
模拟输入
允许修改路径
禁止修改路径
失败时上报格式
```

减少"自己理解需求、自己定义完成、自己写测试证明自己完成"的空间。

> **修正（v69，与工作流蓝图对齐）**：原清单含「预期输出」「验收命令」，但与工作流蓝图 1.3/3.2/4.3
> 「Worker 全程不知道测试输入和**预期输出**、不知道自己模块的最终测试用例」以及既有不变量
> `prompt_builder.py`「mock_tests must never be rendered to workers」直接冲突——把 oracle/验收命令
> 给 worker 会让其 teach-to-the-test，反而违背本计划「消除自己写测试证明自己完成」的主轴。故按蓝图
> **盲验证**收口：worker 只拿 mock_inputs + 接口规范（开发输入），expected_outputs 与 black_box_tests
> 验收命令由 module-acceptance 引擎独立运行、worker 不可见。M3-3 实现已据此修正。

### 4. 批次级行为断言

批次完成后的 E2E 不受 plan suppress_codes 控制：

```yaml
batch_e2e:
  commands:
    - "cccc model suggest backend"
    - "cccc workflow run sample-af-task"
  assertions:
    - "model_runtime == codex"
    - "execution_engine == af"
    - "workflow.completed emitted only after verification_passed"
```

### 5. 假完成拦截映射

| 假完成类型 | 蓝图中间层如何拦截 |
|-----------|------------------|
| AF 组件写好但 orchestrator 不调用 | Task 级拼接验证失败 |
| compile 了但没有 execute | Module/Task 验收缺少 expected output |
| model rating 只写不读 | Batch E2E 中 `model suggest` 输出不符合预期 |
| WORKFLOW_EVALUATION 空章节 | 黑盒输出对照失败 |
| 默认 runtime 改一处漏一处 | interface/default registry consistency 失败 |
| guide 改了但行为没变 | Batch E2E 行为断言失败 |

## M4：建立固定 E2E 回归场景

目标：不再每轮临时设计 E2E。建立一组"假完成回归场景"，每次 solve flow 后自动跑。

### 回归场景集（至少 6 个）

| 场景 | 预期 |
|------|------|
| AF 默认启用 | 日志显示 `execution_engine: af`，出现 `[af] execution done`，无 legacy fallback |
| AF runtime 缺失 | fail-closed 或明确 `af.execution_unavailable` event，不允许静默 legacy |
| 模型选择 backend task | `cccc model suggest backend → codex`，actor runtime 主要为 codex |
| Foreman override runtime | 允许但必须有 selector-bypass event 和复盘说明 |
| 空 WORKFLOW_EVALUATION | workflow.completed 被阻断 |
| 假集成 fixture | 新模块存在但主路径不可达时，DG-1 失败 |

### evidence bundle 结构

每个场景输出一个结构化结果：

```yaml
scenario_id:
  command:
  expected:
  actual:
  pass:
  logs:
  events:
  regression_lock:
```

归档时引用 bundle，而不是引用自然语言结论。

## M5：改造 Solve Flow / E2E Flow 的通过条件

### Solve Flow

| Step | 当前 | 改进 |
|------|------|------|
| Step 1 Understand | 无检查 | 必须产出"原始症状、活跃路径假设、需要证明的行为变化" |
| Step 2 Plan | plan.yaml 存在 + validate 0 error | plan 必须含 behavior verification，不得只含 pytest |
| Step 3 Codex Review | JSON 格式正确 + success=true | review findings 必须被采纳、显式拒绝或登记为 deferred；增加 call-chain/fallback/guard-ordering/default-drift 四类审查维度 |
| Step 4 Gaps | tracker 有新增 | 缺口必须生成 validate rule 或 flow check 任务 |
| Step 5 Execute | pytest 退出码 0 | pytest + 主路径命令 + 日志断言全部通过 |
| Step 6 Guide | guide 文件存在 | guide 只能记录已由规则/证据证明的内容，不能作为完成依据 |

### E2E Flow

| Step | 当前 | 改进 |
|------|------|------|
| Step 4 Review | 关键词存在 + ≥500 字节 | WORKFLOW_EVALUATION 每个章节必须实质化，空章节失败 |
| Step 6 Improvement | 关键词匹配 | verified 项必须引用 evidence bundle |
| Step 7 Retrospective | 关键词 + registry 时间戳 | 检查八维复盘完整性，验证 rating 真写入且被读取 |
| Step 8 Cleanup | group stop 退出码 0 | 额外确认无 orphan actor / repeated dispatch / stale lease |
| 全局 | 无 | 自动断言 AF 是否执行、模型选择是否符合预期、是否有 silent fallback |

## 实施顺序

### 第一阶段：M0 + M2（止血 + 闭合主链路）

先做 M0 的归档冻结、evidence bundle、suppress 白名单化、反推诿锁死。
并行修 M2 的 AF-07（fire-and-forget 是当前最危险的 bug，不能等规则补好才修）、
模型选择读端、评价阻断。

退出标准：真实 E2E 中 AF 跑完整任务、`model suggest backend → codex`、
空 WORKFLOW_EVALUATION 被阻断。

### 第二阶段：M1（Ralph 规则补齐）

上线 DG-1（调用可达性）和 DG-3（静默降级捕捉）。
搭配 DG-4（guard-ordering）和 DG-2（semantic-default）。
同步完成 review adoption check。

退出标准：一个"AF 组件存在但主路径不调用"的 fixture 能被 `ralph validate` 自动拦截。

### 第三阶段：M4 + M5（回归场景 + Flow 关口升级）

建立 6 个固定回归场景，每次 solve flow 后自动跑。
改造 Solve Flow Step 1/5 和 E2E Flow Step 4/6/7 的通过条件。

退出标准：假完成回归场景全部自动通过；
flow 不再依赖"看起来完成"，每一步都有行为证据。

### 第四阶段：M3（蓝图中间层）

先从一个 task 类型试点（如 model selection 或 WORKFLOW_EVALUATION），
建立 module_spec、mock I/O、expected output、拼接测试。
验证闭环后再推广到 AF 和通用任务。

退出标准：一个真实 Task 能被拆成至少两个 Module，
用 mock I/O 黑盒验收，再拼接通过 Task verify gate。

## 后续每个问题的完成标准

```
1. 原始症状被重新复现或明确记录
2. 修改点从当前默认 entrypoint 可达
3. 运行时条件在 E2E 环境中满足
4. 主路径行为发生可观察变化
5. fallback 不静默
6. 失败用例会失败，修复后会通过
7. 归档项引用具体 evidence bundle
8. Codex review 发现已采纳、拒绝或转成 tracker item
```

核心判断标准只有一个：不要再问"代码有没有写完"，只问"原始症状是否在真实主路径中消失"。
