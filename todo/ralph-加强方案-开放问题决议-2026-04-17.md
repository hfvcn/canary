## Q1 · #1 hard guard 默认拦在哪一层（v2 · Codex 审查修正）

**v1 立场被否**：原来写"同时拦在 `on_task_completed` 和 `_auto_sync_plan_state`"。Codex 指出这是**太晚的拦截点**——真实 call chain 是：
```
complete_task()
  → apply_task_event("completed")                          ← workflow_orchestrator.py:2137
    → engine.report_worker_completion()                    ← workflow_state_engine.py:189
      (_run_pre_transition_hooks KIND_TASK_REPORTED_COMPLETED)
    → engine.record_verification_result()                  ← workflow_state_engine.py:206
  → on_task_completed()                                    ← 只在终态之后
```
到 `on_task_completed` 时 ledger 的 `workflow.task_reported_completed` / `workflow.verification_*` 已写、engine state 已进入 VERIFYING/COMPLETED——guard 做的不是"拦截"，是"事后补记"，依然脑裂。

**v2 立场**：**前移到 WorkflowEngine 的 pre-transition hook**。`workflow_state_engine.py:112 register_pre_transition_hook` 已是现存机制（`workflow_orchestrator.py:202-204` 已注册了多个 hook，如 `create_completer_mismatch_hook`）。新增 `create_plan_digest_freshness_hook(plan_context, plan_path)`：
- 注册时机：daemon 初始化 orchestrator 时（与现有 3 个 hook 同批）
- 拦截 kind（v3 Codex round-3 修正，覆盖**全部非可逆 transition**）：
  - `KIND_TASK_REPORTED_COMPLETED`（`workflow_state_types.py:17`）
  - `KIND_VERIFICATION_PASSED`（`:19`）
  - `KIND_VERIFICATION_FAILED`（`:21`）
  - `KIND_VERIFICATION_SKIPPED`（`:20`）
  - `KIND_TASK_FAILED`（`:18`）
  原来只注册在 `KIND_TASK_REPORTED_COMPLETED`；Codex round-3 指出其他 5 个 kind 也直接 `_append` + 改 engine state 不走 pre-hook（`:196-259`），task 在 RUNNING/VERIFYING 期间 plan 变 stale 时仍可写 ledger/state 产生 drift
- 行为：hook 收到 `data` 时计算当前磁盘 `plan_digest`；与 `plan_context.plan_digest` 不一致 → 抛 `PreTransitionVetoed` 错误，engine **拒绝进入终态**，事件不入 ledger
- override 通道：hook 从 `data.get("override_stale_digest")` 读显式标记；CLI `--force-stale-complete` 在 `apply_task_event` 入口把 flag 写入 event.data
- 仍 emit ledger 事件：**在 hook 抛 veto 的同一事务里**写 `workflow.plan_digest_divergence`（新事件 kind），携带 `{registered_digest, current_digest, task_id, override_used}`。这是唯一被写的事件——terminal state 事件一条都不写

**`on_task_completed` / `_auto_sync_plan_state` 改为 defense-in-depth**：
- 不再是主拦截点
- 仅做二次校验，若 pre-transition hook 漏（理论上不可能）则 emit `workflow.plan_digest_divergence_post_hoc` hint 给 audit
- 不影响流程

**依据（代码锚点）**：
- `workflow_state_engine.py:112-113` pre_transition_hooks 注册接口
- `workflow_state_engine.py:140, 189` hook 在 `KIND_TASK_STARTED` / `KIND_TASK_REPORTED_COMPLETED` 入 engine 写入**之前**触发
- `workflow_orchestrator.py:202-204` 现有 3 个 hook 注册——digest guard 是第 4 个
- `workflow_state_types.py:17` KIND_TASK_REPORTED_COMPLETED 的 canonical name

**落点**：
- Wave 2 任务改名为 `W2-pre-transition-digest-guard`，claimed_paths 增加 `src/cccc/kernel/workflow_state_engine.py` 的 hook 注册入口（如果 hook 模块独立可抽出）以及 `workflow_state_types.py`（新增 kind）；不再只改 `workflow_orchestrator.py`
- `PlanContext.runtime_plan` 冻结语义保留；`tests/test_foreman_workflow.py:1688` 不受影响
- validate 侧的 `W_REGISTERED_PLAN_STALE`（warning）保留——用于计划阶段尽早提醒作者

## Q2 · #5 confidence 阈值（v2 · Codex 审查修正）

**v1 立场被否**：两处致命问题：
1. **Taxonomy 冲突**：原决议写 `exact | heuristic | unknown`；代码实际用 `exact | best_effort | opaque`（`semantic_metrics.py:16` CONFIDENCE_LEVELS、`ConsistencyLevel` 枚举）——引入新 taxonomy 会破坏 `gate_readiness` 统计和 audit 消费路径。
2. **升级门方向错**：用"stale path 与 task.claimed_paths/covers.paths/target.path 交集非空"作为 warning 门，**天然漏掉最典型的 interface/rename 破坏场景**——因为 `semantic_validator.py:1086-1106 _check_interface_consistency` 专门抓的是 **scope 外** stale refs（"改了接口但没修外部调用方"），这类 stale path 按定义不在任何一个 task 的 claimed/covers/target 内。

**v2 立场**：

**1. Taxonomy 沿用 `exact | best_effort | opaque`**（代码既有），不新引入枚举。决议中其他位置提到的 `confidence` 全部指这三档。

| 级别 | 来源 | 代码锚点 |
|---|---|---|
| `exact` | provider 返回精确符号解析（`find_symbol` single match + `find_references` non-opaque） | Serena-strict 路径 |
| `best_effort` | provider 可用但结果部分 opaque 或多义；fallback 推断 | `semantic_validator._load_current_references` None 不等的情况 |
| `opaque` | provider 不可用 / mode=off / 无法解析 | `semantic_validator._load_current_references` 返回 None |

**2. #5 主升级门 = `ConsistencyReport.overall == "inconsistent"`**（`semantic_validator.py:1148`），配合以下二级条件：

- **Primary**：`report.overall == "inconsistent"` **且** stale refs 集合中**至少一条** `confidence == "exact"` → 升 warning `W_VERIFY_PASSED_BUT_SEMANTIC_INCONSISTENT`。注意：path 是否在 task claimed_paths **无关**——我们要抓的就是"scope 外破坏"。
- **Secondary**：`report.overall == "inconsistent"` 但所有 stale refs confidence 都是 `best_effort` → 仅升 hint；同一 task 在 `ralph audit` 统计里连续 ≥3 轮复现 → 升 warning（W5 不实现累积计数，留给 Wave 9）
- **Inconclusive**：`report.overall == "inconclusive"`（有 opaque）→ hint + `semantic_details`，不升 warning，显式带 `"provider_degraded": true`
- **Consistent**：`report.overall == "consistent"` → 不 emit issue

**3. Worker-facing 映射层（不改代码 taxonomy，只改展示）**：

Wave 4 `W4-2-issue-digest` 在注入 worker prompt 时，把 `exact | best_effort | opaque` 映射成给 LLM 看的人话：
- `exact` → "verified by semantic layer"
- `best_effort` → "inferred, likely"
- `opaque` → "unverified"

映射只在 prompt 渲染时发生，不污染 core taxonomy。

**落点**：
- Wave 4 `W4-finding-metadata` 任务给 `ValidationIssue` 加 `confidence: Literal["exact","best_effort","opaque"]` + `source: str` + `action_owner` + `worker_relevance`；**不引入 `heuristic` / `unknown`**
- Wave 5 `W5-5-semantic-inconsistency` 任务按上述 `report.overall + 最高 stale confidence` 的组合门实现；claimed_paths 加 `src/cccc/ralph/semantic_metrics.py`（确保 gate_readiness 的 taxonomy 一致性不被 W4 改字段时破坏）
- Wave 8 `W8a-provenance-and-issue-id` 不动 confidence taxonomy，只加 provenance chain

## Q3 · #8 活跃 competing workflow 判定（v2 · Codex 审查修正）

**v1 立场被否**：两个虚构前提：
1. `acquire_write_lease(path, workflow_id, ttl_s)` API **不存在**——`runtime_plan.py:26-73` 只做本 workflow 的 state projection，没有 lease 机制
2. `workflow.heartbeat` event kind **不存在**——`workflow_state_types.py:16` 只有 task 级 `KIND_TASK_HEARTBEAT = "workflow.task_heartbeat"`（加 `last_heartbeat` 字段挂在 task 上）

**v2 立场**：**不新造 lease；复用现有 task heartbeat + 真实 defer 边界 `_defer_batch_for_single_writer`**。

**规则**：

1. **Active workflow 判定**（v3 Codex round-3 修正——冷启动窗口）：workflow 视为"活"当且仅当
   - workflow 状态非 `completed/failed/cancelled`（engine state）**且**
   - 至少一个 task 的 **`max(started_at, last_heartbeat)`** 在过去 **300s** 内更新过
   - `started_at` 在 `report_worker_started`（`workflow_state_engine.py:142`）写入，比首个 heartbeat 更早
   - 原来只看 `last_heartbeat`；Codex round-3 指出 `register_task`/`register_batch`/`approve_batch`/`report_worker_started` 都不写 `last_heartbeat`（`:58-110,142`），冷启动窗口内（dispatch → 首个 heartbeat）workflow 会被误判为不活跃
   - 如需覆盖 dispatch→start 空窗（batch approved 但 worker 还没 start），额外纳入 `assigned_at`（`workflow_state_types.py:51,58`）

2. **Competing 判定**：
   - 对每个 pending task，扫描所有 active workflow 的 `task.claimed_paths`（engine 里已有）
   - `path ∩ other_workflow_task.claimed_paths != ∅` → 视为 competing

3. **Defer 触发点**：**`workflow_orchestrator._defer_batch_for_single_writer`（:687-781）**——这是**现有**的 defer 入口；不动 `runtime_plan.py`
   - 扩展它接受 `external_competing_claims: Dict[path → {workflow_id, task_id, heartbeat_age_ms}]` 参数
   - 参数由调用方（orchestrator `_approve_and_dispatch` 路径）在调用前查询全局 engine state 算出
   - Defer 时除了本有的 reason，追加 external pressure reason

4. **Ledger event**：
   - 沿用**现有** `KIND_TASK_DEFERRED = "workflow.task_deferred"`（`workflow_state_types.py:25`），在 event data 里新增 `deferral_reason ∈ {"internal_writer_conflict", "external_workflow_pressure"}` + `competing_refs: [{workflow_id, task_id, overlapping_paths, heartbeat_age_ms}]`
   - **不**新造 `workflow.task_deferred_due_to_external_write_pressure`——给同一 kind 加 reason 分类即可

5. **不升格为 lease**：本轮不引入 lease。如果未来确实需要 lease（例如长时间任务要锁定路径超过最后一次 heartbeat），作为 §4.6 后续改进另立。

**落点**：
- Wave 10 `W10-cross-workflow-pressure`：
  - claimed_paths 改为 `workflow_orchestrator.py`（`_defer_batch_for_single_writer` 扩参）、`workflow_state_types.py`（可能新增 deferral_reason 常量）、`contracts/v1/event.py`（扩展 TaskDeferredEvent 数据模型）
  - **删除**原来对 `runtime_plan.py` 的修改声明
  - **删除**对 `acquire_write_lease` / `workflow.heartbeat` 的引用

## Q4 · #9 dual-read 兼容窗口

**立场**：**3 阶段迁移，总窗口 90 天**，退役基于事实（v0 事件实际消失），不设固定 cutoff。

**阶段**：
1. **Phase A（launch → +30d）**：writer 单写 v1 schema，reader 同时接受 v0/v1；reader 读 v0 时静默
2. **Phase B（+30d → +90d）**：reader 读 v0 时记录 counter（per-ledger/per-day），ledger `ralph.schema_stats` debug event
3. **Phase C（条件退役）**：当连续 **30 个日历日** 在所有已知 ledger 采样中都 `v0_events_read == 0`，Wave 8 后续 PR 可删除 v0 read path；删除前在 release notes 明确

**不采用 hard bump 的理由**：现场 daemon 和 ledger 是长生命周期，立刻失读旧事件会导致 audit 命令无法回溯（评审 3:1 共识）。

**落点**：
- Wave 8 `W8-ledger-schema-parity` 任务实现 dual-read + `event_schema_version` stamp
- 新增 debug 事件 `ralph.schema_stats`（周期写，非 per-event）
- 不进 Wave 10 后的清退脚本——清退作为后续方案（§4.6 范畴）

## Q5 · Suppress Lease 迁移策略（v2 · Codex 审查修正）

**v1 立场被否**：用 `_provenance` hash set 区分 new/legacy suppress **不成立**——
- `_provenance` 是 `Plan` 的**私有内存属性**（`models.py:287` `_provenance: Dict[str, str] = PrivateAttr(default_factory=dict)`），**不持久化**
- loader（`plan_io.py:199-201, 436-449`）目前只给 `critical_entrypoint` / `critical_flow` / `registration_invariant` 打 provenance——**从未给 suppress 建 identity**
- 结果：每次 daemon restart / reload / CLI 单次调用，所有 suppress 都是"第一次见"，Phase A 的 `E_SUPPRESS_LEASE_INCOMPLETE` 会随机打在所有 legacy 条目上，迁移噪音不可审计

**v2 立场**：**Identity 必须持久化在 plan 本身**。不再试图用运行时 provenance 推断"新旧"。

**规则**：

1. **Identity = plan 文件里的显式字段 + 占位值拒绝**（v3 Codex round-3 修正）：`SuppressInstance` 是 new 的标志 = "具备完整 lease metadata **且值有效**"：
   - `owner` 非空 **且** 标准化后不在占位词集 `{todo, tbd, unknown, n/a, xxx, placeholder}` 中
   - `reason` 非空 **且** 同上占位词检查
   - `expiry` 非空 **且** 可解析为 ISO date `YYYY-MM-DD` **且** ≤ 声明日起 2 年（防 `9999-12-31` 永久占位）
   - 三者**都有效** → "managed"
   - 任一缺失 → "legacy"
   - 任一"非空但无效"（占位词 / 无法解析 / 超上限） → `E_SUPPRESS_LEASE_INCOMPLETE`（半填状态，Codex round-3 指出 `TODO/TBD/9999-12-31` 三件套能空过原规则）
   - 判定**纯基于 plan 文件内容**，不依赖运行时、不依赖 git、不依赖进程内存

2. **Phase A 规则**：
   - legacy suppress：silent 加载，不报 error
   - new suppress（声明了 lease 三件套）：字段缺漏报 `E_SUPPRESS_LEASE_INCOMPLETE`（理论上不该发生，因为"缺漏 = legacy"，但保留用于保护"三件套填了一半"的混乱情况，例如只填 owner 不填 expiry）
   - CLI `ralph suppress add`：**强制三件套**——若用户不传就拒绝写入（CLI 层 enforcement，不经 plan 校验）

3. **Phase B (+30d)**：遍历所有 legacy suppress → emit `H_SUPPRESS_LEGACY` hint（列出 `file:line`，按 action_owner=author 标记）。不再需要"哪些是新、哪些是旧"的区分——区分由 metadata 本身回答

4. **Phase C (+90d)**：`H_SUPPRESS_LEGACY` 升级为 `W_SUPPRESS_LEGACY` warning（+30d 后再升到 error）。legacy 条目补齐 lease metadata 后自动"变 new"

5. **`W_SUPPRESS_EXPIRED`**：suppress 有 `expiry` 且 expiry < today。纯基于字段判断，与 identity 判定同路径

6. **`W_ORPHANED_SUPPRESSION`**：suppress.task 在 `state.completed_task_ids` 内。与 identity 无关

**CLI 协助（可选）**：`ralph migrate-suppress plan.yaml` 交互式让用户填 owner/reason/expiry，输出 diff。用户自己 review 后 commit；不自动改文件。

**落点**：
- Wave 8 `W8b-suppress-lease`：
  - `SuppressInstance` 扩展 `owner: str = ""`、`expiry: Optional[str] = None`（ISO date）、`review_after: Optional[str] = None`（`reason` 字段已存在于 models.py:232）
  - **不改** `_provenance`；identity 判定 = "三件套齐全吗"
  - 仅在 **Phase A** 实现：legacy silent + CLI `ralph suppress add` 强制 + `W_SUPPRESS_EXPIRED` + `W_ORPHANED_SUPPRESSION`
  - Phase B/C 留给后续方案

## Q6 · 第三输出（worker-brief / ValidationPacket）是否独立协议

**立场**：**本轮不做**。推迟到 §4.6 的 "后续改进"，等 #10 + #2 + #4 + PromptBuildManifest 有 2-3 轮实战数据后再决定。

**依据**：
- 现在 LLM worker 的主要问题是 prompt 里"关键信息被埋在散文里"，解法不必然是"新协议"，也可能是 #10 的保底区 + #2 的 digest 前置已经够
- 过早定协议 = 把还没稳定的 field 形状锁死（finding #9 "先跑通一条路径再扩展"）
- 四份评审对"包装形式"并无强共识：`worker-brief` / `ValidationPacket` / `llm-directive` 三个名字都出现过

**启动条件**（明确可观测的触发门）：
1. #10 + #2 + #4 上线后，连续 3 轮实战中 worker 遗漏"已注入但埋在 prose 里"的 blocking_constraints / execution_risks
2. 或 `PromptBuildManifest` 统计显示保底区被截断 ≥ 5% 的分发
3. 或 worker 完成任务后 verify 失败的前三名原因可归因于"prompt 结构不清"（需要 Wave 9 `ralph audit` 支持此归因统计）

满足任一条件时，开立独立方案（不进本轮 plan.yaml）。

**落点**：本轮 plan.yaml **不包含** worker-brief 任务；Wave 3 `W3-prompt-budgeter` 的 omission manifest 设计预留扩展空间（输出 JSON 结构而非纯文本），为未来协议化留接口。

## 执行顺序修正（因应上述决议）

方案原 §4.1 的 10 波顺序存在一处隐性冲突：**#2 inclusion policy 依赖 `action_owner` / `worker_relevance` 字段**，而这些字段被放在 Wave 8。若严格按波次推进，Wave 4 的 #2 跑不起来。

**修正**：把 **"ValidationIssue 最小 finding 元数据扩展"** 从 Wave 8 前置到 **Wave 4 开头**（作为 `W4-finding-metadata`），只加字段不加 provenance 链路（report_schema_version / ruleset_digest / issue_instance_id 仍留 Wave 8）。Wave 8 的任务改名为 `W8-provenance-surface`，在已有字段上继续加治理面。

这个修正不违反评审共识（评审明说 "#2 / #5 前置"），只是把"前置"落到具体 wave 位置。
