## v58 E2E 新发现

### FL-71（auth 测试使用不鉴权端点 /health 验证认证链路，P2）

tests/test_auth.py 的 `test_access_protected_endpoint_with_valid_token`、`test_reject_invalid_token`、
`test_jwt_string_sub_via_endpoint_returns_401` 使用 `/health` 端点测试认证，但 `/health` 实际不要求
认证。后两条测试甚至接受 200 作为通过条件，无法证明认证链路真实生效。

### FL-72（通知隔离测试断言逻辑失效——跨用户泄漏不可检测，P1）

test_security_review.py 的通知隔离测试允许 `notif_ids_a == notif_ids_b`，只检查 `user_id != 0`，
如果接口错误地把两个用户的通知都返回给双方，测试仍会通过。这是 critical flow
`private-channel-isolation` 的安全验证盲区。

### RV-62（independently_reviewed 标记缺乏独立 actor 证据，P2）

WORKFLOW_EVALUATION 将 T5/T6/T7/T8 全部标为 independently_reviewed，但只有 T7 由
独立角色 sec-reviewer 执行。T5/T6/T8 由 worker-1 执行，不具备独立审查属性。
标记与实际执行者不一致。

### RV-63（depends_on 与 consumes 契约不一致——消费无依赖，P2）

T4/T5/T6/T7 消费 T1 的产物（db-session/test-fixtures 等），但 depends_on 未列出 T1。
validate 的 W_CONSUME_WITHOUT_DEP 规则应检测此类不一致，但 plan 仍通过了 validate。

## 系统性反复问题（多轮复现）

### 1. Worker 全用 Claude，未使用 Codex 做主力执行（FL-73，P1）

用户明确要求"codex=主力执行"，但 v58 的 worker-1 和 sec-reviewer 全部使用 claude runtime。
foreman 读了 guide 后仍然选择 `--runtime claude` 而非 `--runtime codex`。
这不是偶发——v57 也是全 claude，说明 guide 中的模型选型指导对 foreman 无效。

**根因**：foreman-capability-guide.md 可能没有足够强制的 codex 优先规则，或 foreman 忽略了
runtime 选择指导。需要在 guide 或 flow 中添加 worker 创建时的 runtime 校验闸门。

### 2. AF 引擎从未实际启用（FL-74，P1）

WORKFLOW_EVALUATION 写着 `execution_engine: legacy`。从 v53（声称组件完成）到 v55（标记层）
到 v56（声称真正接入）到 v58，AF 引擎的执行路径从未被实际调用。
问题清单的"AF 引擎接入过程复盘"已详细记录了这个 compile≠execute 的系统性盲区。

**根因**：`_try_af_execution` 只做了 compile，没有调用 `execute_bundle`。AF 组件存在但
orchestrator 从未切换执行路径。每轮都标记为"待启用"然后推迟。

### 3. 复盘功能持续不达标——UX-23 第四轮复现（系统级）

v50/v51/v57/v58 连续四轮，WORKFLOW_EVALUATION 的定性章节全空。这已超出提示词能解决的范围：
foreman 完成结构化数据填写后认为任务完成，不会自发补充定性内容。
提示词中明确要求的"正面反馈""负面反馈""Worker 可靠性""评分+改进建议"从未被实质填写。

**根因**：workflow completion 路径没有检查定性章节是否有实质内容。需要代码级闸门。
