### #1 `W_REGISTERED_PLAN_STALE`
- 原设计：
  只做 detect-only warning，不自动解冻 frozen plan；热更新留待未来 `ralph reload-plan`。
- 评审共识修正：
  保留 frozen plan 语义，但不能停在 detect-only；需要把 stale guard 推进到 completion / sync-state / ledger 边界，至少能阻止“旧 plan 上报完成，落到账本却被用户误以为是新 plan”的脑裂。
- 是否采纳：
  采纳，但按“warning + completion/sync digest guard + stale event”落地，不采纳“自动 reread / 自动解冻”。
- 理由（基于当前代码）：
  `PlanContext` 在注册时冻结 `plan_source` 与 `plan_digest`，后续 `runtime_plan()` 一直从冻结 bytes 重建运行态。
- 理由（基于当前代码）：
  validate 路径走冻结 plan；而任务完成后的 `_auto_sync_plan_state()` 又重新 `load_plan(plan_path)` 读取磁盘 plan 并同步 state，验证面与落账/写 state 面天然分叉。
- 理由（基于当前代码）：
  这说明问题是真实存在的；但自动 reread 会直接改掉当前 Foreman 的 snapshot 语义，不符合现状，也会破坏既有测试依赖。

### #2 Prompt Task Issue Digest
- 原设计：
  在 worker prompt 里补 task 级 issue digest；原方案采用每 task top-3、`error > warning > hint`、同级内偏“改变执行策略”的 inclusion policy。
- 评审共识修正：
  应改成 actionability-first，而不是 severity-first；先保留真正改变执行策略、验证路径、风险判断的 issue，再做额度内裁剪。
- 是否采纳：
  采纳，但修正为“先 actionability / owner，再 severity”，并强制依赖 #10 的预算器。
- 理由（基于当前代码）：
  `_iter_task_validation_issues()` 已经能按 task 收集 errors / warnings / hints，但 `_build_task_prompt()` 完全没有把这些 issue 注入 prompt。
- 理由（基于当前代码）：
  现有 prompt 已同时拼接 worker prompt、runtime adapter、semantic context、context store，属于多来源累加；如果继续把 digest 硬塞进去而不先做预算，assignment 核心内容会被淹没。
- 理由（基于当前代码）：
  因此评审对“selection 逻辑要先改”“Budgeter 必须前置”的修正符合项目实际。

### #7 Structured Internal Failure Envelope
- 原设计：
  不把 Ralph 内部异常伪装成 ValidationIssue，而是走 out-of-band：CLI exit code 2、JSON 顶层 `error` 对象、orchestrator 单独字段。
- 评审共识修正：
  除了 error envelope 本身，还需要稳定的 `stage` / `internal_error_code`，并且默认不直接向普通路径暴露整段 traceback。
- 是否采纳：
  采纳，且前置到最早波次；不采纳“塞回 report 里当普通 rule”的做法。
- 理由（基于当前代码）：
  CLI 当前只包住 `load_plan()`，后续 `validate_with_project()`、semantic provider、正则/AST 内部异常都可能直接 traceback 冒泡。
- 理由（基于当前代码）：
  Orchestrator validate 路径默认假设拿到的是正常 report，并无内部失败与 plan 失败的稳定分层。
- 理由（基于当前代码）：
  这类故障属于系统自错，不是 plan defect；评审要求将其与 ValidationIssue 分离，符合项目边界。

## 2. 第二阶段其他 6 项（#3/#4/#6/#8/#9/#11）

### #3 Serialize Semantic Summary
- 评审口径：
  一致支持“不要再丢 `fingerprints / suggested_deps`”，但反对把 provider 内部结构原样扩散到 IPC；应改成 bounded、versioned summary。
- 是否采纳：
  采纳。
- 理由：
  当前 `_serialize_validation_report()` 只保留 `errors / warnings / hints`，这属于明确的数据丢失；但 summary 必须可演进，不能把内部对象形状直接绑定成协议。

### #4 Recommended Tests Reach The Worker
- 评审口径：
  四份评审均认可这是“已经算出来却没送达消费者”的高回报修复。
- 是否采纳：
  采纳。
- 理由：
  `recommended_tests` 已在 Ralph 服务侧生成并放进 `semantic_details`，worker 端却完全不可见；这比新增规则更接近真实收益。

### #6 Semantic Gate Cache Freshness
- 评审口径：
  无实质分歧；都认为这是 correctness bug，不是偏好问题。
- 是否采纳：
  采纳。
- 理由：
  `_semantic_gate_cache` 当前只按 `(workflow_id, id(provider))` 命中，没有任何 metrics staleness guard；这会让 gate 长期卡在旧状态。

### #8 `W_CROSS_WORKFLOW_WRITE_PRESSURE`
- 评审口径：
  `gpp-8` 明确反对把它做成 validator warning；其他三份评审支持问题本身，但都要求收口成更窄、更像调度层的信号。
- 是否采纳：
  采纳，但改形态采纳。
- 理由：
  结论是：这不是 validator truth，而是 scheduler pressure signal。
- 理由：
  一行理由：
  它依赖“别的 workflow 当前是否仍活着、是否持有租约、是否最近有心跳”，这些都属于实时调度事实，不属于 plan 本身的真值。
- 理由：
  因此本项不以 `W_*` 规则进入 Ralph validate，而以 Foreman defer reason / coordination note / UI 可见原因落地。

### #9 Validation Ledger Schema Parity
- 评审口径：
  统一支持“必须对齐”，但 `gedt-8` 主张 hard bump，其他三份主张 dual-read / single-write migration。
- 是否采纳：
  采纳，按 migration path 走。
- 理由：
  现状确实存在 CLI 与 orchestrator 两条链路事件不对齐的问题；但直接 hard bump 会让已有 daemon 及历史事件立刻失读，不符合项目现实。
- 理由：
  先做 writer 统一、reader 兼容，再配 version stamp，才是不会阻断已有工作流的演进路径。

### #11 Text Output Semantic Parity
- 评审口径：
  一致支持；并建议与 #3、#5 靠近落地，不要让 JSON 与 text 长期双轨。
- 是否采纳：
  采纳。
- 理由：
  人类默认看的是 text，而现在只有 JSON 才携带 semantic 信息；这会直接制造“机器知道、人不知道”的假差异。

### R-1 确定性 issue 排序
- 决策：
  采纳，但修正排序键。
- 保留什么：
  “确定性排序必须做”这一点不变。
- 修正什么：
  不能只用 `task_ids[0] + stringified evidence`；改用完整 `task_ids` 序列与 canonical evidence 表达。
- 理由：
  项目真正需要的是可重复 diff 与稳定 snapshot，而不是只在多数场景下“看起来差不多稳定”。

### R-2′ `plan.schema_version` + strict extras
- 决策：
  采纳，但补 legacy banner 与迁移口径。
- 保留什么：
  声明 `schema_version` 后开启严格 extras 的方向不变。
- 修正什么：
  legacy `ignore` 不能无限期沉默存在；需要明确输出“当前仍在 legacy 宽松模式”，并给迁移窗口。
- 理由：
  这个项目确实需要兼容老 plan，但不该把 typo 静默吞掉的旧行为长期固化。

### U-3 `ralph validate --diff BEFORE AFTER`
- 决策：
  采纳，但顺序后移。
- 保留什么：
  diff 视图对 rollout 新规则非常有价值，这个判断成立。
- 修正什么：
  它不应先于稳定 `issue_instance_id` / canonical evidence / report schema version 落地。
- 理由：
  否则得到的只是“可看但噪音偏高”的 diff；用于人类参考还行，用于审计或回归判断就不稳。

### CMP-5 `H_SUPPRESS_UNUSED`
- 决策：
  采纳，但严格收口。
- 保留什么：
  只做 flavor 1，也就是“本轮未命中任何 issue 的 suppress”，这个边界继续保留。
- 修正什么：
  必须最后运行，且只作为 cleanup advisory，不升级成 warning 或 blocker。
- 理由：
  suppress 是否“永远没用”与“本轮没命中”不是一回事；治理信号可以有，但不能误导成 correctness 信号。

### CMP-6 `W_COVERS_PATHS_UNVERIFIED`
- 决策：
  采纳，但再收紧第一版触发条件。
- 保留什么：
  只限 compile / unit 层级，不碰 integration / e2e，这一条继续成立。
- 修正什么：
  第一版仅对能直接抽取 literal path 的命令报；shell wrapper / make / npm / tox 等间接调用先不强上。
- 理由：
  这项的价值是真的，但误报门槛也真实存在；第一版先保守，符合项目“先给可信信号”的原则。

### `ralph audit` 中的 `H_PLAN_AGE`
- 决策：
  暂缓，不并入 audit 首波。
- 保留什么：
  `W_TASK_FLAPPING`、`H_COMPLETED_BUT_UNVERIFIED` 继续保留。
- 修正什么：
  `H_PLAN_AGE` 不基于当前 `问题清单*.md` 的 Markdown 归档文本直接推出。

  现在还没有结构化 issue registry；直接用文档归档文本做 audit 依据，会把“文本维护状态”误当成“系统事实”。

## 6. PR 执行顺序调整

不再完全沿用原文的“第一阶段 1→2→3→4，第二阶段 α→β1→β2→γ→δ”。

调整后的关键顺序约束如下：

1. `#7` 前置。
   原因：
   至少三份评审都要求先把内部失败与 plan 失败拆开；否则后面改 prompt / report / provenance 时，排障面会混成一团。

2. `#10` 必先于 `#2 / #4`。
   原因：
   这不是优化顺序，而是实现前置；不先做预算器，任何 issue digest 与 recommended tests 注入都可能把 assignment 主体挤掉。

3. `#3 / #11 / #5` 贴近落地。
   原因：
   这三项都在修 semantic 信号“算出来了但人或控制面看不到”的同一问题；拆太开会制造新的双轨视图。

4. `#1` 早于所有 completion-side 扩展。
   原因：
   stale plan 的 guard 要先封住 validate 面与落账面的脑裂，再谈后续 audit 或 prompt 解释。

5. `#9` 不抢首波，但要先于 `ralph audit` 的 schema 消费增强。
   原因：
   它要做 dual-read / single-write；没有版本戳就先扩 audit，只会把历史兼容问题放大。

6. `U-3` 从原先的前置脚手架改为后置。
   原因：
   它依赖 `issue_instance_id`、canonical evidence、schema version；这些不稳时先做 diff 只会得到噪音。

7. `#8` 保持最后一波，而且改到 Foreman scheduler lane。
   原因：
   它不是 validate rule，而是活跃 workflow 之间的实时压力信号。

一个可执行的新顺序是：
`R-1 / R-4 / #7` → `#1` → `#10` → `#2 / #4 / Forbidden Flows Injection` → `#3 / #11 / #5` → `R-2′ + CMP-1/2/3/4/5/6/7 + U-6 + U-1′` → `#6` → `#9 + provenance stamps + issue_instance_id + U-3` → `ralph audit` → `#8`。

## 7. 开放问题 & 需进一步讨论

1. `#1` 的 hard guard 默认拦在哪里。
   是只拦 `cccc task complete`，还是连 orchestrator 自动 `_auto_sync_plan_state()` 也一起阻断；这会影响用户感知和兼容性。

2. `#5` 的 confidence 阈值怎么定义。
   需要一套项目内固定的 `exact / heuristic / unknown` 升级规则，否则 warning 与 hint 的分层仍会漂移。

3. `#8` 的“活跃 competing workflow”判定依据是什么。
   要不要要求租约、心跳或最近事件时间窗；否则很容易把历史残留 workflow 误判成当前压力源。

4. `#9` 的兼容窗口维持多久。
   dual-read 需要明确 reader 支持几个旧版本，以及何时允许清退 v0/v1 历史字段。

5. suppress lease 对旧配置的迁移策略是什么。
   老 suppress 没有 `owner / reason / expiry` 时，是 silent 兼容、warning 提醒，还是一次性迁移脚本补字段。

6. worker 第三输出格式是否真的需要独立协议。
   如果 #10 + #2 + #4 + PromptBuildManifest 已经足够稳定，是否仍要单独做 `worker-brief`，需要在第一轮落地后再看一次真实使用反馈。
